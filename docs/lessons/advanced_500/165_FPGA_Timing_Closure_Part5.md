## 1. ทฤษฎีวิศวกรรมเชิงลึก (高度なエンジニアリング理論)

### 1.1 กายวิภาคของ Clock Groups ใน SDC/XDC (Clock Group Mechanics)
ในระบบ System-on-Chip (SoC) หรือ FPGA ความเร็วสูงสมัยใหม่ มีสัญญาณนาฬิกาหลายสิบโดเมนทำงานอยู่ร่วมกันบนแผ่นซิลิคอนเดียวกัน เช่น คล็อกระบบหลัก (System Core), คล็อกหน่วยความจำ DDR4/DDR5, คล็อกบัส AXI, และคล็อกความเร็วสูงจาก SerDes Transceiver

คำสั่ง `set_clock_groups` ถูกสร้างขึ้นเพื่อจัดกลุ่มความสัมพันธ์ของสัญญาณนาฬิกาในกราฟ Static Timing Analysis (STA):

```
                   3 โหมดการทำงานของ SET_CLOCK_GROUPS
                   
   [ 1. -asynchronous (สัญญาณนาฬิกาไม่สัมพันธ์กันโดยสิ้นเชิง) ]
   Clock A (200MHz จาก XTAL 1) <──────X──────> Clock B (156.25MHz จาก XTAL 2)
   ===> สัญญาณนาฬิกาทั้งสองมีความสัมพันธ์ทางเฟสแบบสุ่ม (Random Phase Relationship)
        คำสั่งนี้สั่งให้ STA ตัดการวิเคราะห์ไทม์มิ่งระหว่างสองกลุ่มนี้ออกไปทั้งหมด!
   
   [ 2. -logically_exclusive (ไม่สามารถเกิดขึ้นพร้อมกันในเชิงลอจิก) ]
   CLK_SRC_A ──┐
               ├──► [ Clock Multiplexer BUFGCTRL ] ──► CLK_OUT
   CLK_SRC_B ──┘          ▲
                          │ SEL (สวิตช์เลือกได้ทีละ 1 คล็อกเท่านั้น)
   ===> ในทางลอจิก ไม่มีทางที่ CLK_A และ CLK_B จะทำงานในวงจรเดียวกันพร้อมกันได้
   
   [ 3. -physically_exclusive (ไม่สามารถเกิดขึ้นพร้อมกันในเชิงกายภาพ) ]
   ===> สัญญาณนาฬิกาสองตัวถูกป้อนผ่านขาพินภายนอกขาเดียวกัน (เช่น ขา CLK_PIN สลับระหว่าง 2 โหมด)
```

### 1.2 อันตรายระดับวิกฤตของ Blanket `set_clock_groups` (The Fatal Blind Spot)

> [!CRITICAL]
> **ภัยเงียบของการใช้ Blanket `set_clock_groups`:**  
> หากวิศวกรเขียนคำสั่งแบบกวาดคลุมทั้งระบบ (Blanket Constraint):  
> `set_clock_groups -asynchronous -group [get_clocks clk_core] -group [get_clocks clk_axi]`  
> **เครื่องมือ STA จะถูกทำให้ "ตาบอดสนิท 100%" บนทุกเส้นทางระหว่างสองโดเมนนี้!**

```
             ความแตกต่างระหว่าง BLANKET GROUP VS SAFE POINT-TO-POINT
             
   [ กรณีที่ 1: ใช้ Blanket set_clock_groups (อันตรายสูงสุด!) ]
   clk_core ──► [ Unsynchronized 64-bit Bus ] ──► clk_axi (บั๊กลืมใส่ Synchronizer!)
   ===> STA รายงาน: PASS 100% (WNS = +0.25ns)! เพราะเส้นทางนี้ถูก "ลบ" ออกจากรายงาน!
        ผลลัพธ์บนบอร์ดจริง: เกิด Metastability และ Data Bus สลับบิต ข้อมูลพังยับเยิน!
   
   [ กรณีที่ 2: ใช้ Safe CDC Constraints (มาตรฐาน Senior Engineer) ]
   clk_core ──► [ Gray Code / 2-FF Sync ] ──► clk_axi
   ===> ควบคุมด้วย: set_max_delay -datapath_only + set_bus_skew
        หากมีใครเผลอลากสายตรงโดยไม่มี Synchronizer เครื่องมือจะฟ้อง Timing Error ทันที!
```

### 1.3 กระบวนทัศน์การควบคุม CDC สมัยใหม่: `set_max_delay -datapath_only` และ `set_bus_skew`

เพื่อเปิดเผยข้อผิดพลาดของการข้ามโดเมนนาฬิกา (CDC) โดยไม่สร้าง Timing Slack Violation เท็จ วิศวกรระดับอาวุโสต้องใช้คู่คำสั่ง **Point-to-Point CDC Constraints**:

#### 1. คำสั่ง `set_max_delay -datapath_only`
คำสั่งนี้ใช้กับเส้นทางข้ามโดเมนที่ผ่านวงจร Synchronizer (เช่น ปลายทางเข้าฟลิปฟล็อปตัวแรกของ 2-Stage Sync):

```tcl
# กำหนดความล่าช้าสูงสุดเฉพาะสายข้อมูล ไม่คิด Clock Skew
set_max_delay -from [get_cells src_gray_reg[*]] \
              -to   [get_cells dst_sync_ff1_reg[*]] \
              -datapath_only 2.500
```

#### ฟิสิกส์ของสวิตช์ `-datapath_only`:
* ในการคำนวณ Slack ปกติ: $\text{Slack} = T_{required} - T_{arrival}$ ซึ่งต้องนำผลต่างของขอบสัญญาณนาฬิกาและ Clock Skew มาคิด ซึ่งทำให้เกิดข้อผิดพลาดเท็จ
* เมื่อใส่ **`-datapath_only`**: เครื่องมือจะ **ตัด Clock Path ออกจากการคำนวณ $100\%$** และตรวจสอบเฉพาะ:
  $$T_{cko} + T_{routing\_net} \le \text{Max Delay Value}$$
* **งบประมาณเวลาที่เหมาะสม (Rule of Thumb):**
  $$\text{Max Delay Budget} \le \min(T_{period\_src}, T_{period\_dest})$$
  (เพื่อรับประกันว่าข้อมูลจะเดินทางข้ามโดเมนได้ภายใน 1 คาบเวลาของสัญญาณนาฬิกาที่เร็วกว่า)

#### 2. คำสั่ง `set_bus_skew` (การควบคุมความเบี่ยงเบนของสายบัส)
สำหรับบัสพอยน์เตอร์ Gray Code หรือบัสข้อมูลแบบมัลติบิตที่ข้ามโดเมน การควบคุมเพียงแค่ Max Delay ยังไม่เพียงพอ เพราะหากบิต 0 ใช้เวลา $0.5\text{ ns}$ แต่บิต 7 ใช้เวลา $2.4\text{ ns}$ บิตทั้งสองจะเดินทางถึงปลายทางคนละไซเคิล ทำลายคุณสมบัติ Unit-Distance ของ Gray Code ทันที!

$$\text{Bus Skew} = \max(T_{net\_delay\_k}) - \min(T_{net\_delay\_k}) \le \text{Skew Budget}$$

```tcl
# บังคับให้สายไฟทุกเส้นในบัสพอยน์เตอร์มีความยาวใกล้เคียงกัน ไม่ต่างกันเกิน 800ps
set_bus_skew -from [get_cells src_gray_reg[*]] \
             -to   [get_cells dst_sync_ff1_reg[*]] \
             0.800
```
* **งบประมาณความเบี่ยงเบน (Bus Skew Budget):**
  $$\text{Bus Skew Budget} \le 0.5 \times T_{period\_dest}$$

### 1.4 กฎลำดับความสำคัญของคอนสเตรนต์ (Exception Precedence Hierarchy & Overrides)

เมื่อมีการประกาศคอนสเตรนต์ทับซ้อนกันบนเส้นทางเดียวกัน เครื่องมือ STA จะตัดสินว่าคำสั่งใดมีอำนาจเหนือกว่าตาม **กฎลำดับศักดิ์ (Precedence Rules)** ของมาตรฐาน SDC:

```
                    กฎลำดับศักดิ์ของ TIMING EXCEPTIONS
                    
   +--------------------------------------------------------------+
   | ลำดับที่ 1: set_false_path          (อำนาจสูงสุด ตัดทุกคำสั่ง)   |
   +--------------------------------------------------------------+
   | ลำดับที่ 2: set_clock_groups        (ตัดการวิเคราะห์ข้ามกลุ่ม)   |
   +--------------------------------------------------------------+
   | ลำดับที่ 3: set_max_delay / min_delay (กำหนดกรอบเวลาชัดเจน)      |
   +--------------------------------------------------------------+
   | ลำดับที่ 4: set_multicycle_path     (ผ่อนปรนรอบเวลา N ไซเคิล)    |
   +--------------------------------------------------------------+
```

#### กฎความเฉพาะเจาะจงของเป้าหมาย (Target Specificity Rules):
หากคำสั่งเป็นประเภทเดียวกัน คำสั่งที่มี **เป้าหมายเฉพาะเจาะจงมากกว่า** จะชนะคำสั่งที่เป็นแบบกลุ่มกว้าง:
1. **พินต่อพิน (Pin-to-Pin):** `-from [get_pins A/Q] -to [get_pins B/D]` (ชนะ)
2. **เซลล์ต่อเซลล์ (Cell-to-Cell):** `-from [get_cells A] -to [get_cells B]`
3. **คล็อกต่อคล็อก (Clock-to-Clock):** `-from [get_clocks CLK1] -to [get_clocks CLK2]` (แพ้)

## 2. ทริคหน้างาน OJT แบบ Step-by-Step (現場の実践テクニック)

### 2.1 กรณีศึกษาความล้มเหลวหน้างาน: สายอากาศ 5G Massive MIMO สูญเสียทิศทางจากบั๊ก Blanket Clock Groups (5G Massive MIMO Beamforming Phase Failure)

```
+----------------------------------------------------------------------------------------------------+
| กรณีศึกษาความล้มเหลวหน้างาน (現場の失敗事例)                                                                 |
| เหตุการณ์: การ์ดประมวลผลสัญญาณดิจิทัลหน้าด่าน (DFE) ของเสาอากาศ 5G Massive MIMO ขนาด 64T64R               |
| อาการ: บอร์ดผ่านการคอมไพล์ใน Vivado ฉลุย Timing Report รายงาน WNS = +0.18ns, WHS = +0.05ns ไร้ข้อผิดพลาด   |
|        แต่เมื่อนำไปทดสอบในตู้ทดสอบอุณหภูมิความร้อน (Thermal Chamber ที่ 70°C) ปรากฏว่าลำคลื่นวิทยุ (Beam)    |
|        เกิดอาการบิดเบี้ยว ทิศทางการส่งสัญญาณเป๋ไปจากเป้าหมาย 45 องศา และกำลังส่งตกฮวบจนสัญญาณหลุด!            |
+----------------------------------------------------------------------------------------------------+
```

#### การวิเคราะห์หาสาเหตุรากเหง้าด้วยหลักการ 5 Whys (5 Whys Root Cause Analysis):

1. **ทำไมลำคลื่นวิทยุ 5G จึงบิดเบี้ยวและเบี่ยงเบนไปจากเป้าหมาย?**  
   *คำตอบ:* สัมประสิทธิ์เวกเตอร์ควบคุมเฟสของสายอากาศ (Beamforming Weights ขนาด 32 บิต) มีค่าบิดเบือนไปจากที่อัลกอริทึมคำนวณไว้

2. **ทำไมค่าน้ำหนักเฟสจึงบิดเบือน?**  
   *คำตอบ:* บัสข้อมูลค่าน้ำหนักที่ถูกส่งข้ามจากหน่วยควบคุม AXI-Lite ($100\text{ MHz}$) ไปยังหน่วยประมวลผล RF Digital Up-Converter ($491.52\text{ MHz}$) เกิดสภาวะ Data Incoherency บิตข้อมูลบางบิตเปลี่ยนค่าไม่พร้อมกัน

3. **ทำไมบิตข้อมูลจึงเปลี่ยนค่าไม่พร้อมกัน?**  
   *คำตอบ:* วิศวกรลากสายบัสข้อมูล 32 บิตข้ามโดเมนนาฬิกาโดยตรง โดยไม่มีวงจร Handshake หรือ Asynchronous FIFO กั้นกลางแม้แต่น้อย!

4. **ทำไมการเชื่อมต่อบัส CDC ผิดพลาดระดับวิกฤตนี้จึงไม่ถูกรายงานเป็น Timing Violation ใน Vivado?**  
   *คำตอบ:* ในไฟล์คอนสเตรนต์ XDC มีการใส่คำสั่ง:  
   `set_clock_groups -asynchronous -group [get_clocks clk_axi] -group [get_clocks clk_dfe]`  
   ซึ่งสั่งให้ Vivado ปิดการวิเคราะห์ไทม์มิ่งระหว่างคล็อกสองตัวนี้แบบเบ็ดเสร็จ $100\%$ ทำให้เส้นทางบัส 32 บิตนี้ถูกซ่อนไว้ในเงามืด!

5. **ทำไมวิศวกรจึงใส่คำสั่ง Blanket `set_clock_groups`?**  
   *คำตอบ:* ในขั้นตอนแรกของการพัฒนา มีรายงาน Timing Violation นับร้อยเส้นทางโผล่ขึ้นมา วิศวกรจึงค้นหาวิธีแก้จากอินเทอร์เน็ตแล้วคัดลอกคำสั่ง `set_clock_groups` มาใส่เพื่อ "ลบ Error ให้หน้าจอรายงานเป็นสีเขียว" โดยไม่ได้รันการตรวจสอบโครงสร้าง CDC (CDC Structural Audit)!

### 2.3 คู่มือปฏิบัติงาน SOP: การจัดการข้อยกเว้นและการตรวจสอบ CDC สากล (Zero-Defect CDC SOP)

#### สเต็ปที่ 1: การยกเลิกการใช้ Blanket `set_clock_groups`
* ตรวจสอบไฟล์ XDC ทุกไฟล์ หากพบคำสั่ง `set_clock_groups -asynchronous` ที่ผูกระหว่างคล็อกที่มีการแลกเปลี่ยนข้อมูลกัน **ให้ลบทิ้งทันที!**
* อนุญาตให้ใช้ `set_clock_groups -asynchronous` ได้เฉพาะในกรณีที่สองคล็อกนั้น **ไม่มีเส้นทางข้อมูลใดๆ เชื่อมต่อถึงกันอย่างแท้จริง $100\%$** เท่านั้น

#### สเต็ปที่ 2: การใช้คำสั่ง Point-to-Point CDC สำหรับวงจร Synchronizer
* บนวงจร 2-Stage Synchronizer หรือ Gray Code Pointer ให้ระบุคำสั่งเจาะจงเฉพาะคู่รีจิสเตอร์:

```tcl
# กำหนด Max Delay เฉพาะบนสายข้อมูลข้ามโดเมน
set_max_delay -from [get_cells -hierarchical *cdc_src_reg*] \
              -to   [get_cells -hierarchical *cdc_sync_stage1_reg*] \
              -datapath_only [get_property PERIOD [get_clocks clk_fast]]

# กำหนด Bus Skew สำหรับเวกเตอร์หลายบิต
set_bus_skew  -from [get_cells -hierarchical *cdc_src_reg*] \
              -to   [get_cells -hierarchical *cdc_sync_stage1_reg*] \
              [expr [get_property PERIOD [get_clocks clk_fast]] * 0.5]
```

#### สเต็ปที่ 3: การรันการตรวจสอบ CDC เชิงโครงสร้างด้วย `report_cdc`
* รันคำสั่งตรวจสอบ CDC เต็มรูปแบบก่อนการลงนามอนุมัติ:
  `report_cdc -details -file cdc_audit_report.rpt`
* ตรวจสอบว่าในคอลัมน์ **Severity** ต้องไม่มีสถานะ:
  * **Critical / Error:** ต้องไม่มีบัสข้อมูลข้ามโดเมนโดยไร้วงจรซิงโครไนซ์
  * **Unknown / Unsafe:** ทุกเส้นทางต้องได้รับการรับรองเป็น **"Safe"**

#### สเต็ปที่ 4: การรันการตรวจสอบความครอบคลุมของข้อยกเว้น (`report_exceptions`)
* รันคำสั่งตรวจสอบการทับซ้อนของข้อยกเว้น:
  `report_exceptions -coverage -file exceptions_coverage.rpt`
* ยืนยันว่าไม่มีคำสั่งใดที่ถูกขึ้นสถานะ **"Ignored"** หรือ **"Shadowed"** โดยไม่เจตนา

## 3. คำศัพท์และประโยคภาษาญี่ปุ่นสำหรับตรวจแบบ (検図 - Kenzu)

### 3.1 ตารางคำศัพท์เทคนิคเฉพาะทาง

| คำศัพท์คันジ / คาตากานะ | คำอ่าน (Romaji) | ความหมายทางวิศวกรรม (Thai / English) |
| :--- | :--- | :--- |
| **クロックグループ制約** | Kurokku Guruupu Seiyaku | Clock Groups Constraint (ข้อกำหนดจัดกลุ่มสัญญาณนาฬิกา) |
| **非同期クロック指定** | Hidouki Kurokku Shitei | Asynchronous Clock Declaration (การระบุคล็อกไม่สัมพันธ์กัน) |

## 4. ควิซวิเคราะห์ปัญหาระดับวิศวกรอาวุโส (上級技術クイズ)

### ข้อที่ 1: การคำนวณงบประมาณเวลาสำหรับ set_max_delay -datapath_only และ set_bus_skew

#### โจทย์คำถาม:
ในโมดูลรับส่งข้อมูลเครือข่ายความเร็วสูง พอยน์เตอร์ Gray Code ขนาด $8\text{ bits}$ ส่งข้ามโดเมนจาก:
* โดเมนต้นทาง: $CLK_{SRC} = 250\text{ MHz}$ ($T_{period\_src} = 4.000\text{ ns}$)
* โดเมนปลายทาง: $CLK_{DST} = 400\text{ MHz}$ ($T_{period\_dst} = 2.500\text{ ns}$)

พอยน์เตอร์ถูกรับเข้าสู่ฟลิปฟล็อปตัวแรกของวงจร 2-Stage Synchronizer ในโดเมนปลายทาง  
ตามข้อกำหนดมาตรฐานสากลของการออกแบบ FPGA แบบ CDC Sign-Off:
1. ค่า **Max Delay Budget** สำหรับคำสั่ง `set_max_delay -datapath_only` จะต้องไม่เกินคาบเวลาของสัญญาณนาฬิกาที่เร็วกว่า
2. ค่า **Bus Skew Budget** สำหรับคำสั่ง `set_bus_skew` จะต้องไม่เกิน $40\%$ ของคาบเวลาสัญญาณนาฬิกาฝั่งรับ ($CLK_{DST}$)

จงคำนวณหาค่าตัวเลขที่จะต้องใส่ในคำสั่ง XDC:
1. ค่าหน่วงเวลาสูงสุดของ `set_max_delay -datapath_only` ($T_{max\_delay}$)
2. ค่าความเบี่ยงเบนสูงสุดของ `set_bus_skew` ($T_{bus\_skew}$)
3. หากในผลลัพธ์การเดินสายจริง บิตที่เร็วที่สุดใช้เวลา $0.650\text{ ns}$ และบิตที่ช้าที่สุดใช้เวลา $1.850\text{ ns}$ บัสเส้นนี้จะผ่านเกณฑ์ Bus Skew หรือไม่?

* ก. $T_{max\_delay} = 2.500\text{ ns}$, $T_{bus\_skew} = 1.000\text{ ns}$, Skew จริง $= 1.200\text{ ns}$ (ไม่ผ่านเกณฑ์!)
* ข. $T_{max\_delay} = 4.000\text{ ns}$, $T_{bus\_skew} = 1.600\text{ ns}$, Skew จริง $= 1.200\text{ ns}$ (ผ่านเกณฑ์)
* ค. $T_{max\_delay} = 2.500\text{ ns}$, $T_{bus\_skew} = 1.250\text{ ns}$, Skew จริง $= 1.200\text{ ns}$ (ผ่านเกณฑ์)
* ง. $T_{max\_delay} = 1.250\text{ ns}$, $T_{bus\_skew} = 1.000\text{ ns}$, Skew จริง $= 1.200\text{ ns}$ (ไม่ผ่านเกณฑ์!)

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: คำนวณหาค่า $T_{max\_delay}$:**
สัญญาณนาฬิกาทั้งสองตัวมีคาบเวลา:
* $T_{period\_src} = \frac{1}{250\text{ MHz}} = 4.000\text{ ns}$
* $T_{period\_dst} = \frac{1}{400\text{ MHz}} = 2.500\text{ ns}$
คาบเวลาที่เร็วกว่าคือ $\min(4.000, 2.500) = 2.500\text{ ns}$
ดังนั้น:
$$T_{max\_delay} = 2.500\text{ ns}$$

**ขั้นตอนที่ 2: คำนวณหาค่า $T_{bus\_skew}$:**
ตามข้อกำหนด กำหนดให้ใช้ $40\%$ ของคาบเวลาฝั่งรับ ($T_{period\_dst} = 2.500\text{ ns}$):
$$T_{bus\_skew} = 0.40 \times 2.500\text{ ns} = 1.000\text{ ns}$$

**ขั้นตอนที่ 3: ตรวจสอบผลการเดินสายจริง:**
* บิตที่เร็วที่สุด: $T_{min} = 0.650\text{ ns}$
* บิตที่ช้าที่สุด: $T_{max} = 1.850\text{ ns}$
ค่า Bus Skew จริงที่เกิดขึ้น:
$$\Delta T_{skew\_actual} = T_{max} - T_{min} = 1.850\text{ ns} - 0.650\text{ ns} = 1.200\text{ ns}$$
เปรียบเทียบกับงบประมาณ:
$$\Delta T_{skew\_actual} (1.200\text{ ns}) > T_{bus\_skew} (1.000\text{ ns})$$
เกิด **Bus Skew Violation!** บัสเส้นนี้ไม่ผ่านเกณฑ์ความปลอดภัย และมีความเสี่ยงที่จะทำให้ Gray Code ถอดรหัสผิดพลาดในบางไซเคิล!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** ค่า $2.500\text{ ns}$, $1.000\text{ ns}$, Skew จริง $1.200\text{ ns}$ และสรุปว่าไม่ผ่านเกณฑ์ได้อย่างถูกต้องแม่นยำ
* **ข้อ ข. ไม่ถูกต้อง:** นำคาบเวลาฝั่งส่ง ($4.0\text{ ns}$) มาคิด ซึ่งหละหลวมเกินไป
* **ข้อ ค. ไม่ถูกต้อง:** คำนวณ Skew Budget เป็น $50\%$ แทนที่จะเป็น $40\%$
* **ข้อ ง. ไม่ถูกต้อง:** ค่า Max Delay ต่ำเกินจริงไปครึ่งหนึ่ง

**คำตอบที่ถูกต้อง:** **ข้อ ก.**

### ข้อที่ 2: การแก้ปัญหาข้อขัดแย้งของลำดับศักดิ์ข้อยกเว้นไทม์มิ่ง (SDC Exception Priority Conflict)

#### โจทย์คำถาม:
ในไฟล์คอนสเตรนต์ XDC ของระบบประมวลผล มีการประกาศคำสั่ง 3 บรรทัดตามลำดับดังต่อไปนี้:

```tcl
# บรรทัดที่ 1:
set_multicycle_path 3 -setup -from [get_cells u_core/src_reg] -to [get_cells u_core/dst_reg]
# บรรทัดที่ 2:
set_max_delay 4.500 -from [get_cells u_core/src_reg] -to [get_cells u_core/dst_reg]
# บรรทัดที่ 3:
set_false_path -from [get_cells u_core/src_reg] -to [get_cells u_core/dst_reg]
```

กำหนดให้คาบเวลาของสัญญาณนาฬิกาคือ $T_{period} = 2.000\text{ ns}$  
จงวิเคราะห์ว่า เมื่อเครื่องมือ STA ประมวลผลคำสั่งทั้ง 3 บรรทัดนี้เสร็จสิ้น:
1. คำสั่งในบรรทัดใดจะมีผลบังคับใช้จริงบนเส้นทางระหว่าง `src_reg` และ `dst_reg`?
2. เครื่องมือ STA จะมีพฤติกรรมการรายงานไทม์มิ่งบนเส้นทางนี้อย่างไร?

* ก. บรรทัดที่ 2 (`set_max_delay 4.500`) จะชนะ เพราะเป็นคำสั่งที่ระบุค่าเวลาตายตัวที่แม่นยำที่สุด เครื่องมือจะตรวจเช็คว่า Data Path $\le 4.5\text{ ns}$
* ข. บรรทัดที่ 1 (`set_multicycle_path 3`) จะชนะ เพราะถูกประกาศเป็นบรรทัดแรกตามลำดับการอ่านไฟล์ เครื่องมือจะตรวจ Setup ที่ $6.0\text{ ns}$
* ค. บรรทัดที่ 3 (`set_false_path`) จะชนะอย่างเด็ดขาด เนื่องจาก `set_false_path` มีลำดับศักดิ์สูงสุดในมาตรฐาน SDC เหนือกว่าทั้ง Max Delay และ Multicycle โดยเครื่องมือจะตัดเส้นทางนี้ออกจากการวิเคราะห์อย่างสมบูรณ์ และไม่มีการรายงาน Slack ใดๆ
* ง. คำสั่งทั้ง 3 บรรทัดจะทำงานร่วมกัน โดยเครื่องมือจะเลือกค่า Slack ที่แย่ที่สุดมารายงาน

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: วิเคราะห์ลำดับศักดิ์ของ Timing Exceptions ในมาตรฐาน SDC:**
ตามข้อกำหนด IEEE 1481 / SDC Standard:
$$\text{Priority:} \quad \text{set\_false\_path} > \text{set\_clock\_groups} > \text{set\_max\_delay / set\_min\_delay} > \text{set\_multicycle\_path}$$

1. **`set_multicycle_path` (บรรทัดที่ 1):** มีลำดับศักดิ์ต่ำสุดในกลุ่มข้อยกเว้น
2. **`set_max_delay` (บรรทัดที่ 2):** มีลำดับศักดิ์สูงกว่า Multicycle ดังนั้นจะทำการ Override ทับคำสั่งบรรทัดที่ 1 ทันที
3. **`set_false_path` (บรรทัดที่ 3):** มีลำดับศักดิ์ **สูงสุดเด็ดขาด (Highest Precedence)** เหนือกว่าคำสั่งทุกประเภท!

**ขั้นตอนที่ 2: สรุปผลลัพธ์บนกราฟ STA:**
เมื่อ `set_false_path` ถูกประกาศบนเส้นทางเดียวกัน มันจะทำการ **ทับและยกเลิกผล (Override & Invalidate)** ของทั้ง `set_multicycle_path` และ `set_max_delay` โดยสิ้นเชิง!  
เส้นทางนี้จะถูกลบออกจาก Timing Graph และเครื่องมือ STA จะไม่ทำการตรวจสอบ ไม่รายงานค่า Slack และไม่แสดงเส้นทางนี้ใน Timing Report เลย

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ไม่ถูกต้อง:** Max Delay แพ้ False Path
* **ข้อ ข. ไม่ถูกต้อง:** SDC ไม่ได้ใช้ลำดับบรรทัดก่อนหน้า แต่ใช้ลำดับศักดิ์ของประเภทคำสั่ง
* **ข้อ ค. ถูกต้องสมบูรณ์แบบ:** อธิบายกฎลำดับศักดิ์ของ `set_false_path` ได้อย่างถูกต้องแม่นยำ $100\%$
* **ข้อ ง. ไม่ถูกต้อง:** คำสั่งข้อยกเว้นไม่ได้ทำงานร่วมกัน แต่หักล้างกันตามลำดับชั้น

**คำตอบที่ถูกต้อง:** **ข้อ ค.**

### ข้อที่ 3: การวิเคราะห์และจำแนกความเสี่ยงจากรายงาน Vivado CDC Audit Report

#### โจทย์คำถาม:
ในการรันคำสั่ง `report_cdc -details` บนวงจรประมวลผลภาพเรดาร์ความเร็วสูง เครื่องมือสร้างรายงานสรุปดังต่อไปนี้:

| Path ID | Source Clock | Destination Clock | Crossing Type | CDC Structure Detected | Status |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **Path 1** | `clk_100` | `clk_300` | Single-bit | 2-FF Synchronizer with `ASYNC_REG = TRUE` | **Safe** |
| **Path 2** | `clk_156` | `clk_250` | Multi-bit (8-bit) | Gray Coded Counter + 2-FF Sync + `set_bus_skew` | **Safe** |
| **Path 3** | `clk_100` | `clk_400` | Multi-bit (16-bit) | No Synchronizer (Combinational logic directly connects) | **Unsafe** |
| **Path 4** | `clk_200` | `clk_200_shifted` | Single-bit | Same PLL output with fixed 90° phase shift | **User Ignored** |

จงพิจารณาว่า ข้อใดคือ **ข้อสรุปและการกระทำที่ถูกต้องทางวิศวกรรมมากที่สุด**:
* ก. วงจรพร้อมสำหรับการ Sign-Off เนื่องจาก Path 1 และ Path 2 มีสถานะเป็น Safe แล้ว ส่วน Path 3 สามารถใส่ `set_false_path` เพื่อทำให้กลายเป็น Safe ได้
* ข. วงจร **ไม่สามารถ Sign-Off ได้เด็ดขาด** เนื่องจาก **Path 3 มีสถานะ Unsafe** ซึ่งเป็นบัสข้อมูล 16 บิตที่ไม่มีวงจรซิงโครไนซ์ จะต้องถูกแก้ไขใน RTL โดยการแทรก Asynchronous FIFO หรือ Handshake Circuit ก่อน จึงจะอนุมัติแบบได้
* ค. Path 4 มีความเสี่ยงสูงสุด เพราะมีสถานะ User Ignored
* ง. ทั้ง Path 1, 2, 3, และ 4 ต้องเปลี่ยนไปใช้ 3-FF Synchronizer ทั้งหมด

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: วิเคราะห์ Path 1 และ Path 2:**
* Path 1: สัญญาณ 1 บิตผ่าน 2-FF Synchronizer พร้อมแอตทริบิวต์ `ASYNC_REG` ถูกต้องตามมาตรฐาน ปลอดภัย (Safe)
* Path 2: บัสหลายบิตใช้ Gray Code พร้อม 2-FF Sync และมีคอนสเตรนต์ `set_bus_skew` คุม ถูกต้องตามมาตรฐาน ปลอดภัย (Safe)

**ขั้นตอนที่ 2: วิเคราะห์ Path 3 (หายนะทางวิศวกรรม):**
* รายงานระบุชัดเจน: **Multi-bit (16-bit) ไม่มีวงจรซิงโครไนซ์เลย (No Synchronizer)** และมีสถานะเป็น **Unsafe**
* การต่อบัส 16 บิตข้ามจาก 100MHz ไป 400MHz ตรงๆ โดยไม่มีวงจร CDC จะทำให้เกิดความล้มเหลวของข้อมูล ($100\%$ Corrupted Data) บนบอร์ดจริงอย่างแน่นอน!
* **ห้ามใส่ `set_false_path` เด็ดขาด!** เพราะการใส่ False Path ไม่ได้แก้ฮาร์ดแวร์ แต่เป็นการ "ปิดตาตัวเอง" วิศวกรต้องแก้ RTL โดยใส่วงจร Asynchronous FIFO หรือ Handshake Controller เท่านั้น!

**ขั้นตอนที่ 3: วิเคราะห์ Path 4:**
* เป็นคล็อกที่สร้างจาก PLL เดียวกันและมีเฟสคงที่ ($90^\circ$) เป็นวงจรซิงโครนัสที่มีความสัมพันธ์แน่นอน การตั้ง User Ignored หรือวิเคราะห์แบบ Phase Shift ปกติเป็นเรื่องที่ยอมรับได้

ดังนั้น ข้อสรุปที่ถูกต้องคือ **ระบบไม่สามารถผ่านการตรวจแบบได้จนกว่า Path 3 จะได้รับการแก้ไขใน RTL**!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ไม่ถูกต้อง:** แนะนำให้ใส่ False Path แก้บั๊ก ซึ่งเป็นวิธีที่ผิดกฎหมายวิศวกรรมอย่างร้ายแรง
* **ข้อ ข. ถูกต้องสมบูรณ์แบบ:** ชี้ชัดถึงความเสี่ยงของ Path 3 และแนวทางแก้ไขใน RTL อย่างถูกต้องตามมาตรฐาน
* **ข้อ ค. ไม่ถูกต้อง:** Path 4 มีความเสี่ยงต่ำกว่า Path 3 มาก
* **ข้อ ง. ไม่ถูกต้อง:** ไม่จำเป็นต้องแก้ทุก Path

**คำตอบที่ถูกต้อง:** **ข้อ ข.**
