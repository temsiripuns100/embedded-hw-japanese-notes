## 1. ทฤษฎีวิศวกรรมเชิงลึก (高度なエンジニアリング理論)

### 1.1 สถาปัตยกรรมข้อยกเว้นไทม์มิ่ง (Timing Exception Architecture in SDC/XDC)
ตามค่าเริ่มต้นพื้นฐาน เครื่องมือ Static Timing Analysis (STA) ในซอฟต์แวร์สังเคราะห์วงจร (Vivado, Quartus, PrimeTime) จะตั้งสมมติฐานว่า:  
*"ทุกๆ เส้นทางข้อมูลเชื่อมต่อระหว่างสองฟลิปฟล็อป จะต้องส่งผ่านข้อมูลสำเร็จภายใน **1 รอบสัญญาณนาฬิกา (Single-Cycle Assumption)**"*

ทว่าในสถาปัตยกรรมฮาร์ดแวร์จริง มีเส้นทางจำนวนมากที่ไม่จำเป็น หรือเป็นไปไม่ได้ในทางกายภาพที่จะทำงานแบบ 1 ไซเคิล หากวิศวกรไม่ประกาศ **ข้อยกเว้นไทม์มิ่ง (Timing Exceptions)** วงจรจะถูกบีบคั้น (Over-constrained) จนซอฟต์แวร์ Place & Route พยายามดิ้นรนแก้ไทม์มิ่งอย่างไร้ประโยชน์ ทำให้สูญเสียทรัพยากร พลังงาน และอาจทำให้ Timing ปิดไม่ลง

```
                โครงสร้างลำดับชั้นของ TIMING EXCEPTIONS ใน SDC/XDC
                
   [ ลำดับความสำคัญสูงสุด (Highest Precedence) ]
   1. set_false_path           : ปิดการวิเคราะห์ไทม์มิ่งบนเส้นทางนี้ 100% (ลบออกจากกราฟ STA)
   2. set_clock_groups         : ตัดขาดความสัมพันธ์ระหว่างกลุ่มสัญญาณนาฬิกา
   3. set_max_delay / min_delay: กำหนดกรอบเวลาตายตัวโดยไม่สนคาบเวลาของ Clock
   4. set_multicycle_path      : ผ่อนปรนรอบเวลาออกไปเป็น N ไซเคิล
   [ ลำดับความสำคัญต่ำสุด (Lowest Precedence) ]
```

### 1.2 กายวิภาคของ False Paths (`set_false_path`) และกับดักมรณะ (The Lethal Trap)

คำสั่ง `set_false_path` ใช้เพื่อสั่งให้เครื่องมือ STA ตัดเส้นทางที่ระบุออกจากกระบวนการวิเคราะห์โดยสิ้นเชิง โดยเครื่องมือจะไม่รายงาน Setup หรือ Hold Slack บนเส้นทางนี้อีกต่อไป

```
                   กรณีที่อนุญาตให้ใช้ FALSE PATH ได้อย่างถูกต้อง
                   
   [ 1. วงจรลอจิกที่ไม่สามารถเกิดขึ้นได้พร้อมกัน (Mutually Exclusive Logic) ]
   FSM State 0 (TX Mode)  ──► [ MUX Sel = 0 ] ──► Data Path 1
   FSM State 1 (RX Mode)  ──► [ MUX Sel = 1 ] ──► Data Path 2
   ===> ไม่สามารถส่งข้อมูลข้ามโหมดพร้อมกันได้ในทางฟังก์ชัน
   
   [ 2. รีจิสเตอร์กำหนดค่าคงที่ (Quasi-Static Configuration Registers) ]
   CPU SPI/I2C Config Bus ──► [ Config Reg (Gain, Threshold) ] ──► DSP Core Pipeline
   ===> รีจิสเตอร์นี้ถูกเขียนเพียงครั้งเดียวตอนเปิดเครื่อง (Boot Time)
        และอยู่นิ่งสนิทตลอดการทำงาน (Static) ไม่เคยสลับสถานะในขณะประมวลผล!
```

> [!CRITICAL]
> **กับดักมรณะของการใช้ `set_false_path` (The Fatal Masking Trap):**  
> วิศวกรจำนวนมากนำ `set_false_path` ไปใส่ครอบเส้นทางที่ข้ามโดเมนสัญญาณนาฬิกา (Clock Domain Crossing - CDC) เพียงเพราะรำคาญรายงาน Timing Violation!  
> **นี่คือการกระทำที่อันตรายที่สุดในชีวิตการออกแบบดิจิทัล!**  
> การใส่ False Path บนบัสข้อมูล CDC จะทำให้ Place & Route ปล่อยปละละเลยความล่าช้าในการเดินสาย (Routing Delay) ทำให้สายไฟแต่ละบิตในบัสเดียวกันมีความยาวต่างกันมหาศาล (Bus Skew แตกกระจาย) ก่อให้เกิดข้อมูลเน่าเสีย (Data Corruption) บนบอร์ดจริงอย่างถาวร!

### 1.3 ทฤษฎี Multicycle Paths (`set_multicycle_path`) และกฎเหล็กของสวิตช์ `-hold`

เมื่อเส้นทางข้อมูลเชื่อมต่อระหว่างรีจิสเตอร์ต้นทางและปลายทางถูกควบคุมด้วยสัญญาณ **Clock Enable (CE)** ที่เปิดให้ข้อมูลไหลผ่านเพียง 1 ครั้งในทุกๆ $N$ รอบสัญญาณนาฬิกา (เช่น คำนวณเสร็จทุกๆ 4 ไซเคิล):

```
                   ไดอะแกรมเวลาของ MULTICYCLE PATH (N = 4 ไซเคิล)
                   
   CLK      : ──/‾‾\__/‾‾\__/‾‾\__/‾‾\__/‾‾\__/‾‾\__/‾‾\__/‾‾\__
                |     |     |     |     |
   Edge Num :   0     1     2     3     4
                ▲                       ▲
              Launch                  Capture
               Edge                    Edge
   CE Pulse : ──/‾‾‾‾‾\_______________________/‾‾‾‾‾\___________ (แอกทีฟทุก 4 ไซเคิล)
   Data     : ──<     VALID STABLE DATA       >─────────────────
                |<------ 4 Clock Periods ------>|
```

#### หายนะของพฤติกรรมดีฟอลต์ (The Default Multi-Cycle Trap):
เมื่อวิศวกรใส่คำสั่งเพียงบรรทัดเดียว:
`set_multicycle_path 4 -setup -from [get_cells FF1] -to [get_cells FF2]`

เครื่องมือ STA จะปรับเปลี่ยนการตรวจสอบดังนี้:
1. **Setup Check:** เลื่อนขอบ Capture Edge จาก Edge 1 ไปเป็น **Edge 4** (ถูกต้องตามความต้องการ)
2. **Hold Check (กับดักมรณะ!):** ตามทฤษฎี STA ขอบ Hold Check จะต้องอยู่ก่อนหน้าขอบ Setup Check 1 ไซเคิลเสมอ  
   ดังนั้น เครื่องมือจะเลื่อน Hold Check จาก Edge 0 ไปเป็น **Edge 3 (Edge 4 - 1)!**

```
                   หายนะของ DEFAULT HOLD CHECK AT EDGE 3
                   
   Edge:        0              1              2              3              4
   Launch Edge: ▲
   Setup Check:                                                             ▲ (Edge 4)
   Default Hold:                                             ▲ (Edge 3!)
   ===> ความหมายในทางฟิสิกส์: ข้อมูลที่ส่งจาก Edge 0 จะต้องเดินทาง "ช้ากว่า Edge 3"!
        เครื่องมือคิดว่า Data Path Delay ต้องมากกว่า 3 คาบเวลา (3 x Tperiod)!
        Router จึงตกใจและแทรก LUT Delay Buffers ขนาดยักษ์หน่วงเวลาถึง 3 ไซเคิล!
```

#### กฎบัตรภาคบังคับ: การใช้สวิตช์ `-hold` ดึงขอบกลับมาที่เดิม
เพื่อบอกเครื่องมือว่า *"ข้อมูลถูกปล่อยจาก Edge 0 และต้องคงสภาพเทียบกับ Edge 0 เดียวกัน"* วิศวกร **ต้องประกาศคำสั่งคู่กันเสมอ**:

```tcl
# ==============================================================================
# GOLDEN MULTICYCLE CONSTRAINTS: กฎเหล็ก 2 บรรทัดคู่กันเสมอ
# ==============================================================================
# บรรทัดที่ 1: เลื่อน Setup Edge ไปที่ไซเคิลที่ 4
set_multicycle_path 4 -setup -from [get_cells FF1] -to [get_cells FF2]

# บรรทัดที่ 2: ดึง Hold Edge ถอยหลังกลับมา 3 ไซเคิล (N-1) เพื่อให้ตรวจเทียบกับ Edge 0!
set_multicycle_path 3 -hold  -from [get_cells FF1] -to [get_cells FF2]
```

เมื่อใส่คำสั่ง `-hold (N-1)` ขอบ Hold Check จะถูกดึงถอยหลังจาก Edge 3 กลับมาอยู่ที่ **Edge 0** ทำให้ข้อกำหนด Hold Time กลายเป็นปกติ ($T_{hold} \ge 0$) และป้องกันไม่ให้ Router แทรก Delay Buffer แปลกปลอมแม้แต่ตัวเดียว!

### 1.4 การวิเคราะห์แบบเลือกเงื่อนไข (Case Analysis: `set_case_analysis`)

ในชิปที่รองรับหลายโหมดการทำงาน เช่น โหมดทำงานปกติ (Mission Mode) และโหมดทดสอบในโรงงาน (Manufacturing Test / Scan Mode) ซึ่งถูกควบคุมด้วยพินสวิตช์มัลติเพล็กเซอร์:

```tcl
# ล็อกขาควบคุม TEST_MODE ให้เป็นลอจิก 0 ตลอดการวิเคราะห์ STA ทั่วไป
set_case_analysis 0 [get_pins u_top/u_ctrl/test_mode_reg/Q]
```

คำสั่งนี้จะสั่งให้ STA Engine ทำการปิดกั้น (Disable) เส้นทางและเกตทั้งหมดที่เชื่อมโยงกับโหมดทดสอบ ทำให้ไม่นำเส้นทางที่ไม่มีวันเกิดขึ้นในสภาวะการทำงานจริงมารวมในรายงาน Timing ช่วยลดขนาดของ Timing Graph และเพิ่มความแม่นยำในการ Sign-Off

## 2. ทริคหน้างาน OJT แบบ Step-by-Step (現場の実践テクニック)

### 2.1 กรณีศึกษาความล้มเหลวหน้างาน: แขนกลหุ่นยนต์อุตสาหกรรมสั่นกระตุกรุนแรงจากบั๊ก Multicycle ลืม `-hold` (Industrial Robot Arm Jitter & Delay Buffer Hazard)

```
+----------------------------------------------------------------------------------------------------+
| กรณีศึกษาความล้มเหลวหน้างาน (現場の失敗事例)                                                                 |
| เหตุการณ์: ชุดควบคุมแขนกลอุตสาหกรรม 6 แกน (6-Axis Robotic Servo Controller) ความแม่นยำระดับไมครอน         |
| อาการ: บอร์ดควบคุมเวอร์ชันใหม่ที่อัปเกรดความถี่จาก 100MHz เป็น 200MHz ทำให้ข้อต่อแขนกลเกิดการสั่นกระตุกรุนแรง |
|        (Violent Mechanical Vibration) มอเตอร์ส่งเสียงครางและพลาดตำแหน่งพิกัดเป้าหมายจนชนเข้ากับแท่นประกอบ   |
|        การวัดสัญญาณในแล็บพบว่า ค่าพิกัดมุมจาก Optical Encoder ขาดหายไปบางจังหวะและดีเลย์ไปกว่า 15ns!           |
+----------------------------------------------------------------------------------------------------+
```

#### การวิเคราะห์หาสาเหตุรากเหง้าด้วยหลักการ 5 Whys (5 Whys Root Cause Analysis):

1. **ทำไมแขนกลจึงเกิดการสั่นกระตุกและชนแท่นประกอบ?**  
   *คำตอบ:* สัญญาณค่าพิกัดมุมของข้อต่อที่ผ่านวงจรตัวกรองดิจิทัล (Digital Position Filter) มีความล่าช้าสะสมและส่งข้อมูลผิดพลาด ทำให้ลูปควบคุม PID สั่งเร่งมอเตอร์ชดเชยเกินขอบเขต (Over-compensation)

2. **ทำไมวงจร Digital Filter จึงมีความล่าช้าทางเวลาสูงถึง 15ns?**  
   *คำตอบ:* บนเส้นทางคำนวณของฟิลเตอร์ มีการแทรกก้อนลอจิกหน่วงเวลา (LUT Delay Buffers) ซ้อนกันถึง 18 ตัวโดยที่เราเตอร์เป็นผู้สร้างขึ้นมาเอง

3. **ทำไมเราเตอร์จึงแทรก LUT Delay Buffers จำนวนมากบนเส้นทางของฟิลเตอร์?**  
   *คำตอบ:* เครื่องมือพบสภาวะ Hold Violation รุนแรงบนเส้นทางข้อมูล โดยรายงานระบุว่า Data Path ต้องการเวลาหน่วงอย่างน้อย $14.5\text{ ns}$ เพื่อให้ผ่าน Hold Check!

4. **ทำไม Hold Check จึงต้องการเวลาหน่วงสูงถึง $14.5\text{ ns}$ ทั้งที่คาบเวลา Clock คือ $5.0\text{ ns}$?**  
   *คำตอบ:* วิศวกรกำหนดคอนสเตรนต์ Multicycle บนวงจรคำนวณที่รันทุกๆ 4 ไซเคิลว่า:  
   `set_multicycle_path 4 -setup -to [get_cells *filter_acc_reg*]`  
   แต่ **ลืมใส่คำสั่ง `-hold 3` คู่กัน!** ทำให้ Vivado ย้ายขอบ Hold Check จากไซเคิล 0 ไปตรวจที่ **ไซเคิลที่ 3 ($3 \times 5.0\text{ ns} = 15.0\text{ ns}$)**!

5. **ทำไมวิศวกรจึงลืมใส่สวิตช์ `-hold 3`?**  
   *คำตอบ:* วิศวกรเข้าใจผิดคิดว่าคำสั่ง `set_multicycle_path 4 -setup` มีผลเฉพาะกับ Setup Time และเครื่องมือจะคง Hold Time ไว้ที่เดิมโดยอัตโนมัติ โดยไม่ทราบกลไกพื้นฐานของ STA ว่าการไม่ระบุ `-hold` จะทำให้เครื่องมือสร้างข้อกำหนด Hold ปลอมขึ้นมาบีบตัวเอง!

### 2.3 คู่มือปฏิบัติงาน SOP: การประกาศและตรวจสอบ Timing Exceptions อย่างรัดกุม (Timing Exceptions SOP)

#### สเต็ปที่ 1: กฎเหล็กการเขียน Multicycle Path (The Inseparable Pair Rule)
* ทุกครั้งที่มีการใช้คำสั่ง `set_multicycle_path N -setup` **ต้องเขียนคำสั่ง `set_multicycle_path (N-1) -hold` ควบคู่กันเสมอในบรรทัดถัดไป**:

```tcl
# แม่แบบมาตรฐานสำหรับ Clock Enable Path (N ไซเคิล)
set_multicycle_path $N     -setup -from [get_cells src_reg*] -to [get_cells dst_reg*]
set_multicycle_path [expr $N - 1] -hold  -from [get_cells src_reg*] -to [get_cells dst_reg*]
```

#### สเต็ปที่ 2: การตรวจสอบพฤติกรรมขอบสัญญาณด้วยรายงาน Timing Report
* รันคำสั่งตรวจสอบเส้นทางที่ประกาศ Multicycle เพื่อดูตำแหน่ง Edge:
  `report_timing -from [get_cells src_reg*] -to [get_cells dst_reg*] -delay_type min_max`
* ตรวจสอบในตารางรายงาน:
  * ในส่วน **Setup Path:** บรรทัด `Clock Requirement` ต้องเท่ากับ $N \times T_{period}$
  * ในส่วน **Hold Path:** บรรทัด `Clock Requirement` ต้องเท่ากับ **$0.000\text{ ns}$** (หรือเทียบเท่า Edge 0)

#### สเต็ปที่ 3: การรันการตรวจสอบ Timing Exceptions Audit
* รันคำสั่งตรวจสอบความสมเหตุสมผลของข้อยกเว้นทั้งหมดใน Vivado:
  `report_exceptions -coverage -file timing_exceptions.rpt`
* ตรวจสอบว่าไม่มีเส้นทางใดถูกจัดอยู่ในกลุ่ม **"Invalid Exceptions"** หรือ **"Partially Overridden Exceptions"**

#### สเต็ปที่ 4: การตรวจสอบข้อห้ามการใช้ False Path บนบัส CDC
* ห้ามใช้ `set_false_path` กับบัสข้อมูลที่ข้ามโดเมนนาฬิกาเด็ดขาด
* สำหรับเส้นทางข้ามโดเมนที่ผ่านวงจร Synchronizer ให้ใช้:
  `set_max_delay -datapath_only` ควบคู่กับ `set_bus_skew` เท่านั้น!

## 3. คำศัพท์และประโยคภาษาญี่ปุ่นสำหรับตรวจแบบ (検図 - Kenzu)

### 3.1 ตารางคำศัพท์เทคนิคเฉพาะทาง

ผมเลยเขียนเพื่อผ่อนปรนข้อกำหนด Setup Time ออกไปเป็น 4 ไซเคิล (20ns)

เมื่อมีความล่าช้าแปลกปลอมถึง 15ns ฝังอยู่ในลูปควบคุม ค่า Phase Margin ของเซอร์โวจะถูกทำลาย
และทำให้หุ่นยนต์สั่นกระตุกอย่างรุนแรงจนคุมไม่อยู่ครับ!
รีบใส่ '-hold 3' เข้าไปเพื่อดึงขอบตรวจ Hold กลับมาที่ไซเคิล 0 เดี๋ยวนี้เลยครับ!)

## 4. ควิซวิเคราะห์ปัญหาระดับวิศวกรอาวุโส (上級技術クイズ)

### ข้อที่ 1: การวิเคราะห์ตำแหน่งขอบ Setup และ Hold Check ใน Multicycle Path

#### โจทย์คำถาม:
ในวงจรประมวลผลสัญญาณกรองความถี่ FIR Filter สัญญาณนาฬิกาของระบบมีความถี่ $f_{clk} = 250\text{ MHz}$ ($T_{period} = 4.000\text{ ns}$)

วิศวกรออกแบบเส้นทางคำนวณคูณสะสม (MAC) ให้รับข้อมูลใหม่ทุกๆ **$N = 3\text{ รอบสัญญาณนาฬิกา}$** ผ่านการควบคุมของสัญญาณ Clock Enable

หากวิศวกรทดลองใส่คอนสเตรนต์ 2 รูปแบบในไฟล์ XDC:
* **รูปแบบ A:**  
  `set_multicycle_path 3 -setup -from [get_cells R1] -to [get_cells R2]`  
  *(ไม่มีการใส่คำสั่ง `-hold`)*
* **รูปแบบ B:**  
  `set_multicycle_path 3 -setup -from [get_cells R1] -to [get_cells R2]`  
  `set_multicycle_path 2 -hold  -from [get_cells R1] -to [get_cells R2]`

กำหนดให้ Launch Edge เกิดขึ้นที่เวลา $t = 0.000\text{ ns}$ (Edge 0)  
จงหาว่า:
1. ในรูปแบบ A: ขอบเวลาสำหรับตรวจสอบ Setup Check ($t_{setup\_A}$) และ Hold Check ($t_{hold\_A}$) อยู่ที่เวลาใด?
2. ในรูปแบบ B: ขอบเวลาสำหรับตรวจสอบ Setup Check ($t_{setup\_B}$) และ Hold Check ($t_{hold\_B}$) อยู่ที่เวลาใด?
3. รูปแบบใดที่จะส่งผลให้เครื่องมือ Place & Route เกิดการแทรก Delay Buffer ขนาดใหญ่โดยไม่จำเป็น?

* ก.
  * รูปแบบ A: $t_{setup\_A} = 12.0\text{ ns}$ (Edge 3), $t_{hold\_A} = 8.0\text{ ns}$ (Edge 2)
  * รูปแบบ B: $t_{setup\_B} = 12.0\text{ ns}$ (Edge 3), $t_{hold\_B} = 0.0\text{ ns}$ (Edge 0)
  * รูปแบบ A ทำให้เกิดการแทรก Delay Buffer ไม่จำเป็น
* ข.
  * รูปแบบ A: $t_{setup\_A} = 12.0\text{ ns}$ (Edge 3), $t_{hold\_A} = 0.0\text{ ns}$ (Edge 0)
  * รูปแบบ B: $t_{setup\_B} = 12.0\text{ ns}$ (Edge 3), $t_{hold\_B} = 4.0\text{ ns}$ (Edge 1)
  * รูปแบบ B ทำให้เกิดการแทรก Delay Buffer ไม่จำเป็น
* ค.
  * รูปแบบ A: $t_{setup\_A} = 8.0\text{ ns}$ (Edge 2), $t_{hold\_A} = 4.0\text{ ns}$ (Edge 1)
  * รูปแบบ B: $t_{setup\_B} = 8.0\text{ ns}$ (Edge 2), $t_{hold\_B} = 0.0\text{ ns}$ (Edge 0)
  * รูปแบบ A ทำให้เกิดการแทรก Delay Buffer ไม่จำเป็น
* ง.
  * รูปแบบ A: $t_{setup\_A} = 12.0\text{ ns}$ (Edge 3), $t_{hold\_A} = 12.0\text{ ns}$ (Edge 3)
  * รูปแบบ B: $t_{setup\_B} = 12.0\text{ ns}$ (Edge 3), $t_{hold\_B} = 0.0\text{ ns}$ (Edge 0)
  * รูปแบบ A ทำให้เกิดการแทรก Delay Buffer ไม่จำเป็น

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: วิเคราะห์รูปแบบ A (มีเฉพาะ `-setup 3`):**
* สำหรับ Setup Check:
  ขอบ Capture Edge ถูกเลื่อนออกไป $N = 3$ ไซเคิลจาก Launch Edge:
  $$t_{setup\_A} = 3 \times T_{period} = 3 \times 4.000\text{ ns} = 12.000\text{ ns} \quad (\text{Edge 3})$$
* สำหรับ Hold Check (พฤติกรรมดีฟอลต์ของ SDC/XDC):
  ขอบ Hold Check จะถูกวางไว้ก่อนหน้า Setup Edge 1 คาบเวลาเสมอ ($N - 1 = 3 - 1 = 2$):
  $$t_{hold\_A} = (3 - 1) \times T_{period} = 2 \times 4.000\text{ ns} = 8.000\text{ ns} \quad (\text{Edge 2})$$
* ผลลัพธ์ทางกายภาพ: เครื่องมือจะบังคับว่า ข้อมูลที่ออกจาก Edge 0 จะต้องมาถึง **หลังเวลา $8.000\text{ ns}$** ซึ่งบีบให้ Router ต้องยัดเยียด Delay Buffer หน่วงเวลาไม่น้อยกว่า $8\text{ ns}$!

**ขั้นตอนที่ 2: วิเคราะห์รูปแบบ B (มีทั้ง `-setup 3` และ `-hold 2`):**
* สำหรับ Setup Check:
  $$t_{setup\_B} = 3 \times T_{period} = 12.000\text{ ns} \quad (\text{Edge 3})$$
* สำหรับ Hold Check:
  คำสั่ง `-hold 2` จะดึงขอบ Hold ถอยหลังกลับมา $2$ คาบเวลาจากตำแหน่งดีฟอลต์ (จาก Edge 2 ถอยมา 2 ไซเคิล):
  $$t_{hold\_B} = 8.000\text{ ns} - (2 \times 4.000\text{ ns}) = 0.000\text{ ns} \quad (\text{Edge 0})$$
* ผลลัพธ์ทางกายภาพ: ขอบ Hold กลับมาอยู่ที่ Edge 0 ซึ่งเป็นจุดเวลาเดียวกันกับ Launch Edge พอดี ทำให้ข้อกำหนดกลายเป็นค่าปกติ ($T_{hold\_slack} \ge 0$) และไม่เกิดการแทรก Delay Buffer เลย!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** $t_{setup\_A} = 12.0\text{ ns}$, $t_{hold\_A} = 8.0\text{ ns}$, $t_{setup\_B} = 12.0\text{ ns}$, $t_{hold\_B} = 0.0\text{ ns}$ และระบุว่ารูปแบบ A ก่อให้เกิด Delay Buffer ชัดเจน
* **ข้อ ข. ไม่ถูกต้อง:** สลับพฤติกรรมระหว่างรูปแบบ A และ B
* **ข้อ ค. ไม่ถูกต้อง:** คำนวณคาบเวลา Setup ผิดเป็น 2 ไซเคิล
* **ข้อ ง. ไม่ถูกต้อง:** Hold Check ในรูปแบบ A ไม่ได้อยู่ที่ Edge 3 (อยู่ที่ Edge 2)

**คำตอบที่ถูกต้อง:** **ข้อ ก.**

### ข้อที่ 2: การคำนวณ Data Path Delay Margin ภายใต้ Multicycle Constraint

#### โจทย์คำถาม:
ในวงจรลอจิกถอดรหัสรหัสลับ (Cryptography Decryption Core) เส้นทาง Combinational Logic ประกอบด้วยตาราง S-Box ซ้อนกัน 4 ชั้น มีความล่าช้าของเกตรวมสายส่ง $T_{data\_path} = 7.850\text{ ns}$  
ระบบทำงานที่สัญญาณนาฬิกา $f_{clk} = 200\text{ MHz}$ ($T_{period} = 5.000\text{ ns}$)

พารามิเตอร์ของเซลล์ฟลิปฟล็อป:
* $T_{cko} = 0.350\text{ ns}$
* $T_{setup} = 0.150\text{ ns}$
* $T_{uncertainty} = 0.100\text{ ns}$
* สมมติว่า Clock Skew เป็นศูนย์ ($\Delta T_{skew} = 0$)

หากวิศวกรกำหนดให้เส้นทางนี้เป็น Multicycle Path ขนาด **$N = 2\text{ ไซเคิล}$** (พร้อมคำสั่ง `-hold 1` ที่ถูกต้อง):

จงคำนวณหา:
1. ค่า Setup Slack ($\text{Slack}_{setup}$) ของเส้นทางนี้
2. หากไม่กำหนดเป็น Multicycle Path (ใช้ Default 1-Cycle) เส้นทางนี้จะติดลบค่า Setup Slack เท่าใด?
3. สรุปว่าการกำหนด Multicycle ช่วยให้ระบบผ่าน Timing หรือไม่?

* ก. $\text{Slack}_{setup} = +1.550\text{ ns}$, ถ้าเป็น 1-Cycle จะติดลบ $-3.450\text{ ns}$, ผ่าน Timing สมบูรณ์แบบ
* ข. $\text{Slack}_{setup} = +2.150\text{ ns}$, ถ้าเป็น 1-Cycle จะติดลบ $-2.850\text{ ns}$, ผ่าน Timing สมบูรณ์แบบ
* ค. $\text{Slack}_{setup} = +1.550\text{ ns}$, ถ้าเป็น 1-Cycle จะติดลบ $-2.450\text{ ns}$, ไม่ผ่าน Timing
* ง. $\text{Slack}_{setup} = -0.450\text{ ns}$, ถ้าเป็น 1-Cycle จะติดลบ $-5.450\text{ ns}$, ไม่ผ่าน Timing

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: คำนวณ Data Arrival Time:**
$$T_{arrival} = T_{cko} + T_{data\_path} = 0.350\text{ ns} + 7.850\text{ ns} = 8.200\text{ ns}$$

**ขั้นตอนที่ 2: คำนวณ Setup Slack ในโหมด Multicycle (N = 2 ไซเคิล):**
คาบเวลาสำหรับ 2 ไซเคิล:
$$T_{budget} = 2 \times T_{period} = 2 \times 5.000\text{ ns} = 10.000\text{ ns}$$
Data Required Time:
$$T_{required\_multi} = T_{budget} - T_{setup} - T_{uncertainty} = 10.000\text{ ns} - 0.150\text{ ns} - 0.100\text{ ns} = 9.750\text{ ns}$$
คำนวณ Slack:
$$\text{Slack}_{setup\_multi} = T_{required\_multi} - T_{arrival} = 9.750\text{ ns} - 8.200\text{ ns} = +1.550\text{ ns}$$
ระบบผ่าน Timing อย่างปลอดภัยด้วย Margin ถึง $+1.550\text{ ns}$!

**ขั้นตอนที่ 3: คำนวณ Setup Slack ในโหมด Default (N = 1 ไซเคิล):**
Data Required Time ใน 1 ไซเคิล:
$$T_{required\_single} = 1 \times 5.000\text{ ns} - 0.150\text{ ns} - 0.100\text{ ns} = 4.750\text{ ns}$$
คำนวณ Slack:
$$\text{Slack}_{setup\_single} = T_{required\_single} - T_{arrival} = 4.750\text{ ns} - 8.200\text{ ns} = -3.450\text{ ns}$$
หากไม่ประกาศ Multicycle เส้นทางนี้จะติดลบรุนแรงถึง $-3.450\text{ ns}$!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** ตัวเลข $+1.550\text{ ns}$ และ $-3.450\text{ ns}$ ถูกต้องตามหลักคณิตศาสตร์ STA ทุกประการ
* **ข้อ ข. ไม่ถูกต้อง:** ลืมหักค่า $T_{cko}$
* **ข้อ ค. ไม่ถูกต้อง:** ค่า 1-cycle slack คำนวณผิด
* **ข้อ ง. ไม่ถูกต้อง:** คำนวณผิดพลาดทำให้ Slack ติดลบ

**คำตอบที่ถูกต้อง:** **ข้อ ก.**

### ข้อที่ 3: การประเมินความเสี่ยงของการใช้คำสั่ง set_false_path ผิดวัตถุประสงค์ (False Path Audit Risk Analysis)

#### โจทย์คำถาม:
ในระหว่างขั้นตอนการตรวจแบบ (Kenzu Audit) ของระบบประมวลผลเครือข่ายความเร็วสูง วิศวกรตรวจพบคำสั่ง 4 คำสั่งในไฟล์คอนสเตรนต์ XDC:

1. `set_false_path -from [get_ports rst_n_async]`
2. `set_false_path -from [get_cells -hierarchical *cfg_reg*]` (รีจิสเตอร์เก็บค่าพารามิเตอร์ที่เขียนผ่าน AXI-Lite ตอนบูตเท่านั้น)
3. `set_false_path -from [get_clocks clk_core] -to [get_clocks clk_pcie]` (บัสข้อมูล 64 บิตส่งข้ามโดเมนนาฬิกาโดยมี FIFO ควบคุม)
4. `set_case_analysis 0 [get_pins u_mux/sel]` (ขาสวิตช์เลือกโหมดปกติเทียบกับโหมด BIST)

ในฐานะ Principal Verification Reviewer จงประเมินว่า **คำสั่งใดมีความเสี่ยงระดับวิกฤต (Critical High Risk) ที่จะปิดบังบั๊กของฮาร์ดแวร์และก่อให้เกิดข้อผิดพลาดร้ายแรงบนชิปจริง**:
* ก. คำสั่งที่ 1 (เพราะ Asynchronous Reset ต้องเช็ค Recovery/Removal Time) และ คำสั่งที่ 3 (เพราะ False Path บนบัส CDC จะทำลายการควบคุม Bus Skew)
* ข. เฉพาะคำสั่งที่ 2 เท่านั้น
* ค. เฉพาะคำสั่งที่ 4 เท่านั้น
* ง. ทั้งคำสั่งที่ 2 และ 4 มีความเสี่ยงสูงที่สุด

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: วิเคราะห์คำสั่งที่ 1 (`set_false_path` บน Reset):**
* แม้ว่า Reset จะเป็น Asynchronous ตอนแอกทีฟ ($0 \to 1$) แต่จังหวะ **ปลดรีเซ็ต (Reset Deassertion: $1 \to 0$)** จะต้องซิงโครไนซ์กับขอบนาฬิกาเพื่อป้องกัน Metastability
* การใส่ `set_false_path` ครอบทั้งพอร์ต จะทำให้เครื่องมือ **ไม่ตรวจสอบ Recovery Time และ Removal Time** ของรีเซ็ต ส่งผลให้ฟลิปฟล็อปบางตัวหลุดจากรีเซ็ตก่อนตัวอื่นในคนละไซเคิล (Reset Skew Hazard)! จึงมีความเสี่ยงสูงมาก

**ขั้นตอนที่ 2: วิเคราะห์คำสั่งที่ 2 (Quasi-Static Config Register):**
* รีจิสเตอร์ที่เขียนเฉพาะตอนเปิดเครื่องและคงที่ตลอดเวลา เป็นการใช้งาน `set_false_path` ที่ถูกต้องตามตำราและปลอดภัย

**ขั้นตอนที่ 3: วิเคราะห์คำสั่งที่ 3 (`set_false_path` ข้าม Clock Domain บนบัส 64 บิต):**
* การใส่ `set_false_path` ข้ามระหว่าง Clock Core และ PCIe จะตัดการควบคุมความยาวสายส่งของบัสข้อมูลทั้ง 64 บิตโดยสิ้นเชิง
* เครื่องมือ Place & Route จะไม่ควบคุม Bus Skew ทำให้บิตข้อมูลและสัญญาณ Handshake วิ่งไปถึงปลายทางด้วยความล่าช้าที่ต่างกันเกิน 1 ไซเคิล นำไปสู่ **Silent Data Corruption** บนชิปจริงทันที! นี่คือข้อห้ามระดับสูงสุด!

**ขั้นตอนที่ 4: วิเคราะห์คำสั่งที่ 4 (`set_case_analysis`):**
* เป็นการกำหนดโหมดการทำงานตามปกติ ปลอดภัย $100\%$

ดังนั้น คำสั่งที่มีความเสี่ยงระดับวิกฤตคือ **คำสั่งที่ 1 และ คำสั่งที่ 3**!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** ชี้ชัดถึงความเสี่ยงของการละเลย Recovery/Removal บน Reset (คำสั่ง 1) และการทำลาย Bus Skew บน CDC (คำสั่ง 3)
* **ข้อ ข., ค., และ ง. ไม่ถูกต้อง:** เข้าใจผิดเกี่ยวกับความปลอดภัยของ Config Register และ Case Analysis

**คำตอบที่ถูกต้อง:** **ข้อ ก.**
