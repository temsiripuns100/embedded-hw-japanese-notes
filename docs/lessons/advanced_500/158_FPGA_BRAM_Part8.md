## 1. ทฤษฎีวิศวกรรมเชิงลึก (高度なエンジニアリング理論)

### 1.1 มิติของการขยายขนาดหน่วยความจำ (Width Expansion vs Depth Expansion)
ในระบบประมวลผลขนาดใหญ่ ข้อมูลตารางค้นหา (Lookup Tables), โครงสร้างคำสั่ง (Order Books ในระบบการเงินความถี่สูง), หรือเฟรมบัฟเฟอร์ มักมีขนาดใหญ่เกินกว่าขีดจำกัดของฮาร์ดแวร์ Block RAM เพียงก้อนเดียว ($36\text{ Kbits}$) วิศวกรต้องผสมผสาน BRAM หลายบล็อกเข้าด้วยกันผ่าน 2 รูปแบบพื้นฐาน:

```
                  การเปรียบเทียบสถาปัตยกรรมขยายหน่วยความจำ
                  
   [ 1. การขยายความกว้างบัส (Width Expansion) ]
   ต้องการ: 1024 Words x 128 bits (ใช้ BRAM36 กว้าง 32 บิต x 4 บล็อก)
   
              ADDR [9:0] ══════════════╦══════════════╦══════════════╗
                                       ▼              ▼              ▼
                                  ┌─────────┐    ┌─────────┐    ┌─────────┐
                                  │ BRAM #0 │    │ BRAM #1 │    │ BRAM #3 │
                                  │(1K x 32)│    │(1K x 32)│    │(1K x 32)│
                                  └────┬────┘    └────┬────┘    └────┬────┘
                                       ▼              ▼              ▼
   DOUT [127:0] ══════════════════[ 31:0 ]════════[ 63:32 ]═══════[127:96]
   ===> บล็อกทั้งหมดทำงานพร้อมกัน 100%, ใช้ Address เดียวกัน, ไม่ต้องมี Multiplexer!
   
   -------------------------------------------------------------------------
   
   [ 2. การขยายความลึกของแอดเดรส (Depth Expansion) ]
   ต้องการ: 4096 Words x 32 bits (ใช้ BRAM36 ลึก 1024 x 4 บล็อก)
   
              ADDR [11:10] (Bank Select) ─────────────────────────┐
              ADDR [9:0]   ════════════╦════════════╦═════════╗   │
                                       ▼            ▼         ▼   ▼
                                  ┌─────────┐  ┌─────────┐  ┌───┴─────┐
                                  │ BRAM #0 │  │ BRAM #1 │  │ BRAM #3 │
                                  │ (0-1K)  │  │ (1K-2K) │  │ (3K-4K) │
                                  └────┬────┘  └────┬────┘  └────┬────┘
                                       │            │            │
                                       ▼            ▼            ▼
                                  ┌───────────────────────────────────┐
                                  │      READ MULTIPLEXER TREE        │◄── (คอขวดไทม์มิ่ง!)
                                  └─────────────────┬─────────────────┘
                                                    ▼
                                               DOUT [31:0]
```

#### คุณลักษณะทางกายภาพ:
1. **การขยายความกว้าง (Width Expansion):**
   * บล็อก BRAM ทั้งหมดแชร์สายสัญญาณ Address, Clock, และ Enable ร่วมกัน
   * ข้อมูลถูกอ่านและเขียนขนานกันในจังหวะเดียวกัน ($T_{access}$ คงที่เท่ากับ 1 บล็อก)
   * ข้อจำกัดทางกายภาพ: อัตรา Fanout ของสายแอดเดรสเพิ่มขึ้นตามจำนวนบล็อกที่ต่อขนาน ($C_{load} = N \cdot C_{in}$)
2. **การขยายความลึก (Depth Expansion):**
   * บิตสูงสุดของแอดเดรส ($ADDR[MSB : N]$) ทำหน้าที่ถอดรหัสเลือกบล็อก (Chip Select / Enable Decoder)
   * ข้อมูลเอาต์พุตจาก BRAM ทุกบล็อกต้องถูกนำมารวมกันผ่าน **ต้นไม้มัลติเพล็กเซอร์ (Read Multiplexer Tree)**
   * **ข้อจำกัดวิกฤต:** ความล่าช้าของวงจร MUX Tree และสายไฟที่วิ่งข้ามระหว่างบล็อก BRAM ที่อยู่ห่างกันจะกลายเป็น Critical Path ที่ทำลายความถี่ $F_{max}$ ของระบบ!

### 1.2 ฟิสิกส์ของคอขวด Read Multiplexer Tree และการทำ MUX Pipelining

เมื่อขยายความลึกของหน่วยความจำขึ้นเป็น $16\text{ บล็อก}, 32\text{ บล็อก},$ หรือ $64\text{ บล็อก}$ สัญญาณเอาต์พุตของ BRAM แต่ละตัวจะต้องวิ่งผ่านโครงสร้างลอจิกมัลติเพล็กเซอร์หลายชั้น (Cascade of LUT6 and MUXF7/MUXF8/CARRY8):

```
                   โครงสร้างของ READ MULTIPLEXER TREE ขนาด 16:1
                   
   BRAM 0-3   ──► [ LUT6 Mux Layer 1 ] ──┐
   BRAM 4-7   ──► [ LUT6 Mux Layer 1 ] ──┼──► [ LUT6 Mux Layer 2 ] ──┐
   BRAM 8-11  ──► [ LUT6 Mux Layer 1 ] ──┤                           ├──► [ Final MUX ] ──► DOUT
   BRAM 12-15 ──► [ LUT6 Mux Layer 1 ] ──┘                           │
                                         [ Routing Wire Delay ] ─────┘
```

#### สมการความล่าช้าของ Unpipelined Read MUX Tree:
$$T_{read\_mux} = T_{cko\_bram} + \sum_{l=1}^{\text{Layers}} \left( T_{lut\_mux}(l) + T_{wire\_net}(l) \right) + T_{setup}$$

โดยที่:
* $\text{Layers} = \lceil \log_4(N) \rceil$ (เมื่อใช้ LUT6 สังเคราะห์เป็น 4:1 MUX)
* สำหรับหน่วยความจำขนาด 64 บล็อก: มีความลึกของ MUX อย่างน้อย 3 ถึง 4 ชั้น
* ค่าความล่าช้าในการเดินสาย Interconnect ข้ามระหว่างคอลัมน์ BRAM ($T_{wire\_net}$) มีค่าสูงมากในสถาปัตยกรรมขนาดใหญ่ ($1.5\text{ ns} - 3.5\text{ ns}$)
* **ผลลัพธ์:** ความถี่สูงสุด $F_{max}$ จะร่วงหล่นจาก $500\text{ MHz}$ เหลือเพียง $160\text{ MHz} - 220\text{ MHz}$ ทันทีหากไม่มีการแทรก Pipeline Register!

#### การแก้ปัญหาด้วย Pipelined MUX Tree:
การรักษาความถี่ระดับสูง ($> 450\text{ MHz}$) ทำได้โดยการแทรกฟลิปฟล็อปตัดตอนในแต่ละชั้นของ MUX Tree พร้อมทั้งปรับความล่าช้าของสัญญาณถอดรหัสแอดเดรส (Address Decoding Pipeline) ให้สมดุลกัน:

```
               สถาปัตยกรรม PIPELINED MUX TREE (BALANCED LATENCY)
               
   Cycle 1: ออกแอดเดรส ──► BRAM Core ทำงาน
   Cycle 2: BRAM DO_REG ขับข้อมูลออก ──► เข้าสู่ MUX Layer 1 ──► [ Pipeline Reg 1 ]
   Cycle 3: ข้อมูลผ่าน MUX Layer 2 ──► [ Pipeline Reg 2 ] ──► DOUT มีเสถียรภาพ!
   ===> Read Latency = 3 ไซเคิล แต่ความถี่ Fmax ทะยานขึ้นสู่ 500 MHz สมบูรณ์แบบ!
```

### 1.3 คณิตศาสตร์ของการเข้าถึงแบบขนานและทฤษฎีความน่าจะเป็นของการชนกันในหน่วยความจำหลายแบงก์ (Multi-Bank Conflict Probability)

เพื่อเพิ่มแบนด์วิดท์ในการเข้าถึงข้อมูลพร้อมกันจากหลายหน่วยประมวลผล (Multi-Core Processing หรือ Parallel DSP Pipelines) วิศวกรนิยมจัดระเบียบหน่วยความจำเป็น **ระบบหลายแบงก์ (Multi-Bank Memory Architecture)**:

```
                     สถาปัตยกรรม MULTI-BANK INTERLEAVED MEMORY
                     
   Client 0 Request ──┐
   Client 1 Request ──┼──► [ Crossbar Switch / Arbiter ] ──┬──► [ Bank 0 (BRAM 0) ]
   Client 2 Request ──┤                                    ├──► [ Bank 1 (BRAM 1) ]
   Client 3 Request ──┘                                    ├──► [ Bank 2 (BRAM 2) ]
                                                           └──► [ Bank 3 (BRAM 3) ]
```

#### การจัดสรรแอดเดรส (Addressing Schemes):
1. **High-Order Banking (Block Slicing):**  
   บิตบนของแอดเดรสระบุแบงก์ ($Bank = ADDR[MSB : N]$) ข้อมูลที่อยู่เรียงติดกันจะอยู่ในแบงก์เดียวกัน เหมาะสำหรับโครงสร้างข้อมูลแบบแยกส่วน
2. **Low-Order Interleaving (Cyclic Slicing):**  
   บิตล่างของแอดเดรสระบุแบงก์ ($Bank = ADDR[K-1 : 0]$) ข้อมูลที่อยู่ติดกันจะกระจายตัวอยู่คนละแบงก์ เหมาะสำหรับการเข้าถึงแบบ Burst หรือ Stream เพราะช่วยขจัด Bank Conflict ได้อย่างสมบูรณ์แบบในการเข้าถึงแบบ Sequential!

#### การคำนวณความน่าจะเป็นของการชนกัน (Bank Conflict Probability):
เมื่อมีผู้ขอเข้าถึงอิสระจำนวน $M$ พอร์ต (Clients) พยายามเข้าถึงหน่วยความจำที่มีจำนวน $B$ แบงก์พร้อมกันแบบสุ่ม (Uniformly Distributed Random Access):

ความน่าจะเป็นที่ **ไม่มีลูกค้ารายใดชนกันเลย (Zero Conflict Probability)** คือการที่ลูกค้าแต่ละรายเลือกแบงก์ไม่ซ้ำกัน:

$$P(\text{No Conflict}) = \prod_{i=0}^{M-1} \left( 1 - \frac{i}{B} \right) = \frac{B \cdot (B-1) \cdot (B-2) \cdots (B-M+1)}{B^M} = \frac{B!}{B^M (B-M)!}$$

ดังนั้น ความน่าจะเป็นที่จะเกิด **สภาวะการแย่งชิงแบงก์ (Bank Conflict Probability)** อย่างน้อยหนึ่งคู่คือ:

$$P(\text{Conflict}) = 1 - P(\text{No Conflict}) = 1 - \frac{B!}{B^M (B-M)!}$$

#### ปริมาณงานที่มีประสิทธิภาพสุทธิ (Effective Throughput):
จำนวนแบงก์เฉลี่ยที่มีการเข้าถึงข้อมูลสำเร็จใน 1 ไซเคิล ($E[\text{Active Banks}]$):

$$E[\text{Throughput}] = B \cdot \left[ 1 - \left( 1 - \frac{1}{B} \right)^M \right]$$

```
          การเปรียบเทียบ THROUGHPUT: CONFLICT PROBABILITY (B = 8 Banks)
          
   จำนวน Clients (M)    P(No Conflict)    P(Conflict)    Effective Throughput
   -----------------    --------------    -----------    --------------------
   M = 1                1.000 (100%)       0.000 (0%)    1.00 Banks/cycle
   M = 2                0.875 (87.5%)      0.125 (12.5%) 1.88 Banks/cycle
   M = 4                0.410 (41.0%)      0.590 (59.0%) 3.31 Banks/cycle
   M = 8                0.002 (0.2%)       0.998 (99.8%) 5.25 Banks/cycle
```

### 1.4 การจัดวางเชิงกายภาพ (Floorplanning) และการเดินสายข้าม Super Logic Regions (SLR Crossings)

ในชิป FPGA ขนาดใหญ่ที่ใช้เทคโนโลยี Stacked Silicon Interconnect (SSI) ชิปจะถูกแบ่งออกเป็น Die ย่อยๆ เรียกว่า **Super Logic Regions (SLRs)** ที่เชื่อมต่อกันด้วยสะพานไมโครบัมพ์ (Passive Interposer):

```
                   ปัญหาการวาง BRAM ข้าม SUPER LOGIC REGIONS
                   
   ┌─────────────────────────────────────────────────────────────┐
   │ SLR 1: Upper Die                                            │
   │ [ BRAM 32-63 ] ───┐                                         │
   └───────────────────┼─────────────────────────────────────────┘
                       │ Interposer Micro-bumps (Laguna Registers)
                       │ สายยาว ความจุสูงมาก (C_interposer >> C_fabric)
   ┌───────────────────┼─────────────────────────────────────────┐
   │ SLR 0: Lower Die  │                                         │
   │ [ BRAM 0-31 ] ────┴──► [ Read Multiplexer Tree ]            │
   └─────────────────────────────────────────────────────────────┘
```

> [!CAUTION]
> **กฎเหล็กของการวาง BRAM ข้าม SLR:**  
> ห้ามสร้าง BRAM Matrix ก้อนเดี่ยวที่มีวงจร Read MUX ข้ามระหว่าง SLR เด็ดขาด!  
> การข้ามรอยต่อของ Die จะต้องผ่านฟลิปฟล็อปพิเศษที่เรียกว่า **Laguna Registers** และมีความล่าช้าในการเดินทางของสัญญาณอย่างน้อย 1 คาบเวลาเต็ม หากปล่อยให้เครื่องมือวาง BRAM กระจัดกระจายข้าม Die โดยไร้ Floorplan คอนสเตรนต์ WNS จะติดลบอย่างรุนแรงจนแก้ไขไม่ได้!

## 2. ทริคหน้างาน OJT แบบ Step-by-Step (現場の実践テクニック)

### 2.1 กรณีศึกษาความล้มเหลวหน้างาน: คอขวดของสมุดคำสั่งซื้อในระบบเทรดความเร็วสูง HFT (Ultra-Low Latency Order Book Timing Collapse)

```
+----------------------------------------------------------------------------------------------------+
| กรณีศึกษาความล้มเหลวหน้างาน (現場の失敗事例)                                                                 |
| เหตุการณ์: ระบบจับคู่คำสั่งซื้อขายหุ้นความถี่สูง (HFT Matching Engine) บนชิป Virtex UltraScale+ VU9P         |
| อาการ: ระบบทำงานผิดพลาดในการรันที่ความถี่เป้าหมาย 400MHz โดย Vivado รายงาน Setup Violation WNS = -1.85ns   |
|        เมื่อทีมงานพยายามแก้ขัดด้วยการลดความถี่ลงเหลือ 220MHz ปรากฏว่า Tick-to-Trade Latency พุ่งสูงขึ้น 82%    |
|        และระบบถูกคู่แข่งส่งออร์เดอร์ตัดหน้าในตลาดหลักทรัพย์โตเกียว (TSE) สูญเสียมูลค่าการเทรดมหาศาล!            |
+----------------------------------------------------------------------------------------------------+
```

#### การวิเคราะห์หาสาเหตุรากเหง้าด้วยหลักการ 5 Whys (5 Whys Root Cause Analysis):

1. **ทำไมระบบจับคู่คำสั่งจึงไม่สามารถทำงานที่ 400MHz ได้?**  
   *คำตอบ:* สัญญาณบนเส้นทางอ่านข้อมูลราคาของ Limit Order Book (LOB) ไม่สามารถวิ่งถึงฟลิปฟล็อปปลายทางได้ทันภายในคาบเวลา $2.5\text{ ns}$

2. **ทำไมเส้นทางอ่านข้อมูลจึงกินเวลาหน่วงสูงถึง $4.35\text{ ns}$ ($WNS = -1.85\text{ ns}$)?**  
   *คำตอบ:* วงจร Order Book มีขนาดความจุ $65,536\text{ รายการ}$ ขนาดกว้าง 64 บิต ถูกสังเคราะห์จากบล็อก BRAM36 จำนวน 64 บล็อก โดยมีวงจร Read MUX ขนาด $64:1$ ที่ไม่มีการแทรก Pipeline Register เลยแม้แต่สเตจเดียว

3. **ทำไมวิศวกรจึงไม่แทรก Pipeline Register ใน MUX Tree?**  
   *คำตอบ:* วิศวกรเข้าใจผิดคิดว่า "ยิ่ง Latency เป็น 1 ไซเคิล ระบบจะยิ่งเร็วที่สุด" จึงบังคับให้การอ่านข้อมูลต้องเสร็จสมบูรณ์ในรอบสัญญาณนาฬิกาเดียว (1-cycle read)

4. **ทำไมผลลัพธ์ของการทำ 1-cycle read จึงทำให้ระบบทำงานช้าลงกว่าเดิม?**  
   *คำตอบ:* เพื่อให้ 1-cycle read ผ่าน Timing ความถี่ระบบต้องถูกลดจาก $400\text{ MHz}$ ($2.5\text{ ns}$) เหลือ $220\text{ MHz}$ ($4.54\text{ ns}$) เมื่อคูณด้วยจำนวนสเตจการจับคู่ทั้งหมด 12 สเตจ ระยะเวลาตอบสนองรวมกลับกลายเป็น $54.5\text{ ns}$ ในขณะที่หากใช้ 400MHz และยอมรับ Latency ของ MUX 3 ไซเคิล ระยะเวลาตอบสนองรวมจะเหลือเพียง $35.0\text{ ns}$ เท่านั้น!

5. **ทำไม Vivado จึงวางตำแหน่ง BRAM ทั้ง 64 บล็อกกระจัดกระจายไปทั่วชิป?**  
   *คำตอบ:* ไม่มีข้อกำหนด Floorplanning (`Pblock`) ในไฟล์ XDC ทำให้เครื่องมือ Place & Route วาง BRAM กระจายตัวข้าม 3 Clock Regions และคาบเกี่ยวข้ามรอยต่อ SLR0 และ SLR1 สร้างเส้นทางเดินสายที่ยาวเหยียดระดับหายนะ!

   ยึดติดกับ 1-Cycle Latency โดยไม่สน Fmax          ใช้ Unpipelined MUX 64:1 ชั้นเดียวจบ

              \                                           \
               \                                           \  ต้นไม้ MUX ลึก 4 ชั้นลอจิก

### 2.3 คู่มือปฏิบัติงาน SOP: การสังเคราะห์และควบคุมไทม์มิ่งหน่วยความจำขนาดใหญ่ (Large Memory Synthesis SOP)

#### สเต็ปที่ 1: การคำนวณและเลือกใช้ Pipelined MUX Tree ใน RTL
* เมื่อหน่วยความจำมีความลึกเกินกว่า $4,096\text{ Words}$ และต้องใช้ BRAM เกินกว่า 8 บล็อกขึ้นไป **ต้องออกแบบโครงสร้าง Pipelined MUX เสมอ**
* กำหนดให้มีฟลิปฟล็อปคั่นระหว่างสเตจของ MUX ทุกๆ อัตราส่วน $4:1$ หรือ $8:1$:

```verilog
// โครงสร้าง 2-Stage Pipelined Multiplexer สำหรับ BRAM 16 บล็อก
reg [DATA_WIDTH-1:0] mux_stage1 [0:3];
reg [1:0]            addr_bank_pipe1;
reg [DATA_WIDTH-1:0] dout_final;

// Stage 1: ยุบ 16 เหลือ 4
integer g;
always @(posedge clk) begin
    addr_bank_pipe1 <= addr[13:12]; // เก็บ Bank Select สำหรับสเตจถัดไป
    for (g = 0; g < 4; g = g + 1) begin
        case (addr[11:10])
            2'b00: mux_stage1[g] <= bram_out[g*4 + 0];
            2'b01: mux_stage1[g] <= bram_out[g*4 + 1];
            2'b10: mux_stage1[g] <= bram_out[g*4 + 2];
            2'b11: mux_stage1[g] <= bram_out[g*4 + 3];
        endcase
    end
end

// Stage 2: ยุบ 4 เหลือ 1 (Final DOUT)
always @(posedge clk) begin
    dout_final <= mux_stage1[addr_bank_pipe1];
end
```

#### สเต็ปที่ 2: การใช้แอตทริบิวต์ `ram_decomp` ของ Vivado
* หากต้องการให้ Synthesis Engine สร้างโครงสร้าง Pipelined Multiplexer ให้อัตโนมัติ สามารถใส่แอตทริบิวต์:
  `(* ram_decomp = "power" *)` หรือ `(* ram_style = "block" *)`
* แอตทริบิวต์ `ram_decomp = "power"` สั่งให้ Vivado สร้างวงจรถอดรหัสแบบประหยัดพลังงาน โดยจะส่ง Enable ไปยังเฉพาะ BRAM บล็อกที่กำลังถูกเข้าถึงเท่านั้น

#### สเต็ปที่ 3: การล็อคพื้นที่ Floorplanning ด้วย Pblock ในไฟล์ XDC
* จัดกลุ่ม BRAM ทั้งหมดและลอจิก MUX ที่เกี่ยวข้องให้อยู่ภายใน Clock Region เดียวกัน หรือคอลัมน์ที่อยู่ติดกัน:

```tcl
# สร้าง Pblock เพื่อล็อค Limit Order Book ให้อยู่ใน Clock Region เดียวกัน
create_pblock pblock_order_book
add_cells_to_pblock [get_pblocks pblock_order_book] [get_cells -hierarchical -filter {NAME =~ *lob_mem_inst*}]
resize_pblock [get_pblocks pblock_order_book] -add {CLOCKREGION_X2Y2:CLOCKREGION_X2Y3}
```

## 4. ควิซวิเคราะห์ปัญหาระดับวิศวกรอาวุโส (上級技術クイズ)

### ข้อที่ 1: การคำนวณเปรียบเทียบ Latency ทางกายภาพจริงระหว่าง Unpipelined vs Pipelined Read MUX

#### โจทย์คำถาม:
ในสถาปัตยกรรมตัวประมวลผลเครือข่าย วงจรค้นหาตารางแอดเดรสขนาดความจุ $32,768\text{ Words} \times 64\text{ bits}$ ถูกสร้างขึ้นจากการต่อพ่วง BRAM36 จำนวน $N = 32\text{ บล็อก}$ (Depth Expansion)

ทีมวิศวกรกำลังเปรียบเทียบสองแนวทางการออกแบบ:
* **แนวทาง A (Unpipelined Single-Cycle Read):** ไม่มีการแทรกฟลิปฟล็อปใน Read MUX Tree โดยสัญญาณจากเอาต์พุตของ BRAM ทั้ง 32 ตัววิ่งผ่านลอจิก LUT6/MUXF7/MUXF8 เป็นโครงสร้าง MUX 32:1 โดยตรง
  * มีค่าความล่าช้าของวงจรรวม $T_{path\_A} = 4.80\text{ ns}$ (ทำให้ระบบสามารถรันความถี่สัญญาณนาฬิกาสูงสุดได้เพียง $f_{clk\_A} = 200\text{ MHz}$ หรือคาบเวลา $T_A = 5.0\text{ ns}$)
  * สถาปัตยกรรมโดยรวมมีจำนวนขั้นตอนใน Pipeline ทั้งหมด $D_A = 6\text{ สเตจ}$ (รอบการทำงาน)
* **แนวทาง B (Pipelined Multi-Stage Read):** แทรก Pipeline Register จำนวน 2 สเตจเข้าไปใน Read MUX Tree ทำให้แบ่งเส้นทางความล่าช้าออกเป็น 3 ช่วงอย่างสมดุล โดยช่วงที่ยาวที่สุดมีค่าความล่าช้าเพียง $T_{path\_B} = 1.85\text{ ns}$
  * ระบบสามารถรันความถี่สัญญาณนาฬิกาสูงสุดได้ถึง $f_{clk\_B} = 500\text{ MHz}$ (คาบเวลา $T_B = 2.0\text{ ns}$)
  * การเพิ่มฟลิปฟล็อปทำให้จำนวนขั้นตอนใน Pipeline รวมเพิ่มขึ้นเป็น $D_B = 6 + 2 = 8\text{ สเตจ}$ (รอบการทำงาน)

จงคำนวณหา:
1. เวลาหน่วงทางกายภาพในการประมวลผลคำขอค้นหา 1 รายการตั้งแต่เริ่มต้นจนจบ (End-to-End Latency: $t_{latency}$) ของแนวทาง A
2. เวลาหน่วงทางกายภาพในการประมวลผลของแนวทาง B
3. เปอร์เซ็นต์ความเร็วที่แนวทาง B ทำงานได้เร็วกว่าแนวทาง A (Latency Speedup Percentage)

* ก. $t_{latency\_A} = 30.0\text{ ns}$, $t_{latency\_B} = 16.0\text{ ns}$, แนวทาง B เร็วกว่า $46.7\%$
* ข. $t_{latency\_A} = 28.8\text{ ns}$, $t_{latency\_B} = 14.8\text{ ns}$, แนวทาง B เร็วกว่า $48.6\%$
* ค. $t_{latency\_A} = 30.0\text{ ns}$, $t_{latency\_B} = 24.0\text{ ns}$, แนวทาง B เร็วกว่า $20.0\%$
* ง. $t_{latency\_A} = 25.0\text{ ns}$, $t_{latency\_B} = 16.0\text{ ns}$, แนวทาง B เร็วกว่า $36.0\%$

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: คำนวณ End-to-End Latency ของแนวทาง A:**
* คาบเวลาสัญญาณนาฬิกา:
  $$T_A = \frac{1}{200\text{ MHz}} = 5.0\text{ ns}$$
* จำนวนสเตจของระบบ:
  $$D_A = 6\text{ ไซเคิล}$$
* เวลาหน่วงรวมจริงทางกายภาพ:
  $$t_{latency\_A} = D_A \times T_A = 6 \times 5.0\text{ ns} = 30.0\text{ ns}$$

**ขั้นตอนที่ 2: คำนวณ End-to-End Latency ของแนวทาง B:**
* คาบเวลาสัญญาณนาฬิกา:
  $$T_B = \frac{1}{500\text{ MHz}} = 2.0\text{ ns}$$
* จำนวนสเตจของระบบ (รวม MUX Pipeline 2 สเตจ):
  $$D_B = 6 + 2 = 8\text{ ไซเคิล}$$
* เวลาหน่วงรวมจริงทางกายภาพ:
  $$t_{latency\_B} = D_B \times T_B = 8 \times 2.0\text{ ns} = 16.0\text{ ns}$$

**ขั้นตอนที่ 3: คำนวณเปอร์เซ็นต์ความเร็วที่ปรับปรุงได้ (Latency Reduction / Speedup):**
$$\text{Speedup Percentage} = \frac{t_{latency\_A} - t_{latency\_B}}{t_{latency\_A}} \times 100\% = \frac{30.0\text{ ns} - 16.0\text{ ns}}{30.0\text{ ns}} \times 100\% = \frac{14.0}{30.0} \times 100\% \approx 46.67\% \approx 46.7\%$$

การยอมเพิ่ม Pipeline Stages จาก 6 เป็น 8 ไซเคิล ช่วยปลดล็อกให้ความถี่เพิ่มจาก 200MHz เป็น 500MHz ทำให้เวลาประมวลผลจริงลดลงจาก $30\text{ ns}$ เหลือเพียง $16\text{ ns}$ เร็วขึ้นถึง **$46.7\%$**!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** ตัวเลข $30.0\text{ ns}$, $16.0\text{ ns}$ และ $46.7\%$ ถูกต้องตามหลักคณิตศาสตร์ทุกประการ
* **ข้อ ข. ไม่ถูกต้อง:** นำค่า Data Path เพียวๆ ($4.8\text{ ns}$ และ $1.85\text{ ns}$) มาคูณรอบเวลาโดยไม่คิดคาบ Clock Period
* **ข้อ ค. ไม่ถูกต้อง:** คิดว่าจำนวนสเตจของ B คือ 12 ไซเคิล
* **ข้อ ง. ไม่ถูกต้อง:** คำนวณคาบเวลาของ A ผิดพลาด

**คำตอบที่ถูกต้อง:** **ข้อ ก.**

### ข้อที่ 2: การคำนวณความน่าจะเป็นของการแย่งชิงแบงก์และ Throughput สุทธิ (Multi-Bank Conflict Math)

#### โจทย์คำถาม:
ในระบบประมวลผลกราฟิกส์ GPU บน FPGA วงจรแรสเตอร์ไรเซอร์มีหน่วยคำนวณพิกเซลแบบขนานจำนวน $M = 4\text{ Units}$ (Clients) โดยแต่ละ Unit มีความต้องการอ่านและเขียนข้อมูลพิกเซลลงใน On-Chip Frame Buffer พร้อมกันในทุกๆ รอบสัญญาณนาฬิกา

สถาปัตยกรรมบัฟเฟอร์ถูกจัดโครงสร้างเป็นระบบหลายแบงก์ที่มีจำนวนแบงก์อิสระ $B = 8\text{ แบงก์}$ โดยพิกเซลที่แต่ละ Unit สุ่มเข้าถึงมีการกระจายตัวแบบสุ่มอย่างสม่ำเสมอ (Uniform Random Distribution)  
หากในรอบใดที่มีการเข้าถึงแบงก์เดียวกันมากกว่า 1 คำขอ วงจร Crossbar Arbiter จะอนุญาตให้เพียง 1 คำขอเข้าถึงได้ ส่วนคำขอที่เหลือจะถูก Stall ไว้ในรอบถัดไป

จงคำนวณหา:
1. ความน่าจะเป็นที่ในรอบสัญญาณนาฬิกาหนึ่งๆ จะ **ไม่มีการแย่งชิงแบงก์เกิดขึ้นเลย ($P_{no\_conflict}$)** (ทุก Unit ได้รับข้อมูลพร้อมกันครบทั้ง 4 ตัว)
2. ความน่าจะเป็นที่จะเกิด **Bank Conflict ขึ้นอย่างน้อย 1 คู่ ($P_{conflict}$)**
3. ปริมาณงานเฉลี่ยสุทธิ (Expected Throughput: จำนวนคำขอที่ได้รับบริการสำเร็จต่อรอบสัญญาณนาฬิกา)

* ก. $P_{no\_conflict} \approx 0.4102$, $P_{conflict} \approx 0.5898$, Expected Throughput $\approx 3.31\text{ Requests/cycle}$
* ข. $P_{no\_conflict} \approx 0.5000$, $P_{conflict} \approx 0.5000$, Expected Throughput $\approx 2.00\text{ Requests/cycle}$
* ค. $P_{no\_conflict} \approx 0.2500$, $P_{conflict} \approx 0.7500$, Expected Throughput $\approx 3.00\text{ Requests/cycle}$
* ง. $P_{no\_conflict} \approx 0.4102$, $P_{conflict} \approx 0.5898$, Expected Throughput $\approx 4.00\text{ Requests/cycle}$

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: คำนวณความน่าจะเป็น $P_{no\_conflict}$:**
จำนวนวิธีที่ Unit ทั้ง 4 ตัวเลือกแบงก์จาก 8 แบงก์โดยไม่ซ้ำกันเลย:
$$P_{no\_conflict} = \prod_{i=0}^{4-1} \left( 1 - \frac{i}{8} \right) = \left(1 - \frac{0}{8}\right) \times \left(1 - \frac{1}{8}\right) \times \left(1 - \frac{2}{8}\right) \times \left(1 - \frac{3}{8}\right)$$
$$P_{no\_conflict} = 1 \times \frac{7}{8} \times \frac{6}{8} \times \frac{5}{8} = \frac{7 \times 6 \times 5}{512} = \frac{210}{512} \approx 0.410156 \approx 0.4102 \quad (41.02\%)$$

**ขั้นตอนที่ 2: คำนวณความน่าจะเป็น $P_{conflict}$:**
$$P_{conflict} = 1 - P_{no\_conflict} = 1 - 0.410156 = 0.589844 \approx 0.5898 \quad (58.98\%)$$

**ขั้นตอนที่ 3: คำนวณ Expected Throughput สุทธิ:**
จำนวนแบงก์ที่ไม่ถูกเลือกเลยโดย Unit ใดๆ มีความน่าจะเป็น:
$$P(\text{Bank } k \text{ is empty}) = \left( 1 - \frac{1}{B} \right)^M = \left( 1 - \frac{1}{8} \right)^4 = \left( \frac{7}{8} \right)^4 = \frac{2401}{4096} \approx 0.58618$$

ความน่าจะเป็นที่แบงก์ $k$ จะมีคำขออย่างน้อย 1 คำขอ (ซึ่งจะให้บริการสำเร็จ 1 คำขอ):
$$P(\text{Bank } k \text{ is served}) = 1 - \left( 1 - \frac{1}{8} \right)^4 = 1 - 0.58618 = 0.41382$$

จำนวนคำขอเฉลี่ยสุทธิที่ได้รับบริการต่อรอบ (ผลรวมค่าคาดหมายของทุกแบงก์):
$$E[\text{Throughput}] = B \times P(\text{Bank served}) = 8 \times 0.41382 \approx 3.3105 \approx 3.31\text{ Requests/cycle}$$

ผลลัพธ์แสดงให้เห็นว่า แม้จะส่งคำขอมา 4 ตัว แต่เนื่องจากสภาวะการชนกันของแบงก์ที่มีโอกาสเกิดถึง $58.98\%$ ปริมาณงานจริงที่ทำได้จะลดทอนเหลือเฉลี่ย $3.31$ คำขอต่อไซเคิล!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** ค่า $0.4102$, $0.5898$ และ $3.31\text{ Requests/cycle}$ ถูกต้องตามหลักทฤษฎีความน่าจะเป็นและการสุ่ม
* **ข้อ ข. ไม่ถูกต้อง:** เป็นการประมาณการแบบหยาบเกินจริง
* **ข้อ ค. ไม่ถูกต้อง:** คำนวณการกระจายตัวผิด
* **ข้อ ง. ไม่ถูกต้อง:** Expected Throughput คิดว่าไม่มีการชนกัน (คิดเป็น 4.0 เต็ม)

**คำตอบที่ถูกต้อง:** **ข้อ ก.**

### ข้อที่ 3: การวิเคราะห์การจัดสรรบล็อก BRAM และ Fanout ของ Address Bus (Width vs Depth Trade-Off)

#### โจทย์คำถาม:
วิศวกรต้องการสร้างหน่วยความจำที่มีขนาดความจุรวม **$131,072\text{ bits}$** ($128\text{ Kbits}$) โดยใช้บล็อกฮาร์ดแวร์ `RAMB18E2` (ซึ่งแต่ละบล็อกมีความจุ $18\text{ Kbits}$ หรือจัดคอนฟิกได้สูงสุด $16,384\text{ bits}$ ในโหมดสแตนดาร์ด $2^N$)

หากเปรียบเทียบการจัดโครงสร้างสองรูปแบบ:
* **รูปแบบที่ 1 (Pure Width Expansion):** จัดเป็นขนาดความลึก $512\text{ Words} \times 256\text{ bits}$ โดยใช้บล็อก RAMB18E2 ในโหมด $512 \times 32\text{-bit}$ ต่อขนานกันทั้งหมด $8\text{ บล็อก}$
* **รูปแบบที่ 2 (Pure Depth Expansion):** จัดเป็นขนาดความลึก $4,096\text{ Words} \times 32\text{ bits}$ โดยใช้บล็อก RAMB18E2 ในโหมด $512 \times 32\text{-bit}$ ต่อเรียงกันทางความลึกทั้งหมด $8\text{ บล็อก}$ พร้อมวงจร Read MUX 8:1

จงพิจารณาข้อความต่อไปนี้ว่าข้อใด **ถูกต้องแม่นยำที่สุด**:
* ก. รูปแบบที่ 1 มี Fanout บนสายสัญญาณแอดเดรสต่ำกว่ารูปแบบที่ 2 และสิ้นเปลืองลอจิก LUT ในการทำ Read MUX มากกว่า
* ข. รูปแบบที่ 1 ต้องขับสายแอดเดรสขนาด 9 บิตไปยัง BRAM ทั้ง 8 บล็อกพร้อมกัน ทำให้มี Fanout รวมบนบัสแอดเดรสเท่ากับ 8 โหลดต่อบิต แต่ไม่มีค่าใช้จ่ายด้าน Read MUX LUT เลย ในขณะที่รูปแบบที่ 2 ต้องใช้ LUT สำหรับสร้าง Read MUX 8:1 แต่มี Dynamic Power ของ BRAM ต่ำกว่าเพราะสามารถปิด Enable บล็อกที่ไม่ใช้งานได้ 7 บล็อกในแต่ละไซเคิล
* ค. รูปแบบที่ 2 มีความถี่สูงสุด $F_{max}$ สูงกว่ารูปแบบที่ 1 เสมอ เนื่องจากใช้สายแอดเดรสน้อยกว่า
* ง. ทั้งสองรูปแบบกินกำลังไฟฟ้า Dynamic Power เท่ากันทุกประการเนื่องจากใช้ BRAM จำนวน 8 บล็อกเท่ากัน

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: วิเคราะห์รูปแบบที่ 1 (Width Expansion: $512 \times 256$):**
* ใช้ BRAM 8 บล็อกทำงานขนานกัน
* สายแอดเดรสขนาด 9 บิต ($2^9 = 512$) วิ่งกระจายไปยังขาแอดเดรสของ BRAM ทั้ง 8 ตัวพร้อมกัน:
  $$\text{Fanout per address bit} = 8\text{ BRAM inputs}$$
* ในการอ่านข้อมูล ข้อมูล 256 บิตดึงออกจาก BRAM ทั้ง 8 ตัวเข้าสู่ปลายทางโดยตรง **ไม่จำเป็นต้องมี Multiplexer เลย (LUT Overhead = 0)**
* ด้านกำลังไฟฟ้า: ทุกครั้งที่มีคำขออ่าน/เขียน BRAM ทั้ง 8 ตัวจะตื่นขึ้นมาสลับสถานะพร้อมกัน $100\%$ ทำให้เกิด Dynamic Power สูงสุด

**ขั้นตอนที่ 2: วิเคราะห์รูปแบบที่ 2 (Depth Expansion: $4096 \times 32$):**
* ใช้ BRAM 8 บล็อกเรียงต่อความลึก แอดเดรสมีขนาด 12 บิต ($2^{12} = 4096$):
  * บิตล่าง 9 บิต ($ADDR[8:0]$) วิ่งไปยัง BRAM ทั้ง 8 บล็อก
  * บิตบน 3 บิต ($ADDR[11:9]$) วิ่งเข้าวงจรถอดรหัส Enable Decoder เพื่อเปิดใช้งาน BRAM เพียง 1 บล็อกในแต่ละไซเคิล!
* ด้านกำลังไฟฟ้า: มี BRAM เพียง 1 ใน 8 ตัวเท่านั้นที่ Active ในแต่ละไซเคิล อีก 7 ตัวอยู่ในสถานะ Idle ทำให้ **Dynamic Power ของ BRAM ลดลงเหลือเพียงประมาณ $\frac{1}{8} \approx 12.5\%$** เมื่อเทียบกับรูปแบบที่ 1!
* ข้อเสีย: เอาต์พุตของ BRAM ทั้ง 8 ตัวต้องต่อผ่าน MUX ขนาด 8:1 กว้าง 32 บิต ซึ่งกินลอจิก LUT6 ใน Fabric และเพิ่ม Propagation Delay

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ไม่ถูกต้อง:** รูปแบบที่ 1 ไม่มี Read MUX เลย ไม่ใช่สิ้นเปลืองมากกว่า
* **ข้อ ข. ถูกต้องสมบูรณ์แบบ:** อธิบายพฤติกรรม Fanout, การประหยัด LUT ในรูปแบบที่ 1, และการประหยัด Dynamic Power จากการ Enable ทีละบล็อกในรูปแบบที่ 2 ได้อย่างถูกต้องตามทฤษฎีและฟิสิกส์ของชิป
* **ข้อ ค. ไม่ถูกต้อง:** รูปแบบที่ 2 มักจะมี $F_{max}$ ต่ำกว่าหรือต้องใส่ Pipeline เนื่องจากติด MUX Tree
* **ข้อ ง. ไม่ถูกต้อง:** Dynamic Power ไม่เท่ากันอย่างสิ้นเชิง เนื่องจากการจัดการ Clock/Chip Enable

**คำตอบที่ถูกต้อง:** **ข้อ ข.**
