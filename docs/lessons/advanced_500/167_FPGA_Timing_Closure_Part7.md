## 1. ทฤษฎีวิศวกรรมเชิงลึก (高度なエンジニアリング理論)

### 1.1 ความสัมพันธ์ระหว่างระดับชั้นลอจิก (Logic Levels) กับความถี่สูงสุด $F_{max}$
ในสถาปัตยกรรม FPGA ระดับชั้นลอจิก (Logic Levels หรือ LUT Depth) คือจำนวนก้อน Look-Up Table (LUT) และวงจรมัลติเพล็กเซอร์ที่สัญญาณข้อมูลต้องเดินทางผ่าน ระหว่างรีจิสเตอร์ต้นทาง (Launch FF) ไปยังรีจิสเตอร์ปลายทาง (Capture FF)

ความล่าช้าสะสมของเส้นทางข้อมูล (Data Path Delay) ประกอบด้วย 2 ส่วนที่ขยายตัวตามจำนวนระดับชั้นลอจิก ($L$):

$$T_{data\_path} = \sum_{k=1}^{L} T_{lut\_k} + \sum_{k=1}^{L+1} T_{net\_k}$$

```
                ความล่าช้าในแต่ละระดับชั้นลอจิก (1 LOGIC LEVEL)
                
     ┌───────────┐      ┌───────────┐      ┌───────────┐
     │ LUT Level │ ───► │ Interconn │ ───► │ LUT Level │ ───► ...
     │  (T_lut)  │      │ Net(T_net)│      │  (T_lut)  │
     └───────────┘      └───────────┘      └───────────┘
     |<------- 1 Logic Level Delay: ~0.40ns ถึง ~0.55ns ------->|
```

#### กฎเกณฑ์เชิงประจักษ์ในชิป UltraScale/UltraScale+ (16nm FinFET):
* ความล่าช้าภายในตัวเกต LUT6: $T_{lut} \approx 0.050\text{ ns} - 0.090\text{ ns}$
* ความล่าช้าของสายส่ง Interconnect เฉลี่ยในแต่ละชั้น: $T_{net} \approx 0.350\text{ ns} - 0.450\text{ ns}$
* **ความล่าช้าเฉลี่ยต่อ 1 Logic Level:** $\Delta T_{level} \approx 0.450\text{ ns} - 0.550\text{ ns}$

#### การคำนวณจำนวน Logic Levels สูงสุดที่ยอมรับได้ ($L_{max}$):
กำหนดให้ $T_{overhead} = T_{cko} + T_{setup} + T_{uncertainty} - \Delta T_{skew} \approx 0.750\text{ ns}$
งบประมาณเวลาสำหรับลอจิก:
$$T_{logic\_budget} = T_{period} - T_{overhead}$$
$$L_{max} = \left\lfloor \frac{T_{period} - T_{overhead}}{\Delta T_{level}} \right\rfloor$$

```
          ตารางขีดจำกัด LOGIC LEVELS สูงสุดตามความถี่เป้าหมาย
          
   ความถี่เป้าหมาย (Fclk)   คาบเวลา (Tperiod)   Logic Budget   Logic Levels สูงสุด (Lmax)
   --------------------   -----------------   ------------   -------------------------
   200 MHz                5.000 ns            4.250 ns       7 ถึง 8 ระดับ
   300 MHz                3.333 ns            2.583 ns       4 ถึง 5 ระดับ
   400 MHz                2.500 ns            1.750 ns       3 ถึง 4 ระดับ (วิกฤต!)
   500 MHz                2.000 ns            1.250 ns       2 ถึง 3 ระดับ (ขีดจำกัดสูงสุด!)
   600 MHz                1.667 ns            0.917 ns       1 ถึง 2 ระดับ (ห้ามเกิน 2 LUTs!)
```

### 1.2 ทฤษฎีการปรับสมดุลรีจิสเตอร์ (Register Retiming Physics)

**Retiming** เป็นขั้นตอนวิธีการแปลงโครงสร้างวงจรทางคณิตศาสตร์ (อิงจากทฤษฎี Leiserson-Saxe Graph Theory) ซึ่งทำหน้าที่เคลื่อนย้ายตำแหน่งของฟลิปฟล็อปข้ามผ่านเกตคอมบิเนชัน โดยที่ฟังก์ชันการทำงานอินพุต-เอาต์พุตของวงจรยังคงเดิม $100\%$:

```
                   กลไกการทำ REGISTER RETIMING
                   
   [ ก่อนทำ Retiming: ไร้สมดุล (Unbalanced) ]
   FF_A ──► [ LUT 1 ] ──► [ LUT 2 ] ──► [ LUT 3 ] ──► [ LUT 4 ] ──► FF_B ──► [ LUT 5 ] ──► FF_C
   |<---------------- 4 Logic Levels (1.8ns) ---------------->|   |<-- 1 Level (0.5ns) ->|
   ===> Critical Path อยู่ที่ช่วง A -> B (จำกัดความถี่ที่ 300MHz)
   
   [ หลังทำ Retiming: ปรับสมดุลอย่างชาญฉลาด (Balanced) ]
   FF_A ──► [ LUT 1 ] ──► [ LUT 2 ] ──► FF_B_RET ──► [ LUT 3 ] ──► [ LUT 4 ] ──► [ LUT 5 ] ──► FF_C
   |<--------- 2 Logic Levels (0.9ns) -------->|   |<--------- 3 Logic Levels (1.3ns) -------->|
   ===> ความถี่ Fmax พุ่งทะยานขึ้นสู่ 500MHz ทันที โดยไม่ต้องแก้โค้ด RTL แม้แต่บรรทัดเดียว!
```

#### สองรูปแบบของ Retiming:
1. **Forward Retiming:** ดันฟลิปฟล็อปจากด้านหน้าข้ามเกตคอมบิเนชันไปไว้ที่ด้านหลัง
2. **Backward Retiming:** ดึงฟลิปฟล็อปจากด้านหลังถอยข้ามเกตกลับมาไว้ที่ด้านหน้า

### 1.3 สิ่งกีดขวางที่ทำลายกระบวนการ Retiming (The Retiming Inhibitors)

> [!CRITICAL]
> **ทำไม Vivado จึงปฏิเสธไม่ยอม Retiming?:**  
> ซอฟต์แวร์ Synthesis จะไม่สามารถทำการ Retiming ได้ หากวงจรติดเงื่อนไขต้องห้ามทางฮาร์ดแวร์ 4 ประการ:

```
                  4 ตัวการทำลาย RETIMING (RETIMING INHIBITORS)
                  
   1. Asynchronous Reset : การเขียน always @(posedge clk or negedge rst_n)
                           ทำให้ฟลิปฟล็อปติดค้างสถานะ Asynchronous Clear
                           เครื่องมือไม่สามารถการันตีสถานะเริ่มต้นข้ามเกตได้ ===> RETIMING ถูกปิด!
   
   2. DONT_TOUCH / KEEP   : แอตทริบิวต์ล็อกเน็ตหรือเซลล์ที่ตกค้างจากการดีบั๊ก
   
   3. Complex Clock Enable: สัญญาณ Enable ที่มีเงื่อนไขไขว้กันข้ามฟลิปฟล็อป
   
   4. Multi-Fanout Latch  : สัญญาณที่แตกสาขาไปยังวงจรอื่นที่ไม่สามารถย้ายพร้อมกันได้
```

#### กฎเหล็ก: เปลี่ยนเป็น Synchronous Reset เพื่อเปิดประตู Retiming
เพื่อให้ Synthesis สามารถเกลี่ยฟลิปฟล็อปได้อย่างอิสระ **ต้องใช้ Synchronous Reset เท่านั้น**:

```verilog
// แม่แบบที่รองรับ Register Retiming 100%
always @(posedge clk) begin
    if (sync_rst) begin
        q <= '0;
    end else begin
        q <= d;
    end
end
```

### 1.4 การตัดทอนสายโซ่แครี่และการแยกส่วน DSP (Carry Chain & DSP Pipelining)

#### 1. การแบ่งสายโซ่แครี่ของตัวบวกกว้าง (Carry Chain Splitting):
วงจรบวกขนาดใหญ่ (เช่น 64-bit หรือ 128-bit Adders) ถูกสังเคราะห์ลงในบล็อก `CARRY8` ในคอลัมน์แนวตั้ง:
* สัญญาณ Carry ต้องวิ่งทะลุผ่านเซลล์ต่อเซลล์แบบอนุกรม (Carry Ripple)
* ความล่าช้าของ Carry Chain 64 บิต: $T_{carry} \approx 1.4\text{ ns} - 1.8\text{ ns}$ (กินเวลาเกือบทั้งคาบเวลาของ 500MHz!)
* **วิธีแก้:** แบ่งตัวบวกออกเป็น $32\text{ บิต} + 32\text{ บิต}$ พร้อมแทรก Pipeline Register คั่นตรงบิต Carry-Out:

```
                    การแบ่ง CARRY CHAIN เป็น 2 สเตจ PIPELINE
                    
   Cycle 1: [ Adder 32-bit ต่ำ ] ──► บันทึกผลรวม [31:0] และ [ Carry_Out_Reg ]
   Cycle 2: [ Adder 32-bit สูง ] ◄── ดึง Carry_Out_Reg มาบวกต่อ ──► บันทึกผลรวม [63:32]
   ===> ตัดความล่าช้าของ Carry Chain ลงครึ่งหนึ่งในพริบตา!
```

#### 2. การเปิดใช้ไปป์ไลน์ภายในบล็อก DSP48E2:
ฮาร์ดแวร์ DSP48E2 มีฟลิปฟล็อปฝังตัวอยู่ภายในตัวถังซิลิคอน (Dedicated Hard Registers):
* `AREG / BREG`: อินพุตไปป์ไลน์ (เลือกระดับ 1 หรือ 2 สเตจ)
* `MREG`: ไปป์ไลน์หลังวงจรคูณ (Multiplier Output Register)
* `PREG`: เอาต์พุตไปป์ไลน์ (Accumulator Output Register)

```
              การเปรียบเทียบ FMAX ของ DSP48E2 ตามการเปิดใช้ REGISTERS
              
   การกำหนดค่า (Pipeline Config)           Fmax สูงสุด    นัยสำคัญทางวิศวกรรม
   -----------------------------          -----------    -------------------
   ไม่เปิดเลย (Pure Combinational)          ~ 220 MHz      ช้ามาก เกิดคอขวดทันที
   เปิดเฉพาะ PREG = 1                     ~ 380 MHz      ระดับปานกลาง
   เปิดครบสมบูรณ์ (AREG=2, MREG=1, PREG=1)  ~ 650 MHz      ความเร็วระดับสูงสุดของซิลิคอน!
```

## 2. ทริคหน้างาน OJT แบบ Step-by-Step (現場の実践テクニック)

### 2.1 กรณีศึกษาความล้มเหลวหน้างาน: หน่วยประมวลผลวิดีโอ 4K120p ติดลบไทม์มิ่งจาก `DONT_TOUCH` ตกค้าง (4K120p Motion Estimator Retiming Failure)

```
+----------------------------------------------------------------------------------------------------+
| กรณีศึกษาความล้มเหลวหน้างาน (現場の失敗事例)                                                                 |
| เหตุการณ์: โมดูลคำนวณการเคลื่อนไหวของภาพวิดีโอ 4K 120fps (Motion Estimation SAD Tree) บน UltraScale+         |
| อาการ: ต้องการความถี่ทำงานที่ 300MHz (คาบเวลา 3.33ns) แต่ Vivado รายงาน Setup Violation WNS = -2.15ns         |
|        รายงานระบุว่าเส้นทาง Critical Path มีระดับชั้นลอจิกสูงถึง 9 ระดับ (9 LUT Levels) กองรวมอยู่ในสเตจเดียว |
|        ทั้งๆ ที่วิศวกรใส่ไปป์ไลน์รีจิสเตอร์ไว้ 3 ขั้น และเปิดออปชัน -retiming ในสคริปต์การสังเคราะห์แล้ว!       |
+----------------------------------------------------------------------------------------------------+
```

#### การวิเคราะห์หาสาเหตุรากเหง้าด้วยหลักการ 5 Whys (5 Whys Root Cause Analysis):

1. **ทำไมโมดูล Motion Estimation จึงติดลบค่า Setup Slack ถึง -2.15ns?**  
   *คำตอบ:* มีลอจิก LUT เรียงต่อกันถึง 9 ระดับบนเส้นทางคำนวณผลต่างพิกเซล (Sum of Absolute Differences - SAD)

2. **ทำไมจึงมีลอจิกกองอยู่ถึง 9 ระดับ ทั้งที่มีการแทรกไปป์ไลน์รีจิสเตอร์ไว้ 3 ขั้น?**  
   *คำตอบ:* ลอจิกทั้งหมด 9 ระดับไปกระจุกตัวอยู่ระหว่างรีจิสเตอร์สเตจที่ 1 กับสเตจที่ 2 ในขณะที่ระหว่างสเตจที่ 2 กับสเตจที่ 3 กลับไม่มีลอจิกเลย (0 Levels - ต่อตรงเป็นสายเปล่า)

3. **ทำไมเครื่องมือ Vivado Synthesis จึงไม่เฉลี่ยลอจิกข้ามรีจิสเตอร์ ทั้งที่เปิดออปชัน `-retiming`?**  
   *คำตอบ:* เครื่องมือรายงานคำเตือนในล็อกไฟล์ว่า:  
   `INFO: [Synth 8-5845] Not retiming register 'sad_stage2_reg' because it has DONT_TOUCH attribute.`

4. **ทำไมรีจิสเตอร์สเตจที่ 2 จึงติดแอตทริบิวต์ `DONT_TOUCH`?**  
   *คำตอบ:* ในช่วงสัปดาห์ก่อนหน้า วิศวกรนำบอร์ดไปดีบั๊กด้วย Integrated Logic Analyzer (ILA) แล้วสัญญาณถูก Optimize หายไป จึงใส่ `(* DONT_TOUCH = "TRUE" *)` ไว้บนคลาสของโมดูลเพื่อบังคับให้เครื่องมือไม่ลบสัญญาณทิ้ง

5. **ทำไมแอตทริบิวต์สำหรับดีบั๊กจึงหลุดรอดมาถึงเวอร์ชัน Release?**  
   *คำตอบ:* ขาดขั้นตอนการทำ Code Review และไม่มีการตรวจสอบรายงานข้อยกเว้นก่อนรวมโค้ดเข้าสู่ Master Branch ทำให้คำสั่ง `DONT_TOUCH` กีดขวางกลไก Retiming จนระบบพังทลาย!

### 2.3 คู่มือปฏิบัติงาน SOP: การวิเคราะห์และปรับโครงสร้างลอจิกให้ผ่านไทม์มิ่ง (Zero-Depth SOP)

#### สเต็ปที่ 1: ตรวจสอบการกระจายตัวของระดับชั้นลอจิกด้วย `report_design_analysis`
* รันคำสั่งวิเคราะห์โครงสร้างลอจิกหลัง Synthesis หรือ Placement:
  `report_design_analysis -logic_level_distribution -file logic_dist.rpt`
* ตรวจสอบตารางการกระจายตัว หากพบเส้นทางใดที่มี Logic Depth เกินกว่า **$4\text{ ระดับ}$** สำหรับความถี่ $\ge 350\text{ MHz}$ ให้ระบุชื่อโมดูลเพื่อทำการปรับปรุงทันที

#### สเต็ปที่ 2: ตรวจสอบและกำจัดตัวกีดขวาง Retiming ทั้งหมด
* ค้นหาและลบแอตทริบิวต์ `DONT_TOUCH` และ `KEEP` ที่หลงเหลือจากการดีบั๊ก:
  `grep -rn "DONT_TOUCH" ./rtl/`
* แปลงกระบวนการ Reset ของโมดูลคำนวณทั้งหมดให้เป็น **Synchronous Reset** เพื่อเปิดทางให้เอนจิน Retiming ทำงานได้อย่างอิสระ $100\%$

#### สเต็ปที่ 3: เปิดใช้งานคำสั่ง Retiming ใน Vivado Synthesis
* เปิดออปชันการปรับสมดุลรีจิสเตอร์ในขั้นตอนการสังเคราะห์:

```tcl
# เปิดใช้งาน Retiming ใน Vivado Synthesis
synth_design -top top_module -part xcku5p-ffvb676-2-e -retiming
```

#### สเต็ปที่ 4: การเปิดใช้ Pipelining ภายในบล็อก DSP และ Carry Chains
* ตรวจสอบให้แน่ใจว่าการคูณสะสมทั้งหมดใช้คุณสมบัติของ DSP48E2 อย่างเต็มประสิทธิภาพ โดยมีค่า Latency ให้อย่างน้อย $3\text{ ไซเคิล}$ (Input, Mult, Output Registers)
* แยกตัวบวกขนาดกว้างกว่า 32 บิตออกเป็นส่วนย่อยแบบ Pipelined Carry

## 3. คำศัพท์และประโยคภาษาญี่ปุ่นสำหรับตรวจแบบ (検図 - Kenzu)

### 3.1 ตารางคำศัพท์เทคนิคเฉพาะทาง

| คำศัพท์คันジ / คาตากานะ | คำอ่าน (Romaji) | ความหมายทางวิศวกรรม (Thai / English) |

| **前方リタイミング** | Zenpou Ritaimingu | Forward Retiming (การย้ายรีจิสเตอร์ไปข้างหน้า) |
| **後方リタイミング** | Kouhou Ritaimingu | Backward Retiming (การย้ายรีจิสเตอร์ถอยหลัง) |

## 4. ควิซวิเคราะห์ปัญหาระดับวิศวกรอาวุโส (上級技術クイズ)

### ข้อที่ 1: การคำนวณจำนวน Logic Levels สูงสุดที่ยอมให้มีได้ตามงบประมาณไทม์มิ่ง

#### โจทย์คำถาม:
ในโมดูลประมวลผลเครือข่ายความเร็วสูง สัญญาณนาฬิกาถูกกำหนดให้ทำงานที่ความถี่ $f_{clk} = 450\text{ MHz}$ ($T_{period} = 2.222\text{ ns}$) บนชิป UltraScale+ (Speed Grade -2)

พารามิเตอร์ทางกายภาพของวงจรที่สภาวะ Slow Corner มีดังนี้:
* ค่า Clock-to-Out สูงสุด: $T_{cko} = 0.320\text{ ns}$
* ค่า Setup Time ของฟลิปฟล็อป: $T_{setup} = 0.110\text{ ns}$
* ค่า Clock Uncertainty รวม Jitter: $T_{uncertainty} = 0.090\text{ ns}$
* ค่า Clock Skew สุทธิเป็นลบ: $\Delta T_{skew} = -0.150\text{ ns}$ (มาถึง Capture FF ก่อน)
* ความล่าช้าเฉลี่ยของลอจิกเกตต่อ 1 LUT Level: $T_{lut} = 0.075\text{ ns}$
* ความล่าช้าเฉลี่ยของสายส่ง Interconnect ต่อ 1 ระดับชั้น: $T_{net} = 0.345\text{ ns}$
* สายส่งระดับสุดท้ายจาก LUT ตัวสุดท้ายเข้าสู่ขา $D$ ของ Capture FF: $T_{net\_final} = 0.280\text{ ns}$

จงคำนวณหา:
1. งบประมาณเวลาสูงสุดที่เหลืออยู่สำหรับวงจร Combinational Logic และสายส่ง ($T_{data\_budget}$)
2. จำนวนระดับชั้นของลอจิก (Logic Levels: $L_{max}$) สูงสุดที่จะยอมให้มีได้ระหว่างสองฟลิปฟล็อปนี้ โดยไม่ทำให้เกิด Setup Violation

* ก. $T_{data\_budget} = 1.552\text{ ns}$, $L_{max} = 3\text{ ระดับชั้น}$
* ข. $T_{data\_budget} = 1.852\text{ ns}$, $L_{max} = 4\text{ ระดับชั้น}$
* ค. $T_{data\_budget} = 1.552\text{ ns}$, $L_{max} = 2\text{ ระดับชั้น}$
* ง. $T_{data\_budget} = 1.252\text{ ns}$, $L_{max} = 2\text{ ระดับชั้น}$

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: คำนวณงบประมาณเวลาสูงสุดสำหรับ Data Path ($T_{data\_budget}$):**
จากสมการ Setup Slack:
$$\text{Slack}_{setup} = T_{period} + \Delta T_{skew} - (T_{cko} + T_{data\_path} + T_{setup} + T_{uncertainty}) \ge 0$$
จัดรูปเพื่อหา $T_{data\_path}$ สูงสุดที่ยอมรับได้:
$$T_{data\_budget} = T_{period} + \Delta T_{skew} - T_{cko} - T_{setup} - T_{uncertainty}$$
แทนค่าตัวแปร:
$$T_{data\_budget} = 2.222\text{ ns} + (-0.150\text{ ns}) - 0.320\text{ ns} - 0.110\text{ ns} - 0.090\text{ ns}$$
$$T_{data\_budget} = 2.072\text{ ns} - 0.520\text{ ns} = 1.552\text{ ns}$$

**ขั้นตอนที่ 2: คำนวณความล่าช้าต่อ 1 ระดับชั้นลอจิก ($\Delta T_{level}$):**
ในแต่ละระดับชั้น ประกอบด้วยตัวเกต LUT และสายส่งระหว่างเกต:
$$\Delta T_{level} = T_{lut} + T_{net} = 0.075\text{ ns} + 0.345\text{ ns} = 0.420\text{ ns/level}$$

**ขั้นตอนที่ 3: คำนวณจำนวนระดับชั้นสูงสุด ($L_{max}$):**
ความล่าช้ารวมของ $L$ ระดับชั้น:
$$T_{data\_path} = (L \times \Delta T_{level}) + T_{net\_final} \le T_{data\_budget}$$
$$(L \times 0.420\text{ ns}) + 0.280\text{ ns} \le 1.552\text{ ns}$$
$$L \times 0.420\text{ ns} \le 1.552\text{ ns} - 0.280\text{ ns} = 1.272\text{ ns}$$
$$L \le \frac{1.272\text{ ns}}{0.420\text{ ns}} \approx 3.028$$
ปัดลงเป็นจำนวนเต็ม:
$$L_{max} = 3\text{ ระดับชั้น}$$

หมายความว่า ที่ความถี่ $450\text{ MHz}$ บนเส้นทางที่มี Negative Skew วงจรจะทนทานต่อลอจิกได้ **สูงสุดเพียง 3 LUT Levels เท่านั้น!** หากมีระดับที่ 4 ($4 \times 0.42 + 0.28 = 1.96\text{ ns} > 1.552\text{ ns}$) จะติดลบ Setup Violation ทันที!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** งบประมาณ $1.552\text{ ns}$ และขีดจำกัด $L_{max} = 3$ ระดับชั้น ถูกต้องตามหลัก STA $100\%$
* **ข้อ ข. ไม่ถูกต้อง:** ลืมหักค่า Negative Skew (คิดว่ามีงบ $1.852\text{ ns}$)
* **ข้อ ค. ไม่ถูกต้อง:** ประมาณการจำนวนระดับชั้นต่ำเกินไป
* **ข้อ ง. ไม่ถูกต้อง:** คำนวณงบประมาณเวลาผิดพลาด

**คำตอบที่ถูกต้อง:** **ข้อ ก.**

### ข้อที่ 2: การวิเคราะห์การแบ่งสายโซ่แครี่ 64 บิต (Carry Chain Pipelining Improvement)

#### โจทย์คำถาม:
ในโมดูลคำนวณตำแหน่งพิกัดดาวเทียม วงจรประกอบด้วยตัวบวกขนาดกว้าง $64\text{ bits}$ โดยสัญญาณ Carry ถูกส่งผ่านสายโซ่ฮาร์ดแวร์ `CARRY8` ต่อเนื่องกันทั้งหมด $8\text{ บล็อก}$ ในแนวตั้ง

พารามิเตอร์ของวงจรบวก:
* ความล่าช้าในการสร้างสัญญาณ Carry เริ่มต้นและเดินทางผ่าน CARRY8 ทั้ง 8 บล็อก: $T_{carry\_chain} = 1.680\text{ ns}$
* ความล่าช้าของลอจิกอินพุตและสายส่งก่อนเข้าตัวบวก: $T_{in\_logic} = 0.850\text{ ns}$
* ความล่าช้าของสายส่งออกจากตัวบวกไปยังฟลิปฟล็อปปลายทาง: $T_{out\_net} = 0.420\text{ ns}$
* ค่า $T_{overhead} = T_{cko} + T_{setup} + T_{uncertainty} = 0.450\text{ ns}$
* ความถี่เป้าหมายของระบบคือ $f_{clk} = 400\text{ MHz}$ ($T_{period} = 2.500\text{ ns}$)

หากวิศวกรทำการแบ่งตัวบวกออกเป็นสองส่วน: **32 บิตต่ำ** และ **32 บิตสูง** โดยแทรก Pipeline Register คั่นกลาง 1 ไซเคิลเพื่อเก็บค่า Carry-Out จากส่วนต่ำไปป้อนให้ส่วนสูง:
* แต่ละส่วนมี CARRY8 เพียง 4 บล็อก ทำให้ความล่าช้าของ Carry Chain ในแต่ละสเตจลดลงเหลือ $T_{carry\_split} = 0.840\text{ ns}$
* พารามิเตอร์ $T_{in\_logic}$, $T_{out\_net}$, และ $T_{overhead}$ กระจายตัวเฉลี่ยเท่ากันในทั้งสองสเตจ

จงคำนวณหา:
1. ค่า Setup Slack เดิมของตัวบวก 64 บิตก่อนแบ่งสเตจ ($\text{Slack}_{orig}$)
2. ค่า Setup Slack ใหม่ในสเตจที่วิกฤตที่สุดหลังการแบ่ง Pipelined Split ($\text{Slack}_{new}$)
3. สรุปผลว่าการแบ่ง Carry Chain ช่วยกู้ชีพวงจรได้สำเร็จหรือไม่?

* ก. $\text{Slack}_{orig} = -0.900\text{ ns}$, $\text{Slack}_{new} = -0.060\text{ ns}$, ยังไม่ผ่าน
* ข. $\text{Slack}_{orig} = -0.900\text{ ns}$, $\text{Slack}_{new} = +0.380\text{ ns}$, กู้ชีพสำเร็จผ่านเกณฑ์!
* ค. $\text{Slack}_{orig} = -0.480\text{ ns}$, $\text{Slack}_{new} = +0.380\text{ ns}$, กู้ชีพสำเร็จผ่านเกณฑ์!
* ง. $\text{Slack}_{orig} = -0.900\text{ ns}$, $\text{Slack}_{new} = +0.760\text{ ns}$, กู้ชีพสำเร็จผ่านเกณฑ์!

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: คำนวณ Setup Slack เดิมก่อนแบ่งสเตจ:**
ความล่าช้ารวมของ Data Path เดิม:
$$T_{data\_orig} = T_{in\_logic} + T_{carry\_chain} + T_{out\_net} = 0.850\text{ ns} + 1.680\text{ ns} + 0.420\text{ ns} = 2.950\text{ ns}$$
คำนวณ Setup Slack เดิม:
$$\text{Slack}_{orig} = T_{period} - T_{overhead} - T_{data\_orig} = 2.500\text{ ns} - 0.450\text{ ns} - 2.950\text{ ns} = 2.050\text{ ns} - 2.950\text{ ns} = -0.900\text{ ns}$$
เดิมติดลบค่า Setup Slack ถึง $900\text{ ps}$!

**ขั้นตอนที่ 2: คำนวณ Setup Slack ใหม่หลังแบ่ง 32 บิต:**
ในแต่ละสเตจ ความล่าช้าของ Carry ลดลงเหลือ $0.840\text{ ns}$:
สมมติว่างบประมาณของลอจิกอินพุตและเอาต์พุตในสเตจที่ยาวที่สุดประมาณ $T_{in\_split} + T_{out\_split} \approx 0.830\text{ ns}$:
ความล่าช้าใหม่ของ Data Path:
$$T_{data\_new} = 0.830\text{ ns} + 0.840\text{ ns} = 1.670\text{ ns}$$
คำนวณ Setup Slack ใหม่:
$$\text{Slack}_{new} = T_{period} - T_{overhead} - T_{data\_new} = 2.500\text{ ns} - 0.450\text{ ns} - 1.670\text{ ns} = 2.050\text{ ns} - 1.670\text{ ns} = +0.380\text{ ns}$$

การแบ่ง Carry Chain ออกเป็น 2 สเตจช่วยพลิกค่า Slack จากติดลบ **$-0.900\text{ ns}$** กลับมาเป็นบวก **$+0.380\text{ ns}$** ทำให้ระบบผ่าน Timing ที่ 400MHz ได้อย่างสวยงาม!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ไม่ถูกต้อง:** Slack ใหม่คำนวณผิดพลาด
* **ข้อ ข. ถูกต้องสมบูรณ์แบบ:** $\text{Slack}_{orig} = -0.900\text{ ns}$ และ $\text{Slack}_{new} = +0.380\text{ ns}$ ถูกต้องตรงตามหลักคณิตศาสตร์
* **ข้อ ค. ไม่ถูกต้อง:** Slack เดิมคำนวณต่ำกว่าความเป็นจริง
* **ข้อ ง. ไม่ถูกต้อง:** Slack ใหม่สูงเกินจริง

**คำตอบที่ถูกต้อง:** **ข้อ ข.**

### ข้อที่ 3: การวิเคราะห์ผลลัพธ์ของการเปิดใช้ Pipeline Registers ภายใน DSP48E2

#### โจทย์คำถาม:
ในสถาปัตยกรรมตัวกรองสัญญาณดิจิทัล บล็อกฮาร์ดแวร์ `DSP48E2` ทำหน้าที่คูณสะสม ($P = A \cdot B + C$) โดยทำงานที่ความถี่ $f_{clk} = 500\text{ MHz}$ ($T_{period} = 2.000\text{ ns}$)

พารามิเตอร์ความล่าช้าภายในของ DSP48E2:
* ความล่าช้าของวงจรคูณภายใน (Multiplier Core Array): $T_{mult} = 1.650\text{ ns}$
* ความล่าช้าของวงจรบวกสะสมภายใน (Accumulator Core): $T_{accum} = 1.100\text{ ns}$
* ความล่าช้าของสายส่งภายนอกเชื่อมต่อไปยังรีจิสเตอร์ปลายทาง: $T_{ext\_net} = 0.450\text{ ns}$
* ค่า Clock-to-Out และ Setup Time รวม: $T_{cell\_overhead} = 0.250\text{ ns}$

หากวิศวกรเปรียบเทียบการคอนฟิกรีจิสเตอร์ภายใน DSP สองรูปแบบ:
* **รูปแบบที่ 1:** ปิดรีจิสเตอร์ภายในทั้งหมด (`MREG = 0`, `PREG = 0`) โดยใช้ฟลิปฟล็อปภายนอกใน Fabric รับผลลัพธ์
* **รูปแบบที่ 2:** เปิดรีจิสเตอร์ภายในครบทุกจุด (`MREG = 1`, `PREG = 1`)

จงวิเคราะห์ว่า:
1. ในรูปแบบที่ 1 ความล่าช้าของ Critical Path มีค่าเท่าใด และผ่าน Timing ที่ 500MHz หรือไม่?
2. ในรูปแบบที่ 2 ความล่าช้าของสเตจที่ยาวที่สุดภายใน DSP มีค่าเท่าใด และผ่าน Timing ที่ 500MHz หรือไม่?

* ก.
  * รูปแบบที่ 1: $T_{path1} = 3.450\text{ ns}$ (ไม่ผ่าน Timing ที่ 500MHz!)
  * รูปแบบที่ 2: $T_{path2} = 1.650\text{ ns}$ (ผ่าน Timing ที่ 500MHz ฉลุย!)
* ข.
  * รูปแบบที่ 1: $T_{path1} = 2.200\text{ ns}$ (ไม่ผ่าน Timing ที่ 500MHz)
  * รูปแบบที่ 2: $T_{path2} = 1.950\text{ ns}$ (ผ่าน Timing ที่ 500MHz)
* ค.
  * รูปแบบที่ 1: $T_{path1} = 3.450\text{ ns}$ (ไม่ผ่าน Timing)
  * รูปแบบที่ 2: $T_{path2} = 2.150\text{ ns}$ (ไม่ผ่าน Timing)
* ง.
  * รูปแบบที่ 1: $T_{path1} = 1.650\text{ ns}$ (ผ่าน Timing)
  * รูปแบบที่ 2: $T_{path2} = 0.850\text{ ns}$ (ผ่าน Timing)

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: วิเคราะห์รูปแบบที่ 1 (ปิด MREG=0, PREG=0):**
สัญญาณต้องวิ่งทะลุผ่านทั้งตัวคูณและตัวสะสมรวดเดียวในไซเคิลเดียว:
$$T_{path1} = T_{mult} + T_{accum} + T_{ext\_net} + T_{cell\_overhead}$$
$$T_{path1} = 1.650\text{ ns} + 1.100\text{ ns} + 0.450\text{ ns} + 0.250\text{ ns} = 3.450\text{ ns}$$
เนื่องจากคาบเวลา $T_{period} = 2.000\text{ ns}$ ดังนั้นค่า $3.450\text{ ns}$ จึงติดลบอย่างรุนแรง ($\text{Slack} = 2.000 - 3.450 = -1.450\text{ ns}$)!

**ขั้นตอนที่ 2: วิเคราะห์รูปแบบที่ 2 (เปิด MREG=1, PREG=1):**
การเปิดใช้ทั้งสองรีจิสเตอร์ทำให้เส้นทางถูกตัดขาดออกจากกันเป็น 2 ช่วงอิสระ:
* **ช่วงที่ 1 (ระหว่างอินพุตกับ MREG):** มีเฉพาะตัวคูณ
  $$T_{stage1} = T_{mult} = 1.650\text{ ns}$$
* **ช่วงที่ 2 (ระหว่าง MREG กับ PREG):** มีเฉพาะตัวบวกสะสม
  $$T_{stage2} = T_{accum} = 1.100\text{ ns}$$
* **ช่วงที่ 3 (จาก PREG ออกภายนอก):**
  $$T_{stage3} = T_{ext\_net} + T_{cell\_overhead} = 0.450\text{ ns} + 0.250\text{ ns} = 0.700\text{ ns}$$

สเตจที่ยาวที่สุดคือช่วงที่ 1 ($T_{stage1} = 1.650\text{ ns}$):
เปรียบเทียบกับคาบเวลา:
$$T_{stage1} (1.650\text{ ns}) < T_{period} (2.000\text{ ns})$$
Timing Slack กลายเป็นบวก ($\text{Slack} \approx 2.000 - 1.650 = +0.350\text{ ns}$) ผ่านการวิเคราะห์ไทม์มิ่งที่ 500MHz ได้อย่างราบรื่น!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** ตัวเลข $3.450\text{ ns}$ (ไม่ผ่าน) และ $1.650\text{ ns}$ (ผ่าน) ถูกต้องตรงตามพารามิเตอร์ฮาร์ดแวร์ DSP48E2 $100\%$
* **ข้อ ข., ค., และ ง. ไม่ถูกต้อง:** คำนวณความล่าช้าสะสมและสเตจภายในผิดพลาด

**คำตอบที่ถูกต้อง:** **ข้อ ก.**
