## 1. ทฤษฎีวิศวกรรมเชิงลึก (高度なエンジニアリング理論)

### 1.1 เกณฑ์ชี้วัดเชิงปริมาณของคุณภาพผลลัพธ์ (Quality of Results - QOR Sign-Off Metrics)
ขั้นตอนสุดท้ายของการออกแบบ FPGA คือการลงนามอนุมัติปล่อยแบบเพื่อการผลิตจริง (**Timing Closure Sign-Off**) ในระดับอุตสาหกรรม การที่รายงานสรุปแสดงเพียงว่า *"Timing Met"* ไม่ได้เป็นหลักประกันว่าชิปจะทำงานได้อย่างปลอดภัยตลอดอายุการใช้งาน

วิศวกรระดับ Senior ต้องใช้เกณฑ์ชี้วัดเชิงปริมาณที่เข้มงวด 4 ประการ (The 4 Zero-Violation Criteria) ร่วมกับ **Timing Margin Guardband**:

```
                  4 เกณฑ์ชี้วัดพื้นฐานในการ SIGN-OFF (ZERO-VIOLATION)
                  
   1. WNS (Worst Negative Slack - Setup) >= 0.000 ns   (ห้ามติดลบเด็ดขาด)
   2. TNS (Total Negative Slack - Setup)  = 0.000 ns   (ผลรวมติดลบต้องเป็นศูนย์)
   3. WHS (Worst Hold Slack - Hold)       >= 0.000 ns   (ห้ามติดลบเด็ดขาด)
   4. THS (Total Hold Slack - Hold)       = 0.000 ns   (ผลรวมติดลบต้องเป็นศูนย์)
```

#### เกณฑ์ระยะเผื่อความปลอดภัยขั้นต่ำตามประเภทภารกิจ (Mission Profile Guardbands):
ลำพังเพียงค่า $Slack = +0.001\text{ ns}$ ไม่เพียงพอต่อการส่งมอบงาน วิศวกรต้องกำหนดค่า **Design Margin** ขั้นต่ำตามระดับความวิกฤตของระบบ:

| ระดับภารกิจ (Mission Profile) | มาตรฐานสากลที่ควบคุม | WNS Margin ขั้นต่ำ | WHS Margin ขั้นต่ำ |
| :--- | :--- | :--- | :--- |
| **Commercial / Consumer** | ทั่วไป (Consumer Electronics) | $\ge +0.100\text{ ns}$ | $\ge +0.030\text{ ns}$ |
| **Industrial / Telecom** | IEC 61508 / Telcordia | $\ge +0.150\text{ ns}$ | $\ge +0.050\text{ ns}$ |
| **Automotive (ยานยนต์)** | **ISO 26262 (ASIL-B ถึง ASIL-D)** | $\ge +0.250\text{ ns}$ | $\ge +0.060\text{ ns}$ |
| **Aerospace & Defense (การบิน)**| **DO-254 (DAL-B ถึง DAL-A)** | $\ge +0.400\text{ ns}$ | $\ge +0.100\text{ ns}$ |

### 1.2 ฟิสิกส์ของการเสื่อมสภาพตามอายุการใช้งานและการตกของแรงดันไฟฟ้า (Aging Degradation & Voltage Droop Physics)

ชิปซิลิคอนไม่ได้รักษาความเร็วคงที่ตลอดไป ทรานซิสเตอร์ FinFET ระดับนาโนเมตร (16nm, 7nm) จะค่อยๆ ทำงานช้าลงเมื่อเวลาผ่านไปหลายปี เนื่องจากปรากฏการณ์ทางกายภาพของสารกึ่งตัวนำ:

```
                   กลไกการเสื่อมสภาพของทรานซิสเตอร์ (SILICON AGING)
                   
     [ 1. Bias Temperature Instability (BTI: NBTI / PBTI) ]
     สนามไฟฟ้าแรงสูงร่วมกับความร้อนเหนี่ยวนำให้เกิด Trap States ในชั้น Gate Dielectric
     ===> แรงดันขีดเริ่ม (Threshold Voltage: Vth) ขยับสูงขึ้นเรื่อยๆ ตามเวลา!
     
     [ 2. Hot Carrier Injection (HCI) ]
     อิเล็กตรอนพลังงานสูงพุ่งชนและฝังตัวในชั้นออกไซด์ใกล้ Drain Junction
     ===> กระแสขับอิ่มตัว (Saturation Current: Idsat) ลดลง ทรานซิสเตอร์สลับช้าลง!
```

#### 1. การคำนวณการหน่วงเวลาเพิ่มขึ้นจากอายุการใช้งาน 10 ปี (10-Year Aging Derating):
จากการทดสอบเร่งสภาวะของโรงหล่อซิลิคอน (TSMC / GlobalFoundries):
$$\Delta T_{aging}(10\text{ years}) \approx +(3.0\% \text{ ถึง } 5.0\%) \times T_{nominal\_delay}$$
หมายความว่า สำหรับเส้นทางข้อมูลที่กินเวลา $2.500\text{ ns}$ ในวันที่ 1 เมื่อผ่านการทำงานต่อเนื่อง 10 ปี เส้นทางเดิมจะช้าลงเป็น:
$$T_{data\_10yr} = 2.500\text{ ns} \times 1.05 = 2.625\text{ ns} \quad (\text{ช้าลงถึง } +125\text{ ps}!)$$

#### 2. ผลกระทบของแรงดันไฟฟ้ากระเพื่อมและแรงดันตก (Power Supply Ripple & Droop):
ในสภาวะที่มีการประมวลผลกระชาก (Sudden Current Spike $dI/dt$) รางจ่ายไฟ $V_{CCINT}$ อาจเกิดแรงดันตกชั่วขณะ (Voltage Droop $\Delta V_{dd} \approx \pm 3\% - \pm 5\%$):

$$\Delta T_{V_{droop}} \approx -k_V \cdot \left( \frac{\Delta V_{dd}}{V_{nom}} \right) \cdot T_{nominal}$$
การตกของแรงดันไฟเลี้ยง $V_{CCINT}$ ลง $5\%$ จะทำให้ความล่าช้าของเกตเพิ่มขึ้นทันที **$+6.0\% - +8.0\%$**!

#### สมการงบประมาณ Guardband รวมที่ต้องเผื่อไว้ใน Sign-Off:
$$T_{guardband\_total} = \Delta T_{aging} + \Delta T_{V_{droop}} + \Delta T_{thermal\_drift}$$
ในการออกแบบระดับอากาศยาน DO-254 วิศวกรต้องเผื่อ Margin รวมไว้อย่างน้อย **$+10\% - +12\%$ ของคาบเวลาสัญญาณนาฬิกา** เสมอ!

### 1.3 การตรวจสอบกฎระเบียบการออกแบบ (Comprehensive Methodology DRC Gatekeepers)

ก่อนการลงนามปล่อยแบบ วิศวกรต้องรันคำสั่งตรวจสอบระเบียบการออกแบบของเครื่องมือ STA อย่างเคร่งครัด:
`report_methodology -file methodology_drc.rpt`

```
               5 ข้อผิดพลาด DRC ระดับวิกฤตที่ห้ามมีในไฟล์ SIGN-OFF
               
   รหัส DRC (Code)       คำอธิบายทางวิศวกรรม (Engineering Hazard)
   -----------------   ------------------------------------------------------------
   TIMING-1 (Fatal)    Combinational Loop: มีลูปคอมบิเนชันวนกลับ ทำให้การวิเคราะห์พัง
   TIMING-6 (Critical) No Common Clock: ข้ามโดเมนนาฬิกาโดยไม่มีสัญญาณอ้างอิงร่วม
   TIMING-11 (Warning) False Path on Sync Path: การใส่ False Path ผิดที่บดบังบั๊กจริง
   TIMING-20 (Fatal)   Non-Clock pin as Clock: สัญญาณนาฬิกาถูกขับจากสายลอจิกทั่วไป
   TIMING-28 (Fatal)   Auto-Derived Clock Overridden: การเขียนทับคล็อกอัตโนมัติของ MMCM
```

> [!CAUTION]
> **กับดักมรณะของ `TIMING-28` (Auto-Derived Clock Override):**  
> ข้อผิดพลาดที่พบบ่อยที่สุดคือ วิศวกรไปเขียนคำสั่ง `create_clock` ซ้ำซ้อนที่ขาเอาต์พุตของ MMCM/PLL แทนที่จะปล่อยให้เครื่องมือสร้าง `create_generated_clock` ให้อัตโนมัติ:  
> การกระทำนี้จะ **ตัดขาดความสัมพันธ์ทางเฟสระหว่าง Clock ขาเข้าและขาออกของ MMCM โดยสิ้นเชิง!**  
> เครื่องมือจะคิดว่าสองคล็อกนี้ไม่มีความสัมพันธ์กัน และไม่ตรวจสอบ Phase Jitter / Phase Error ทำให้เกิดความล้มเหลวที่อินเทอร์เฟซภายนอกทันที!

### 1.4 การรับรองบิตสตรีมแบบทำซ้ำได้ (Deterministic Build Reproducibility)

ตามข้อกำหนดมาตรฐาน **DO-254 (Avionics)** และ **ISO 26262 (Automotive)** การคอมไพล์ FPGA จะต้องมีความสามารถในการทำซ้ำได้ $100\%$ แบบ **Deterministic**:
* เมื่อนำซอร์สโค้ด RTL ชุดเดิม ไฟล์คอนสเตรนต์ XDC ชุดเดิม และเวอร์ชันของเครื่องมือเดิมมารันคอมไพล์ในอีก 5 ปีข้างหน้า ไฟล์บิตสตรีมที่ได้จะต้องมีค่าตรวจสอบ **Cryptographic Hash (SHA-256) ตรงกันแบบบิตต่อบิต!**
* **ข้อกำหนด:** ต้องปิดออปชันการสุ่ม Seed (`-random_seed`) และต้องบันทึก Tool Version, Operating System Environment, และ Git Commit Hash ลงในหัวไฟล์บันทึกการ Sign-Off เสมอ

## 2. ทริคหน้างาน OJT แบบ Step-by-Step (現場の実践テクニック)

### 2.1 กรณีศึกษาความล้มเหลวหน้างาน: หน่วยควบคุมปีกเครื่องบินพาณิชย์ถูกผู้ตรวจการ FAA สั่งระงับบินจากบั๊ก DRC หลุดรอด (DO-254 Avionics Actuator Audit Failure)

```
+----------------------------------------------------------------------------------------------------+
| กรณีศึกษาความล้มเหลวหน้างาน (現場の失敗事例)                                                                 |
| เหตุการณ์: กล่องควบคุมเซอร์โวมอเตอร์ขับดันแพนหางเครื่องบินพาณิชย์ (DO-254 DAL-A Flight Control Actuator)    |
| อาการ: บอร์ดผ่านการทดสอบในแล็บ 100% แต่ในขั้นตอนการตรวจประเมินรับรองมาตรฐานการบินขั้นสุดท้าย (FAA SOI#3 Audit) |
|        ผู้เชี่ยวชาญของสำนักงานบริหารการบินแห่งชาติ (FAA) สั่งปฏิเสธการรับรอง (Audit Non-Compliance) ทันที      |
|        เนื่องจากรายงาน Timing Sign-Off มีการแอบใส่สคริปต์กรองซ่อนคำเตือน Methodology DRC 'TIMING-28'          |
|        และไม่มีการแสดงหลักฐานการเผื่อ Margin สำหรับการเสื่อมสภาพของซิลิคอนในระยะเวลา 15 ปี!                      |
+----------------------------------------------------------------------------------------------------+
```

#### การวิเคราะห์หาสาเหตุรากเหง้าด้วยหลักการ 5 Whys (5 Whys Root Cause Analysis):

1. **ทำไมผู้ตรวจการ FAA จึงสั่งระงับและไม่รับรองกล่องควบคุมการบิน?**  
   *คำตอบ:* เอกสารรับรองไทม์มิ่ง (Timing Compliance Evidence) ไม่มีความน่าเชื่อถือ และตรวจพบการละเมิดกฎ Design Methodology

2. **ทำไมรายงาน Timing Sign-Off จึงถูกมองว่าขาดความน่าเชื่อถือ?**  
   *คำตอบ:* มีคำเตือนระดับวิกฤต `TIMING-28` และ `TIMING-11` ตกค้างอยู่มากกว่า 12 จุด และทีมพัฒนาใช้สคริปต์กรองข้อความ (Grep filter) ตัดคำเตือนเหล่านี้ออกจากรายงานสรุปเพื่อรีบส่งงาน

3. **ทำไมจึงเกิดคำเตือน `TIMING-28` ในระบบ?**  
   *คำตอบ:* วิศวกรไปเขียนคำสั่ง `create_clock -period 10.0 [get_pins u_pll/CLKOUT0]` ทับลงบนพินเอาต์พุตของ PLL  
   ทำให้ความสัมพันธ์ทางเฟสระหว่าง Bus Clock กับ Core Clock ถูกตัดขาด กลายเป็นพาธที่ไม่มีการควบคุมความปลอดภัย

4. **ทำไมทีมงานจึงไม่คำนวณ Guardband เผื่อการเสื่อมสภาพตามอายุ 15 ปี?**  
   *คำตอบ:* ทีมงานยึดเกณฑ์การประเมินแบบอุปกรณ์อิเล็กทรอนิกส์ทั่วไปที่มองเพียงว่าค่า $Slack \ge 0.000\text{ ns}$ ก็ถือว่าผ่านแล้ว โดยไม่ทราบข้อกำหนดของ DO-254 ว่าต้องเผื่อ Aging Derating สำหรับเครื่องบินที่มีอายุการบินหลายสิบปี

5. **ทำไมกระบวนการ Kenzu ภายในบริษัทจึงปล่อยให้ความผิดพลาดนี้หลุดรอดไปถึง FAA?**  
   *คำตอบ:* บริษัทเพิ่งเปลี่ยนผ่านจากการทำชิ้นส่วนโทรคมนาคมเชิงพาณิชย์มาจับงานอากาศยาน โดยไม่ได้ปรับปรุงคู่มือปฏิบัติงาน (Sign-Off SOP Checklist) ให้สอดคล้องกับมาตรฐานความปลอดภัยระดับสูงของอากาศยาน!

### 2.3 คู่มือปฏิบัติงาน SOP: การตรวจสอบและลงนามอนุมัติไทม์มิ่งระดับภารกิจวิกฤต (Mission-Critical Sign-Off SOP)

#### สเต็ปที่ 1: การกำจัดคำเตือน Methodology DRC ให้เหลือศูนย์อย่างแท้จริง (Zero-Warning DRC Clean-Up)
* รันการตรวจสอบแบบเข้มงวด:
  `report_methodology -file final_methodology.rpt`
* ตรวจสอบว่าในไฟล์รายงาน **ต้องมีจำนวนคำเตือนเป็นศูนย์ (0 Warnings, 0 Errors)**:
  * หากพบ `TIMING-28`: ให้ลบคำสั่ง `create_clock` ที่เขียนทับขา PLL/MMCM ออกทันที และปล่อยให้ระบบใช้ `create_generated_clock` อัตโนมัติ
  * หากพบ `TIMING-1`: แก้ไขโค้ด RTL เพื่อขจัด Combinational Loop ทันที

#### สเต็ปที่ 2: การคำนวณและตรวจสอบ Aging & Voltage Droop Guardband
* ตรวจสอบว่าค่า Setup Slack ($WNS$) ในรายงานสุดท้ายต้องสอดคล้องกับสมการความปลอดภัย:
  $$WNS_{actual} \ge T_{period} \times 0.10 \quad (\text{ต้องมี Margin ไม่ต่ำกว่า } 10\% \text{ ของคาบเวลา})$$
* สำหรับ Hold Slack ($WHS$):
  $$WHS_{actual} \ge +0.080\text{ ns} \quad (\text{ที่ Fast Corner อุณหภูมิ } -40^\circ\text{C})$$

#### สเต็ปที่ 3: การตรวจสอบความสมบูรณ์ของ Timing Coverage
* รันคำสั่งตรวจสอบความครอบคลุม:
  `report_timing_summary -check_timing_verbose -delay_type min_max -file final_timing.rpt`
* ยืนยันว่า:
  * Unconstrained Endpoints $= 0$
  * No Clock Endpoints $= 0$

#### สเต็ปที่ 4: การลงนามและบันทึกหลักฐานการสร้างบิตสตรีมแบบทำซ้ำได้ (Sign-Off Sign-Off Documentation)
* บันทึกข้อมูลสภาพแวดล้อมการสร้างชิ้นงานลงในรายงาน Sign-Off:
  * Git Commit Hash ของ RTL และ XDC
  * Vivado Tool Version และ Build Number
  * คำนวณค่า SHA-256 Checksum ของไฟล์ `.bit` หรือ `.pdi`
* วิศวกรผู้ตรวจแบบ (Kenzu Lead Reviewer) ลงนามอนุมัติในเอกสาร **Timing Closure Verification Report (TCVR)** ตามระเบียบ DO-254 / ISO 26262

## 3. คำศัพท์และประโยคภาษาญี่ปุ่นสำหรับตรวจแบบ (検図 - Kenzu)

### 3.1 ตารางคำศัพท์เทคนิคเฉพาะทาง

## 4. ควิซวิเคราะห์ปัญหาระดับวิศวกรอาวุโส (上級技術クイズ)

### ข้อที่ 1: การคำนวณ Guardband สำหรับการเสื่อมสภาพ 15 ปีและแรงดันไฟฟ้าตกในระบบยานยนต์

#### โจทย์คำถาม:
ในกล่องควบคุมระบบขับเคลื่อนอัตโนมัติยานยนต์ (Automotive Autonomous Driving ECU) ตามมาตรฐานความปลอดภัย **ISO 26262 ASIL-D** วงจรบนชิป FPGA FinFET ต้องได้รับการรับประกันอายุการใช้งานอย่างปลอดภัยเป็นเวลา **$15\text{ ปี}$** ภายใต้อุณหภูมิ Junction ทำงานต่อเนื่องเฉลี่ย $T_j = 105^\circ\text{C}$

ระบบทำงานที่ความถี่สัญญาณนาฬิกา $f_{clk} = 250\text{ MHz}$ ($T_{period} = 4.000\text{ ns}$) โดยจากการวิเคราะห์ Static Timing Analysis (STA) ที่กระบวนการผลิต Slow Corner เริ่มต้นพบว่า:
* ค่าความล่าช้าของ Critical Data Path: $T_{data\_nominal} = 2.800\text{ ns}$
* ค่าความล่าช้าของ Overhead อื่นๆ (Clock Path Skew, $T_{cko}$, $T_{setup}$, $T_{uncertainty}$): $T_{overhead} = 0.850\text{ ns}$
* ค่า Setup Slack ณ วันส่งมอบเริ่มต้น:
  $$\text{Slack}_{initial} = T_{period} - T_{overhead} - T_{data\_nominal} = 4.000\text{ ns} - 0.850\text{ ns} - 2.800\text{ ns} = +0.350\text{ ns}$$

พารามิเตอร์การเสื่อมสภาพทางกายภาพของซิลิคอน (Physical Derating):
1. **ผลกระทบจากการเสื่อมสภาพของทรานซิสเตอร์ (15-Year FinFET Aging: BTI + HCI):** ทำให้ค่าความล่าช้าของ Data Path เพิ่มขึ้น **$+4.5\%$** จากค่าเดิม
2. **ผลกระทบของแรงดันไฟเลี้ยงตก (Worst-Case Voltage Droop $\Delta V_{dd} = -4\%$):** ทำให้ค่าความล่าช้าของ Data Path เพิ่มขึ้นอีก **$+5.5\%$** จากค่าเดิม
*(พารามิเตอร์ $T_{overhead}$ สมมติว่ามีผลกระทบรวมคงที่)*

จงคำนวณหา:
1. ค่าความล่าช้าที่เพิ่มขึ้นรวมทั้งหมดของ Data Path ($\Delta T_{data\_penalty}$) จาก Aging และ Voltage Droop
2. ค่า Setup Slack จริงที่เหลืออยู่หลังจากใช้งานไป 15 ปีภายใต้สภาวะแรงดันตก ($\text{Slack}_{15yr}$)
3. หากมาตรฐาน ASIL-D ระบุว่าระบบต้องมี Slack คงเหลือขั้นต่ำในสภาวะเลวร้ายที่สุด $\ge +0.100\text{ ns}$ วงจรนี้จะสอบผ่านการรับรองความปลอดภัยตลอดอายุ 15 ปีหรือไม่?

* ก. $\Delta T_{data\_penalty} = +0.280\text{ ns}$, $\text{Slack}_{15yr} = +0.070\text{ ns}$, **ไม่ผ่านเกณฑ์ ASIL-D!**
* ข. $\Delta T_{data\_penalty} = +0.280\text{ ns}$, $\text{Slack}_{15yr} = +0.150\text{ ns}$, **ผ่านเกณฑ์ ASIL-D**
* ค. $\Delta T_{data\_penalty} = +0.154\text{ ns}$, $\text{Slack}_{15yr} = +0.196\text{ ns}$, **ผ่านเกณฑ์ ASIL-D**
* ง. $\Delta T_{data\_penalty} = +0.400\text{ ns}$, $\text{Slack}_{15yr} = -0.050\text{ ns}$, **ไม่ผ่านเกณฑ์ ASIL-D!**

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: คำนวณเปอร์เซ็นต์ความล่าช้าที่เพิ่มขึ้นรวมของ Data Path:**
ผลกระทบรวมจากทั้งสองปัจจัย:
$$\text{Penalty Percentage} = \text{Aging} + \text{Voltage Droop} = +4.5\% + 5.5\% = +10.0\%$$

**ขั้นตอนที่ 2: คำนวณค่าเวลาหน่วงที่เพิ่มขึ้นจริง ($\Delta T_{data\_penalty}$):**
$$\Delta T_{data\_penalty} = 10.0\% \times T_{data\_nominal} = 0.10 \times 2.800\text{ ns} = +0.280\text{ ns} = +280\text{ ps}$$

ความล่าช้าใหม่ของ Data Path หลังจาก 15 ปี:
$$T_{data\_15yr} = T_{data\_nominal} + \Delta T_{data\_penalty} = 2.800\text{ ns} + 0.280\text{ ns} = 3.080\text{ ns}$$

**ขั้นตอนที่ 3: คำนวณ Setup Slack หลัง 15 ปี ($\text{Slack}_{15yr}$):**
$$\text{Slack}_{15yr} = \text{Slack}_{initial} - \Delta T_{data\_penalty} = +0.350\text{ ns} - 0.280\text{ ns} = +0.070\text{ ns} = +70\text{ ps}$$

**ขั้นตอนที่ 4: เปรียบเทียบกับข้อกำหนดมาตรฐาน ASIL-D:**
ตามข้อกำหนดระบุว่า ต้องมี Slack เหลือไม่น้อยกว่า $+0.100\text{ ns}$:
$$\text{Slack}_{15yr} (+0.070\text{ ns}) < +0.100\text{ ns}$$
แม้ว่าค่า Slack จะยังคงเป็นบวก ($+70\text{ ps}$) แต่ **ไม่ผ่านเกณฑ์ความปลอดภัยขั้นต่ำของ ASIL-D!**  
ระบบมีความเสี่ยงที่จะเกิดความผิดพลาดเมื่อใช้งานจริงเกิน 10-12 ปี วิศวกรจำเป็นต้องปรับปรุง Pipelining เพิ่มเติมเพื่อให้มี Initial Slack $\ge +0.380\text{ ns}$!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** ค่าปรับรวม $+0.280\text{ ns}$, Slack เหลือ $+0.070\text{ ns}$ และสรุปว่าไม่ผ่านเกณฑ์ ASIL-D ได้อย่างถูกต้องตามมาตรฐานวิศวกรรม
* **ข้อ ข. ไม่ถูกต้อง:** คำนวณ Slack ที่เหลือผิดพลาด
* **ข้อ ค. ไม่ถูกต้อง:** คิดเปอร์เซ็นต์การเสื่อมสภาพต่ำกว่าความเป็นจริง
* **ข้อ ง. ไม่ถูกต้อง:** ค่าปรับสูงเกินจริง

**คำตอบที่ถูกต้อง:** **ข้อ ก.**

### ข้อที่ 2: การวิเคราะห์ความเสี่ยงของคำเตือน Methodology DRC รหัส TIMING-28

#### โจทย์คำถาม:
ในระหว่างการตรวจสอบรายงาน `report_methodology` ของระบบประมวลผลดาวเทียมสื่อสาร วิศวกรตรวจพบข้อความแจ้งเตือนระดับวิกฤตดังนี้:

```text
CRITICAL WARNING: [Timing 38-28] Path delay is derived from an auto-derived clock 
'clk_out1_pll' on pin u_clock_gen/pll_inst/CLKOUT0, but was overridden by a user 
defined clock 'clk_main_200m' declared in constraint file top_clocks.xdc at line 42.
```

จงวิเคราะห์ว่า **ผลกระทบทางกายภาพที่ร้ายแรงที่สุดที่จะเกิดขึ้นบนชิปจริงจากคำเตือนนี้คือข้อใด**:
* ก. วงจร PLL จะหยุดทำงานและไม่สามารถสร้างสัญญาณนาฬิกาได้
* ข. เครื่องมือ STA จะตัดขาดความสัมพันธ์ทางเวลา (Phase Relationship & Jitter Transfer) ระหว่างสัญญาณนาฬิกาอินพุตของ PLL และเอาต์พุต ทำให้การวิเคราะห์ไทม์มิ่งบนเส้นทางข้ามโดเมนระหว่าง Clock ต้นทางกับ Clock ของ PLL กลายเป็นพาธที่ไม่มีการควบคุม Jitter ซึ่งนำไปสู่ความล้มเหลวในการรับส่งข้อมูลบนบอร์ดจริง
* ค. ไม่มีผลกระทบใดๆ เป็นเพียงคำเตือนเรื่องรูปแบบการเขียนโค้ดเท่านั้น
* ง. ชิป FPGA จะกินกระแสไฟฟ้าสถิต (Static Power) เพิ่มขึ้น 50%

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: วิเคราะห์พฤติกรรมของเครื่องมือเมื่อเกิด `TIMING-28`:**
* เมื่อชิปมีวงจร PLL/MMCM ซอฟต์แวร์ Vivado จะสร้างคำสั่ง `create_generated_clock` ขึ้นมาให้อัตโนมัติ โดยคำนวณอัตราทดความถี่ ($M/D$), ความล่าช้าในการเดินทางผ่าน VCO, Phase Jitter, และ Phase Alignment ให้เสร็จสรรพ
* หากวิศวกรไปเขียนคำสั่ง `create_clock` ทับที่พินเอาต์พุตนั้น เครื่องมือจะถือว่าผู้ใช้ต้องการตัดขาดสัญญาณนาฬิกานี้ออกจากต้นทาง และถือว่ามันเป็น Primary Clock ตัวใหม่ที่กำเนิดขึ้นเองลอยๆ!

**ขั้นตอนที่ 2: ผลกระทบทางกายภาพบนชิปจริง:**
* ความสัมพันธ์ของเฟสระหว่างอินพุตและเอาต์พุตของ PLL จะถูกทำลาย
* เครื่องมือ STA จะ **ไม่รวมค่า Phase Jitter และ Phase Error ของ PLL** เข้าไปในสมการ Clock Uncertainty อีกต่อไป!
* การเชื่อมต่อ I/O ภายนอกที่อ้างอิงเฟสกับ Clock อินพุตจะหลุดจากการควบคุม และจะเกิดความล้มเหลวของข้อมูล ($100\%$ Data Corruption) บนบอร์ดจริงทันทีที่อุณหภูมิเปลี่ยน!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ไม่ถูกต้อง:** ฮาร์ดแวร์ PLL ยังคงล็อกความถี่ได้ตามปกติ
* **ข้อ ข. ถูกต้องสมบูรณ์แบบ:** อธิบายกลไกการตัดขาดความสัมพันธ์ทางเฟสและการละเลย Jitter Transfer ได้อย่างแม่นยำ $100\%$
* **ข้อ ค. ไม่ถูกต้อง:** เป็นความเข้าใจผิดที่อันตรายที่สุด
* **ข้อ ง. ไม่ถูกต้อง:** ไม่เกี่ยวกับกระแสไฟฟ้ารั่วไหล

**คำตอบที่ถูกต้อง:** **ข้อ ข.**

### ข้อที่ 3: การประเมินความพร้อมในการ Sign-Off ปล่อยแบบผลิตจริง (Comprehensive Sign-Off Audit)

#### โจทย์คำถาม:
ในขั้นตอนการประชุมตรวจรับรองแบบขั้นสุดท้าย (Final Kenzu Sign-Off Review) ของโมดูลประมวลผลเรดาร์อากาศยาน DO-254 DAL-B วิศวกรนำเสนอข้อมูลผลลัพธ์ดังต่อไปนี้:

1. **Timing Slack:** $WNS = +0.450\text{ ns}$, $TNS = 0.000\text{ ns}$, $WHS = +0.095\text{ ns}$, $THS = 0.000\text{ ns}$ (ที่ความถี่ $200\text{ MHz}$, $T_{period} = 5.000\text{ ns}$)
2. **Methodology DRC Report:** พบ 0 Critical Warnings, 0 Errors, แต่มี 1 Warning: `TIMING-11` (False path on a reset synchronization register)
3. **Build Determinism:** ซอร์สโค้ดและคอนสเตรนต์ถูกแท็ก Git Tag เรียบร้อย การคอมไพล์ซ้ำ 2 ครั้งได้ SHA-256 Checksum ของไฟล์ Bitstream ตรงกัน $100\%$
4. **CDC Verification:** คำสั่ง `report_cdc -details` แสดงสถานะทุกเส้นทางเป็น "Safe" $100\%$

ในฐานะ Chief Reviewer (技師長) จงตัดสินใจว่า **โครงการนี้พร้อมสำหรับการลงนามอนุมัติ Sign-Off หรือไม่ และเพราะเหตุใด**:
* ก. อนุมัติทันที เพราะ WNS สูงถึง $+0.450\text{ ns}$ (คิดเป็น $9\%$ ของคาบเวลา) และบิตสตรีมมีความสามารถในการทำซ้ำได้แล้ว
* ข. **ยังไม่อนุมัติ (Pending):** ต้องกลับไปแก้ไข Warning `TIMING-11` ให้เป็นศูนย์อย่างแท้จริงตามนโยบาย Zero-Warning ของ DO-254 และตรวจสอบว่า WNS $\ge +0.500\text{ ns}$ ($10\%$ ของ $T_{period}$) สำหรับ Margin อากาศยาน ก่อนจึงจะลงนามได้
* ค. ปฏิเสธโครงการและสั่งรื้อโค้ดใหม่ทั้งหมด
* ง. อนุมัติได้โดยมีเงื่อนไขว่าต้องไปแก้ DRC ในเฟิร์มแวร์เวอร์ชันถัดไป

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: วิเคราะห์เกณฑ์มาตรฐาน DO-254 DAL-B:**
1. **Timing Margin:** สำหรับความถี่ $200\text{ MHz}$ ($T_{period} = 5.0\text{ ns}$) ข้อกำหนดอากาศยานต้องการ Margin ไม่ต่ำกว่า $10\%$:
   $$\text{Required Margin} = 10\% \times 5.000\text{ ns} = +0.500\text{ ns}$$
   ปัจจุบันทำได้ $+0.450\text{ ns}$ ซึ่งขาดไปอีกเพียง $50\text{ ps}$
2. **Methodology DRC Zero-Warning Policy:** ในการตรวจรับรองอากาศยาน **ห้ามมีคำเตือน DRC ตกค้างแม้แต่ตัวเดียว (Zero-Warning Policy)!** คำเตือน `TIMING-11` บน Reset Synchronizer ชี้ว่ามีการใส่ False Path ทับบนเส้นทางซิงโครไนซ์ ซึ่งเสี่ยงต่อการถูกผู้ตรวจการ FAA ปฏิเสธ

**ขั้นตอนที่ 2: การตัดสินใจเชิงวิศวกรรมอาวุโส:**
* โครงการทำได้ดีมากในด้าน Build Determinism และ CDC แต่ยังขาดความสมบูรณ์แบบในด้าน Margin อากาศยาน ($+0.450\text{ ns} < +0.500\text{ ns}$) และยังมี DRC Warning ค้างอยู่ 1 ตัว
* การตัดสินใจที่ถูกต้องคือ **ระงับการลงนามชั่วคราว (Pending)** เพื่อให้วิศวกรไปเก็บตกอีก $50\text{ ps}$ และลบคำเตือน `TIMING-11` ให้เป็นศูนย์อย่างสมบูรณ์แบบก่อน จึงจะลงนามส่งมอบงานได้อย่างภาคภูมิใจและไร้ข้อกังขา!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ไม่ถูกต้อง:** หละหลวมเกินไปสำหรับมาตรฐาน DO-254
* **ข้อ ข. ถูกต้องสมบูรณ์แบบ:** สะท้อนมาตรฐานวิศวกรรมการบินระดับสูงสุด ทั้งเรื่อง Zero-Warning และเกณฑ์ Margin 10%
* **ข้อ ค. ไม่ถูกต้อง:** รุนแรงเกินเหตุ วงจรเกือบสมบูรณ์แล้ว
* **ข้อ ง. ไม่ถูกต้อง:** มาตรฐานความปลอดภัยห้ามผัดผ่อน Warning ไปเวอร์ชันถัดไป

**คำตอบที่ถูกต้อง:** **ข้อ ข.**
