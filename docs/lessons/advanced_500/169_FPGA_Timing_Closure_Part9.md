## 1. ทฤษฎีวิศวกรรมเชิงลึก (高度なエンジニアリング理論)

### 1.1 กระบวนการ Physical Optimization ในโฟลว์การสังเคราะห์วงจร (Vivado Implementation Pipeline)
เมื่อการปรับแก้โค้ด RTL และการจัดสรร Floorplanning ดำเนินมาถึงขีดสุด แต่ระบบยังคงติดลบค่า Setup Slack เล็กน้อย (เช่น $WNS = -0.150\text{ ns}$ ถึง $-0.450\text{ ns}$) วิศวกรระดับ Senior ต้องเข้าควบคุมกระบวนการ **Advanced Physical Optimization (`phys_opt_design`)** ซึ่งเป็นเอนจินการแปลงโครงสร้างระดับเน็ตลิสต์และเซลล์ทางกายภาพที่ทำงานระหว่างขั้นตอนการวางตำแหน่ง (Placement) และการเดินสาย (Routing):

```
                   โฟลว์ VIVADO IMPLEMENTATION สมัยใหม่
                   
   [ opt_design ] ──► [ place_design ] ──► [ phys_opt_design (Post-Place) ]
                                                    │
   ┌────────────────────────────────────────────────┘
   ▼
   [ route_design ] ──► [ phys_opt_design (Post-Route) ] ──► [ TIMING CLOSURE! ]
                        (วนลูปแก้ Critical Path สุดท้าย)
```

#### ความแตกต่างระหว่าง Post-Place และ Post-Route Phys-Opt:
1. **Post-Place Physical Optimization:**  
   ทำงานหลังเสร็จสิ้นขั้นตอนวางตำแหน่ง โดยวิเคราะห์บนฐานข้อมูลการประมาณการสายส่ง (Estimated Routing Delay) สามารถย้ายตำแหน่งฟลิปฟล็อป คัดลอกเกต หรือดึงสัญญาณเข้าสู่ IOB/DSP ได้อย่างอิสระ
2. **Post-Route Physical Optimization:**  
   ทำงานหลังจากการเดินสายจริงเสร็จสมบูรณ์ โดยวิเคราะห์บน **ความล่าช้าจริงของสายส่งในชั้นซิลิคอน (Actual Extracted RC Delay)** มีความสามารถในการปลดสายส่งเดิมออก (Rip-up) แล้วเดินสายใหม่เฉพาะเส้นทางวิกฤต (Targeted Re-routing)

### 1.2 กายวิภาคของการแปลงโครงสร้างทางกายภาพ (Physical Optimization Transformations)

```
                 4 เทคนิคหลักของ ADVANCED PHYSICAL OPTIMIZATION
                 
   [ 1. Critical Pin Swapping (การสลับพินวิกฤตใน LUT6) ]
   พิน A1 (ช้า: Delay ~95ps) ◄── สลับสาย ──► พิน A6 (เร็ว: Delay ~50ps)
   ===> ประหยัดเวลาหน่วงในตัวเกตได้ทันที 45ps ต่อ 1 LUT Level!
   
   [ 2. Placement-Aware Logic Replication (การคัดลอกเกตตามกลุ่มพิกัดจริง) ]
   LUT Driver ──► Load Cluster ซ้าย (วางใน Slice X1) + Load Cluster ขวา (วางใน Slice X4)
   ===> แยกเป็น LUT_L (วางที่ X1) และ LUT_R (วางที่ X4) ขจัดสายไฟพาดขวาง!
   
   [ 3. Hard Macro Register Pull-In (การดูดฟลิปฟล็อปเข้าตัวถัง BRAM/DSP) ]
   Fabric FF ──► [ ดึงเข้าไปอยู่ในตัวถัง Hard Macro ] ──► BRAM/DSP Embedded Reg
   ===> ตัดสายไฟข้าม Slice หายไป 100%!
   
   [ 4. Slack-Driven Rip-Up and Re-Route (การรื้อสายส่งและเดินสายใหม่) ]
   รื้อสายที่ไม่วิกฤต (Slack +2.5ns) ให้ยอมวิ่งอ้อม ──► เปิดทางด่วนตรงให้เส้นทางวิกฤต!
```

#### คณิตศาสตร์ของการสลับพิน (Critical Pin Swapping Mechanics):
ภายในโครงสร้างของ LUT6 ในสถาปัตยกรรม UltraScale+ วงจรทรานซิสเตอร์ภายในไม่ได้มีความสมมาตรเท่ากันทุกขา:
* ขา **`A6` และ `A5`** อยู่ติดกับอินเวอร์เตอร์เอาต์พุตตัวสุดท้าย มีความล่าช้าภายในเกตต่ำที่สุด ($T_{pin\_A6} \approx 48\text{ ps}$)
* ขา **`A1` และ `A2`** ต้องส่งผ่าน Pass-Gate หลายชั้น มีความล่าช้าสูงที่สุด ($T_{pin\_A1} \approx 96\text{ ps}$)
* หากเส้นทาง Critical Path บังเอิญถูกต่อเข้าขา `A1` การสั่งสลับพิน (Pin Swapping) ไปเข้าขา `A6` จะสร้าง **Timing Slack คืนกลับมาได้ทันที $40\text{ ps} - 48\text{ ps}$ ต่อหนึ่งตัวเกต!**

### 1.3 ดัชนีความแออัดของสายสัญญาณและกลยุทธ์การแก้ไข (Routing Congestion Metrics & Mitigation)

ความล้มเหลวของการทำ Timing Closure มักไม่ได้เกิดจากความเร็วของทรานซิสเตอร์ แต่เกิดจาก **Routing Congestion (ความแออัดของสายสัญญาณ)** ที่บีบให้เราเตอร์ต้องลากสายอ้อมโลก:

```
               ระดับความรุนแรงของ ROUTING CONGESTION (LEVEL 1-8)
               
   ระดับ (Level)    สภาพความหนาแน่น      ผลกระทบต่อไทม์มิ่ง (Impact)
   -------------   ------------------   -------------------------
   Level 1 - 2     ปกติ (Normal)        เดินสายได้ราบรื่น สายตรงสั้นที่สุด
   Level 3 - 4     ปานกลาง (Warning)    เริ่มมีการขดสายอ้อมเล็กน้อย WNS ลดลง 10-20%
   Level 5         รุนแรง (Severe)      เกิด Route Detours มหาศาล WNS ติดลบหนัก
   Level 6 - 8     วิกฤตขั้นสูงสุด      เราเตอร์ล้มเหลว (Unroutable Design Crash!)
```

#### ประเภทของความแออัด (Congestion Types):
1. **Global Congestion:** เกิดขึ้นเมื่อจำนวนสายส่งในพื้นที่กว้าง (ข้าม Clock Region) มีมากกว่าความจุของช่องทางเดินสายโลหะทั้งหมด
2. **Short Pin Congestion:** เกิดขึ้นเมื่อเซลล์ที่วางอยู่ติดๆ กันใน Slice เดียวกัน มีจำนวนพินขาเข้า-ขาออกหนาแน่นเกินไปจนช่องทางสลับสายใน Switchbox อุดตัน

#### นโยบายและคำสั่ง Directives สำหรับ Place & Route:
เมื่อพบปัญหา Congestion วิศวกรต้องเปลี่ยนจากดีฟอลต์ไปใช้นโยบายขั้นสูง:

| ขั้นตอน (Step) | คำสั่ง Directive แนะนำ | กลไกทางวิศวกรรม (Engineering Mechanism) |
| :--- | :--- | :--- |
| **`place_design`** | `-directive AltSpreadLogic_high` | บังคับกระจายเซลล์ลอจิกออกจากกัน ลดความหนาแน่นในจุดเสี่ยง |
| **`place_design`** | `-directive Explore` | รันอัลกอริทึมจัดวางหลายรูปแบบและเลือกค่าประเมินที่ดีที่สุด |
| **`phys_opt_design`**| `-directive AggressiveExplore` | เปิดใช้ทรานส์ฟอร์มทุกชนิด รวมถึงการคัดลอกเกตและการสลับพินเชิงรุก |
| **`route_design`** | `-directive NoTimingRelaxation` | ห้ามผ่อนปรนไทม์มิ่ง บังคับให้เราเตอร์วนลูปซ่อมแซมเส้นทางสั้นที่สุด |
| **`route_design`** | `-directive MoreLoops` | เพิ่มจำนวนรอบการวนลูป Rip-up and Re-route เพื่อเคลียร์ Congestion |

## 2. ทริคหน้างาน OJT แบบ Step-by-Step (現場の実践テクニック)

### 2.1 กรณีศึกษาความล้มเหลวหน้างาน: ชิปเข้ารหัสความปลอดภัย HSM ติดลบไทม์มิ่งจากการเดินสายลูปไม่รู้จบ 22 ชั่วโมง (Crypto HSM 22-Hour Routing Stagnation)

```
+----------------------------------------------------------------------------------------------------+
| กรณีศึกษาความล้มเหลวหน้างาน (現場の失敗事例)                                                                 |
| เหตุการณ์: โมดูลเข้ารหัสข้อมูลความปลอดภัยสูง Hardware Security Module (AES-256-GCM / SHA-3 Accelerator)    |
| อาการ: ขั้นตอน Route Design รันค้างนานกว่า 22 ชั่วโมงบนเซิร์ฟเวอร์ และสิ้นสุดด้วย WNS = -0.420ns              |
|        รายงานระบุว่าเกิด Routing Congestion ระดับ Level 6 (Severe Congestion) บริเวณบล็อก Galois Field     |
|        Multiplier มีสายสัญญาณขดอ้อมหน่วงเวลาเกิน 2.5ns และไม่สามารถผ่านเกณฑ์การส่งมอบงานได้                  |
+----------------------------------------------------------------------------------------------------+
```

#### การวิเคราะห์หาสาเหตุรากเหง้าด้วยหลักการ 5 Whys (5 Whys Root Cause Analysis):

1. **ทำไมขั้นตอนการเดินสายจึงใช้เวลานานถึง 22 ชั่วโมงและยังคงติดลบ WNS = -0.420ns?**  
   *คำตอบ:* เราเตอร์ติดอยู่ในลูปการพยายามแก้ Hold และ Setup ขัดแย้งกันในบริเวณที่มีความแออัดของสายส่งระดับ Level 6

2. **ทำไมบริเวณ Galois Field Multiplier จึงเกิดความแออัดรุนแรงถึง Level 6?**  
   *คำตอบ:* มีโครงสร้างต้นไม้ลอจิก XOR ขนาดใหญ่ (มากกว่า 60,000 เกต) ถูกนำมาวางกระจุกตัวอัดแน่นอยู่ภายใน Clock Region เพียง 2 โซน

3. **ทำไมอัลกอริทึม Place จึงนำเกตทั้งหมดมากองรวมกันในพื้นที่แคบๆ?**  
   *คำตอบ:* ดีฟอลต์ของอัลกอริทึม Analytical Placer พยายามลดค่าความยาวสายส่งรวม (Bounding Box Wirelength) โดยคิดว่าการนำเซลล์มาวางชิดกันที่สุดจะทำให้วงจรเร็วที่สุด

4. **ทำไมการวางชิดกันจึงกลับกลายเป็นหายนะ?**  
   *คำตอบ:* แม้เซลล์จะชิดกัน แต่จำนวนสายไฟที่ต้องการเชื่อมต่อมีมากกว่าช่องทางเดินสายจริงใน Switchbox ส่งผลให้สายไฟส่วนใหญ่ถูกผลักให้วิ่งอ้อมออกไปด้านนอก เกิดเป็นสายยาวที่หน่วงเวลาถึง $2.5\text{ ns}$!

5. **ทำไมทีมงานจึงไม่ใช้คำสั่ง Congestion-Aware Directives และ Post-Route Phys-Opt?**  
   *คำตอบ:* สคริปต์คอมไพล์ของโปรเจกต์ใช้คำสั่งพื้นฐาน `place_design` และ `route_design` แบบไม่มีออปชันเสริม และตั้งคำสั่งให้หยุดทำงานทันทีที่ `route_design` เสร็จ โดยไม่ได้รันคำสั่ง **Post-Route `phys_opt_design`** เพื่อทำ Slack-Driven Rip-Up and Re-Route!

### 2.3 คู่มือปฏิบัติงาน SOP: การประยุกต์ใช้ Advanced Physical Optimization (WNS Clean-Up SOP)

#### สเต็ปที่ 1: ตรวจสอบความแออัดของสายส่งหลังการ Place ด้วย `report_design_analysis`
* ก่อนเริ่มขั้นตอนการเดินสาย ให้รันการวิเคราะห์ความแออัดล่วงหน้าเสมอ:
  `report_design_analysis -congestion -file place_congestion.rpt`
* หากพบว่ามีบริเวณใดขึ้นสถานะ **Congestion Level $\ge 4$** ให้ปรับเปลี่ยน Directive ของ Placer ทันที:
  `place_design -directive AltSpreadLogic_high`

#### สเต็ปที่ 2: รัน Post-Place Physical Optimization เชิงรุก
* ดำเนินการแปลงโครงสร้างทางกายภาพหลังการวางตำแหน่งเพื่อตัดทอน Critical Path:

```tcl
# ขั้นตอน Post-Place Phys Opt แบบครบวงจร
phys_opt_design -directive AggressiveExplore
```

#### สเต็ปที่ 3: ดำเนินการเดินสายด้วย Directive ควบคุมไทม์มิ่ง
* สั่งให้เราเตอร์มุ่งเน้นการรักษาไทม์มิ่งและขจัดสายอ้อม:
  `route_design -directive NoTimingRelaxation`

#### สเต็ปที่ 4: การรัน Post-Route Multi-Pass Physical Optimization เพื่อเก็บตก WNS
* หากหลังเสร็จสิ้น `route_design` แล้วค่า WNS ยังติดลบเล็กน้อย (เช่น $-0.050\text{ ns}$ ถึง $-0.250\text{ ns}$) ให้รันคำสั่ง **Post-Route Phys-Opt ซ้ำ 2 ถึง 3 รอบ**:

```tcl
# วนลูปเก็บตก WNS ขั้นสุดท้ายหลังการเดินสาย
set_property -name {STEPS.PHYS_OPT_DESIGN.IS_ENABLED} -value {true} [get_runs impl_1]
phys_opt_design -directive Explore
phys_opt_design -directive AggressiveExplore
```
คำสั่งนี้จะสั่งให้เราเตอร์รื้อสายเฉพาะเส้นทางที่ติดลบ แล้วเดินสายใหม่ผ่านช่องทางด่วนที่ว่างอยู่ ดึงค่า WNS กลับมาเป็นบวกได้อย่างน่าอัศจรรย์!

### 3.2 บทสนทนาในห้องตรวจแบบจริง (検図の現場会話)

#### สถานการณ์ที่ 1: การตรวจพบความแออัดของสายส่งและการแก้ปัญหาด้วย Post-Route Phys-Opt (Congestion Review)

## 4. ควิซวิเคราะห์ปัญหาระดับวิศวกรอาวุโส (上級技術クイズ)

### ข้อที่ 1: การคำนวณผลลัพธ์ของการทำ Critical Pin Swapping บนเส้นทางลอจิกหลายระดับ

#### โจทย์คำถาม:
ในโมดูลคำนวณการเข้ารหัสแบบบิตไวส์ เส้นทาง Critical Path ประกอบด้วยเกต Look-Up Table ชนิด LUT6 เรียงต่อกันเป็นจำนวน **$L = 4\text{ ระดับชั้นลอจิก}$** (LUT1 $\to$ LUT2 $\to$ LUT3 $\to$ LUT4)  
ระบบทำงานที่ความถี่ $f_{clk} = 400\text{ MHz}$ ($T_{period} = 2.500\text{ ns}$) โดยก่อนการทำ Physical Optimization เส้นทางนี้มีค่า Setup Slack ติดลบอยู่ที่:
$$\text{Slack}_{orig} = -0.125\text{ ns} \quad (-125\text{ ps})$$

จากการตรวจสอบรายงานทางกายภาพ พบว่าในสถานะเดิม สัญญาณข้อมูลวิ่งเข้าสู่พินอินพุต **`A1`** ของเกต LUT6 ทั้ง 4 ตัว  
พารามิเตอร์ความล่าช้าในการแพร่กระจายสัญญาณภายในตัวเกต LUT6 ของแต่ละพิน:
* ความล่าช้าเมื่อสัญญาณเข้าที่พิน `A1`: $T_{lut\_A1} = 0.092\text{ ns}$ ($92\text{ ps}$)
* ความล่าช้าเมื่อสัญญาณเข้าที่พิน `A6`: $T_{lut\_A6} = 0.048\text{ ns}$ ($48\text{ ps}$)

หากเอนจิน `phys_opt_design` สามารถทำการ **Critical Pin Swapping** สลับสัญญาณบนเส้นทางวิกฤตนี้ให้ย้ายไปเข้าที่พิน **`A6`** แทน ในเกต LUT6 ทั้ง 4 ตัวสำเร็จ โดยที่ความล่าช้าของสายส่งภายนอก ($T_{net}$) คงที่:

จงคำนวณหา:
1. ระยะเวลาหน่วงภายในตัวเกตที่ประหยัดได้ต่อ 1 ตัวเกต LUT6 ($\Delta T_{per\_lut}$)
2. ผลรวมเวลาหน่วงที่ประหยัดลงได้ตลอดทั้งเส้นทาง 4 ระดับ ($\Delta T_{total\_saving}$)
3. ค่า Setup Slack ใหม่หลังการสลับพิน ($\text{Slack}_{new}$) และระบุว่าเส้นทางนี้ผ่าน Timing หรือไม่

* ก. $\Delta T_{per\_lut} = 0.044\text{ ns}$, $\Delta T_{total\_saving} = 0.176\text{ ns}$, $\text{Slack}_{new} = +0.051\text{ ns}$ (ผ่าน Timing สำเร็จ!)
* ข. $\Delta T_{per\_lut} = 0.044\text{ ns}$, $\Delta T_{total\_saving} = 0.088\text{ ns}$, $\text{Slack}_{new} = -0.037\text{ ns}$ (ยังไม่ผ่าน)
* ค. $\Delta T_{per\_lut} = 0.048\text{ ns}$, $\Delta T_{total\_saving} = 0.192\text{ ns}$, $\text{Slack}_{new} = +0.067\text{ ns}$ (ผ่าน Timing สำเร็จ!)
* ง. $\Delta T_{per\_lut} = 0.044\text{ ns}$, $\Delta T_{total\_saving} = 0.176\text{ ns}$, $\text{Slack}_{new} = -0.051\text{ ns}$ (ยังไม่ผ่าน)

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: คำนวณเวลาที่ประหยัดได้ต่อ 1 ตัวเกต LUT6:**
ผลต่างความล่าช้าระหว่างพิน A1 และ พิน A6:
$$\Delta T_{per\_lut} = T_{lut\_A1} - T_{lut\_A6} = 0.092\text{ ns} - 0.048\text{ ns} = 0.044\text{ ns} = 44\text{ ps}$$

**ขั้นตอนที่ 2: คำนวณผลรวมเวลาที่ประหยัดได้ตลอด 4 ระดับชั้น:**
เนื่องจากเกตทั้ง 4 ตัวถูกสลับพินทั้งหมด:
$$\Delta T_{total\_saving} = 4 \times \Delta T_{per\_lut} = 4 \times 0.044\text{ ns} = 0.176\text{ ns} = 176\text{ ps}$$

**ขั้นตอนที่ 3: คำนวณ Setup Slack ใหม่:**
$$\text{Slack}_{new} = \text{Slack}_{orig} + \Delta T_{total\_saving} = -0.125\text{ ns} + 0.176\text{ ns} = +0.051\text{ ns} = +51\text{ ps}$$

เนื่องจาก $\text{Slack}_{new} > 0$ เส้นทางวิกฤตนี้จึง **พลิกกลับมาสอบผ่านเกณฑ์ไทม์มิ่งได้อย่างสมบูรณ์!**  
เพียงแค่การสลับขาพินอินพุตภายใน LUT6 ช่วยดึงเวลาคืนมาได้ถึง $176\text{ ps}$ โดยไม่ต้องแก้โค้ดหรือเปลี่ยนตำแหน่งการวางเซลล์เลย!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** คำนวณเวลาประหยัดต่อตัว $44\text{ ps}$, รวม $176\text{ ps}$, และ Slack ใหม่ $+0.051\text{ ns}$ ถูกต้องตรงตามทฤษฎี $100\%$
* **ข้อ ข. ไม่ถูกต้อง:** คิดจำนวนเกตเพียง 2 ตัว
* **ข้อ ค. ไม่ถูกต้อง:** นำค่าเวลาของพิน A6 ไปเป็นผลต่าง
* **ข้อ ง. ไม่ถูกต้อง:** เครื่องหมายของ Slack ติดลบผิดพลาด

**คำตอบที่ถูกต้อง:** **ข้อ ก.**

### ข้อที่ 2: การวิเคราะห์ Routing Congestion Metric และผลกระทบต่อค่า Routing Wire Detour

#### โจทย์คำถาม:
ในขั้นตอนการเดินสายของชิป UltraScale+ บริเวณ Clock Region `X2Y3` มีช่องทางเดินสายสัญญาณโลหะแนวนอน (Horizontal Routing Tracks) ทั้งสิ้น $N_{tracks} = 40,000\text{ tracks}$  
วงจรในบริเวณนั้นมีเส้นทางสายสัญญาณที่ต้องเชื่อมต่อจริง (Demand Nets) จำนวนทั้งสิ้น $D = 48,000\text{ nets}$

หากแบบจำลองความล่าช้าของการเดินสายอ้อม (Route Detour Delay Model) ระบุว่า:
* ในสภาวะปกติที่ไม่มี Congestion (Demand $\le$ Tracks): ความล่าช้าเฉลี่ยของสายส่งสั้นคือ $T_{net\_nominal} = 0.350\text{ ns}$
* ในสภาวะ Over-Congestion (Demand $>$ Tracks): เราเตอร์จำเป็นต้องผลักสายสัญญาณส่วนเกินร้อยละ $\frac{D - N_{tracks}}{D} \times 100\%$ ให้วิ่งอ้อมออกไปนอก Clock Region ซึ่งสายอ้อมแต่ละเส้นจะมีเวลาหน่วงเพิ่มขึ้นเป็น **$4.0\text{ เท่า}$** ของค่าปกติ ($T_{net\_detour} = 4.0 \times T_{net\_nominal}$)

จงคำนวณหา:
1. อัตราส่วนความแออัดของสายส่ง (Routing Congestion Ratio: $\frac{D}{N_{tracks}} \times 100\%$)
2. จำนวนสายสัญญาณที่ถูกบังคับให้วิ่งอ้อม ($N_{detour\_nets}$)
3. เวลาหน่วงเฉลี่ยของสายส่งทั้งหมดในบริเวณนี้ ($T_{net\_average}$)

* ก. Congestion Ratio $= 120.0\%$, สายอ้อม $= 8,000\text{ nets}$, $T_{net\_average} = 0.525\text{ ns}$
* ข. Congestion Ratio $= 120.0\%$, สายอ้อม $= 8,000\text{ nets}$, $T_{net\_average} = 0.700\text{ ns}$
* ค. Congestion Ratio $= 110.0\%$, สายอ้อม $= 4,000\text{ nets}$, $T_{net\_average} = 0.450\text{ ns}$
* ง. Congestion Ratio $= 120.0\%$, สายอ้อม $= 12,000\text{ nets}$, $T_{net\_average} = 0.850\text{ ns}$

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: คำนวณ Routing Congestion Ratio:**
$$\text{Congestion Ratio} = \frac{D}{N_{tracks}} \times 100\% = \frac{48,000}{40,000} \times 100\% = 120.0\%$$
(ความต้องการใช้งานสูงกว่าความจุจริงถึง $20\%$)

**ขั้นตอนที่ 2: คำนวณจำนวนสายที่ต้องวิ่งอ้อม ($N_{detour\_nets}$):**
จำนวนสายส่วนเกินที่ไม่สามารถเดินตรงได้:
$$N_{detour\_nets} = D - N_{tracks} = 48,000 - 40,000 = 8,000\text{ nets}$$

**ขั้นตอนที่ 3: คำนวณเวลาหน่วงเฉลี่ยของสายส่ง ($T_{net\_average}$):**
* ความล่าช้าของสายส่งปกติ (40,000 เส้น): $T_{nominal} = 0.350\text{ ns}$
* ความล่าช้าของสายส่งอ้อม (8,000 เส้น):
  $$T_{detour} = 4.0 \times 0.350\text{ ns} = 1.400\text{ ns}$$
คำนวณค่าเฉลี่ยถ่วงน้ำหนัก:
$$T_{net\_average} = \frac{(40,000 \times 0.350\text{ ns}) + (8,000 \times 1.400\text{ ns})}{48,000}$$
$$T_{net\_average} = \frac{14,000 + 11,200}{48,000} = \frac{25,200}{48,000} = 0.525\text{ ns}$$

ผลลัพธ์แสดงให้เห็นว่า Congestion เพียง $120\%$ ทำให้เวลาหน่วงเฉลี่ยพุ่งขึ้นจาก $0.350\text{ ns}$ เป็น **$0.525\text{ ns}$ (เพิ่มขึ้นถึง $50\%$)** และสายที่เคราะห์ร้าย 8,000 เส้นนั้นจะติดลบ Setup Violation ทันที!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** คำนวณ Ratio $120\%$, สายอ้อม 8,000 เส้น และความล่าช้าเฉลี่ย $0.525\text{ ns}$ ได้อย่างถูกต้องครบถ้วน
* **ข้อ ข. ไม่ถูกต้อง:** ค่าเฉลี่ยคำนวณผิด
* **ข้อ ค. ไม่ถูกต้อง:** อัตราส่วน Congestion คิดเป็น 110% ผิดพลาด
* **ข้อ ง. ไม่ถูกต้อง:** จำนวนสายอ้อมคำนวณผิด

**คำตอบที่ถูกต้อง:** **ข้อ ก.**

### ข้อที่ 3: การประเมินลำดับขั้นตอนการใช้ Directives ในการปิดไทม์มิ่งที่ยากเป็นพิเศษ

#### โจทย์คำถาม:
ในโปรเจกต์ FPGA ขนาดใหญ่ การรัน Implementation แบบ Default ทำให้เกิด Setup Slack ติดลบ $WNS = -0.380\text{ ns}$ และรายงานระบุว่ามี Routing Congestion ระดับ Level 5 ในพื้นที่กว้าง

ในฐานะ Principal Timing Closure Engineer จงจัดลำดับกลยุทธ์ (Implementation Strategy Sequence) ที่ถูกต้องและมีประสิทธิภาพสูงสุดในการแก้ปัญหานี้:
* ก. รันคำสั่ง `route_design -directive Explore` ซ้ำๆ 10 รอบโดยไม่ต้องแตะขั้นตอน Placement
* ข.
  1. ขั้นตอน Placement: ใช้ `place_design -directive AltSpreadLogic_high` เพื่อขยายการกระจายตัวของลอจิกและลดความแออัด
  2. ขั้นตอน Post-Place: รัน `phys_opt_design -directive AggressiveExplore` เพื่อทำ Pin Swapping และ Replication
  3. ขั้นตอน Routing: ใช้ `route_design -directive NoTimingRelaxation`
  4. ขั้นตอน Post-Route: รัน `phys_opt_design -directive Explore` ซ้ำอีกครั้งเพื่อทำ Rip-up and Re-route
* ค. ปรับลดความถี่ของสัญญาณนาฬิกาลงทันทีโดยไม่ต้องพยายามใช้ Directives
* ง. สั่งเพิ่มแอตทริบิวต์ `(* DONT_TOUCH = "TRUE" *)` บนทุกโมดูลเพื่อป้องกันไม่ให้เราเตอร์ขยับเซลล์

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: วิเคราะห์รากเหง้าของปัญหา:**
* ปัญหาเริ่มต้นจาก **Routing Congestion Level 5** ซึ่งเป็นปัญหาตั้งแต่ขั้นตอนการจัดวาง (Placement)
* การพยายามแก้ที่ Routing โดยตรง (ตามข้อ ก) ไม่สามารถแก้ปัญหาได้ เพราะพื้นที่ถูกอัดแน่นไปแล้วตั้งแต่ขั้นตอน Place

**ขั้นตอนที่ 2: วิเคราะห์กลยุทธ์ตามลำดับขั้น (Hierarchical Closure Strategy):**
1. **แก้ Placement ก่อน:** ใช้ `AltSpreadLogic_high` เพื่อคลายความหนาแน่นและเปิดช่องทางเดินสาย
2. **ทำ Post-Place Phys-Opt:** ใช้ `AggressiveExplore` เพื่อสลับพินและคัดลอกเกตตัดทอนความยาวสาย
3. **คุม Routing อย่างเข้มงวด:** ใช้ `NoTimingRelaxation` บังคับให้เราเตอร์เดินสายสั้นที่สุด
4. **เก็บตกขั้นสุดท้ายด้วย Post-Route Phys-Opt:** ทำ Rip-up and Re-route บนเส้นทางที่เหลืออีกไม่กี่ร้อยพิโกวินาที

นี่คือ **ลำดับกลยุทธ์ระดับมาตรฐานสากล (Golden Standard Strategy)** ที่ได้รับการพิสูจน์แล้วว่าสามารถแก้ปัญหา Slack ติดลบในระดับ $-0.380\text{ ns}$ ได้อย่างมีประสิทธิภาพสูงสุด!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ไม่ถูกต้อง:** การวนลูปเฉพาะ Router ไม่สามารถแก้ Congestion ที่เกิดจาก Placement ได้
* **ข้อ ข. ถูกต้องสมบูรณ์แบบ:** ลำดับขั้นตอนตั้งแต่ Place, Post-Place, Route, และ Post-Route สอดคล้องกับแนวทางวิศวกรรมสากล $100\%$
* **ข้อ ค. ไม่ถูกต้อง:** การยอมลดความถี่เป็นทางเลือกสุดท้าย ไม่ใช่วิธีแก้ปัญหา
* **ข้อ ง. ไม่ถูกต้อง:** การใส่ DONT_TOUCH ยิ่งซ้ำเติมปัญหาให้แย่ลง

**คำตอบที่ถูกต้อง:** **ข้อ ข.**
