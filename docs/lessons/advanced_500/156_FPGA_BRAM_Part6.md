## 1. ทฤษฎีวิศวกรรมเชิงลึก (高度なエンジニアリング理論)

### 1.1 กายวิภาคของ Byte-Write Enable บน BRAM Hard Macro (Silicon Architecture of Byte-Wide WE)
ในระบบประมวลผลข้อมูลสมัยใหม่ ข้อมูลบนบัสหน่วยความจำมักมีขนาดกว้าง เช่น 32 บิต, 64 บิต, หรือ 128 บิต แต่หน่วยประมวลผล (CPU/DSP Core), ตัวควบคุมโครงข่าย (Network MAC Controller), หรือวงจร DMA มักต้องการแก้ไขข้อมูลเฉพาะบางไบต์ (Partial Byte Update) เช่น การเขียนทับเฉพาะ Header Field ขนาด 8 บิต หรือ 16 บิต โดยไม่ต้องการเปลี่ยนแปลงข้อมูลบิตที่เหลือในเวิร์ดเดียวกัน

หากฮาร์ดแวร์หน่วยความจำไม่มีคุณสมบัติ **Byte-Write Enable** วงจรจะต้องใช้วิธี **Read-Modify-Write (RMW)** ซึ่งสร้างปัญหาคอขวดและอันตรายต่อความสมบูรณ์ของข้อมูลอย่างร้ายแรง

```
                 กายวิภาคของ BRAM BYTE-WRITE ENABLE (RAMB36E2)
                 
                      ADDR Bus [14:0]
                            │
                            ▼
     DIN [63:0] ═══════════════════════════════════════╗
     WEB [7:0]  ────┬───┬───┬───┬───┬───┬───┬───┐      ║
                    │   │   │   │   │   │   │   │      ║
                    ▼   ▼   ▼   ▼   ▼   ▼   ▼   ▼      ║
                  ┌───┬───┬───┬───┬───┬───┬───┬───┐    ║
                  │WE7│WE6│WE5│WE4│WE3│WE2│WE1│WE0│    ║
                  └───┴───┴───┴───┴───┴───┴───┴───┘    ║
                    │   │   │   │   │   │   │   │      ║ (แยก Bitline Pass-gate)
                    ▼   ▼   ▼   ▼   ▼   ▼   ▼   ▼      ║
                  ┌───┬───┬───┬───┬───┬───┬───┬───┐    ║
                  │B 7│B 6│B 5│B 4│B 3│B 2│B 1│B 0│◄═══╝ (64-bit Memory Word)
                  │Byte Write Enable Granularity  │
                  └───┴───┴───┴───┴───┴───┴───┴───┘
                            │
                            ▼
     DOUT [63:0] ═══════════════════════════════════════ (อ่านออกทั้ง 64 บิตพร้อมกัน)
```

#### กลไกในระดับซิลิคอน (Silicon Microarchitecture):
* ภายใน BRAM Macro ของสถาปัตยกรรม UltraScale/UltraScale+ (RAMB18E2 / RAMB36E2) สายสัญญาณ Write Enable ไม่ได้เป็นเส้นเดียวโดดๆ แต่ถูกแยกย่อยออกเป็น **เวกเตอร์ Write Enable ระดับไบต์**:
  * สำหรับพอร์ตความกว้าง 32 บิต: สัญญาณ `WE[3:0]` ควบคุมไบต์ละ 8 บิต (หรือ 9 บิตเมื่อรวม Parity)
  * สำหรับพอร์ตความกว้าง 64 บิต (Cascade หรือ 72-bit mode): สัญญาณ `WE[7:0]` ควบคุมไบต์ละ 8 บิต
* แต่ละเส้นสัญญาณ $WE_k$ จะวิ่งเข้าไปควบคุม **Pass-Gate Transistor และ Write Driver เฉพาะของคอลัมน์ Bitline คู่นั้นๆ ($Bitline_k$ และ $\overline{Bitline}_k$)**
* เมื่อ $WE_k = 1$: Write Driver ของไบต์ที่ $k$ จะขับแรงดันประจุลงเซลล์ 6T SRAM เพื่อเขียนข้อมูลใหม่
* เมื่อ $WE_k = 0$: Write Driver ของไบต์ที่ $k$ จะอยู่ในสถานะ High-Impedance (Hi-Z) ปล่อยให้เซลล์ SRAM ในไบต์นั้นคงสถานะประจุเดิมไว้ $100\%$ โดยไม่มีการรบกวน!

### 1.2 หายนะของ Read-Modify-Write (RMW) vs ประสิทธิภาพของ Atomic Byte-Write

เพื่อเข้าใจว่าทำไม Byte-Write Enable จึงเป็นฟีเจอร์ระดับวิกฤต ลองเปรียบเทียบการอัปเดตข้อมูลขนาด 8 บิตลงในเวิร์ดขนาด 64 บิตระหว่างสองแนวทาง:

```
                  การเปรียบเทียบเชิงเวลา: RMW VS NATIVE BYTE-WRITE
                  
   [ แนวทางที่ 1: Read-Modify-Write (RMW) - ไร้ Byte Enable ]
   Cycle 1: ออกแอดเดรส เพื่ออ่านเวิร์ดเดิมออกจาก BRAM  (Read Request)
   Cycle 2: รอ BRAM Pipeline Register ส่งข้อมูลออก      (Read Latency)
   Cycle 3: นำข้อมูลเดิมมารวมกับไบต์ใหม่ผ่าน ALU/MUX   (Modify Data: Old[63:8] | New[7:0])
   Cycle 4: ออกแอดเดรสและขับ Write Enable บันทึกกลับ  (Write Back)
   ===> ใช้เวลา 4 ไซเคิล! (Throughput หดหายเหลือ 25%, เสี่ยงต่อ Race Hazard หากมี Port อื่นแทรก!)
   
   [ แนวทางที่ 2: Native Byte-Write Enable - ซิลิคอน BRAM แท้ ]
   Cycle 1: ส่ง ADDR, DIN[63:0], และสั่ง WE[7:0] = 8'b0000_0001
   ===> สำเร็จใน 1 ไซเคิลเดี่ยว! (Atomic Write, Throughput 100%, ปลอดภัยต่อ Multi-Port Coherency)
```

#### การวิเคราะห์ทางคณิตศาสตร์ของ Throughput และ Bus Efficiency:
กำหนดให้:
* $f_{clk}$: ความถี่สัญญาณนาฬิกาของระบบ ($300\text{ MHz}$)
* $N_{trans}$: จำนวนทรานแซกชันที่ต้องการอัปเดตระดับ Sub-word ($10^6$ operations)
* $L_{BRAM}$: Latency ของ BRAM พร้อม Output Register ($2\text{ cycles}$)

ระยะเวลาที่ใช้ในวิธี RMW:
$$T_{RMW} = N_{trans} \cdot (L_{BRAM} + 1_{modify} + 1_{write}) \cdot \frac{1}{f_{clk}} = 10^6 \cdot (2 + 1 + 1) \cdot 3.33\text{ ns} = 13.32\text{ ms}$$

ระยะเวลาที่ใช้ในวิธี Native Byte-Write:
$$T_{ByteWrite} = N_{trans} \cdot 1_{cycle} \cdot \frac{1}{f_{clk}} = 10^6 \cdot 1 \cdot 3.33\text{ ns} = 3.33\text{ ms}$$

$$\text{Throughput Gain} = \frac{T_{RMW}}{T_{ByteWrite}} = \frac{4}{1} = 400\% \quad (4\times \text{ Performance!})$$

ที่สำคัญยิ่งกว่าความเร็วคือ **Atomic Guarantee**: ในระบบ True Dual-Port BRAM หาก Port A ทำการ Read-Modify-Write ที่กินเวลา 4 ไซเคิล หาก Port B เขียนแทรกเข้ามาที่แอดเดรสเดียวกันใน Cycle 2 ข้อมูลที่ Port A บันทึกกลับใน Cycle 4 จะ **เขียนทับข้อมูลของ Port B จนสูญหาย (Lost Update Anomaly)** ทันที! แต่ Native Byte-Write ทำงานจบในไซเคิลเดียว จึงขจัดช่องโหว่ความไม่สอดคล้องของข้อมูลได้อย่างสมบูรณ์

### 1.3 พาริตี้บิตและเกรนูแลริตี 9 บิต (8-bit vs 9-bit Granularity & Parity Routing)

ในชิป FPGA ตระกูล Xilinx UltraScale/UltraScale+ สถาปัตยกรรม BRAM ถูกออกแบบให้รองรับขนาดบัสข้อมูลพื้นฐานที่เป็นทวีคูณของ **9 บิต** (8 บิตข้อมูล + 1 บิตพาริตี้/ไซด์แบนด์แฟลก):
* ในโหมดไม่ใช้พาริตี้: 1 ไบต์ = 8 บิต ($Byte\_Width = 8$)
* ในโหมดใช้พาริตี้ / ตรวจสอบความถูกต้อง: 1 ไบต์ = 9 บิต ($Byte\_Width = 9$)

```
                   บัสข้อมูล 72 บิตใน BRAM (8 x 9-bit BYTES)
                   
   Data Bits:   [  Byte 7  ][  Byte 6  ] ... [  Byte 1  ][  Byte 0  ]  (64 bits: DIN[63:0])
   Parity Bits: [   P 7   ][   P 6   ] ... [   P 1   ][   P 0   ]  ( 8 bits: DINP[7:0])
                └────┬────┘ └────┬────┘       └────┬────┘ └────┬────┘
                     ▼           ▼                 ▼           ▼
   Write Enable:   WE[7]       WE[6]             WE[1]       WE[0]
```

เมื่อเปิดใช้งาน Byte-Write Enable สัญญาณ $WE_k$ จะควบคุมทั้งบิตข้อมูล $DIN[8k+7 : 8k]$ และบิตพาริตี้ $DINP[k]$ พร้อมกันโดยอัตโนมัติ ทำให้การบันทึกข้อมูลและรหัสตรวจสอบ Parity/Meta-tag เกิดขึ้นแบบเป็นหนึ่งเดียว (Coherent Storage) เสมอ

### 1.4 โครงสร้างโค้ด RTL สำหรับการสังเคราะห์ Byte-Write Enable อัตโนมัติ (Inference Templates)

> [!WARNING]
> **กับดักการเขียน RTL ที่ทำให้ Synthesis ล้มเหลว:**  
> วิศวกรจำนวนมากพยายามเขียน Byte-Write โดยใช้การ Slicing เวกเตอร์แบบไดนามิก เช่น:  
> `mem[addr][byte_sel*8 +: 8] <= din;`  
> รูปแบบนี้ **ไม่ตรงกับ Synthesis Coding Template** ของ Vivado/Quartus! ผลลัพธ์คือ ซอฟต์แวร์จะไม่สามารถดึง Hard Macro BRAM Byte-Enable มาใช้ได้ แต่จะสร้างวงจร Multiplexer และ Latch ภายนอกมหึมา กิน Slice LUT นับพันตัวและทำให้ $F_{max}$ พังทลาย!

#### รูปแบบที่ถูกต้อง (The Golden Verilog Template):
ต้องใช้โครงสร้าง **`generate` Loop หรือ `for` Loop ที่แจกแจงระดับไบต์อย่างชัดเจน** ภายในโพรเซสซิงก์บล็อก:

```verilog
// ==============================================================================
// GOLDEN INFERENCE TEMPLATE: TRUE DUAL-PORT BRAM WITH BYTE-WRITE ENABLE
// ==============================================================================
module bram_byte_write #(
    parameter integer DATA_WIDTH = 32,                 // 32-bit word
    parameter integer ADDR_WIDTH = 10,                 // 1024 depth
    parameter integer BYTE_WIDTH = 8,                  // 8-bit per byte
    parameter integer NUM_BYTES  = DATA_WIDTH / BYTE_WIDTH // 4 bytes
)(
    input  wire                    clk,
    // Port A Interface
    input  wire [NUM_BYTES-1:0]    we_a,               // Byte-wide WE: 4 bits
    input  wire [ADDR_WIDTH-1:0]   addr_a,
    input  wire [DATA_WIDTH-1:0]   din_a,
    output reg  [DATA_WIDTH-1:0]   dout_a
);

    // นิยาม BRAM Array เป็น 2-Dimensional Array ขนาด [DEPTH-1:0]
    // หรือ Array of Bytes ก็ได้ แต่วิธีที่แนะนำสำหรับ Vivado คือ Packed Word:
    (* ram_style = "block" *)
    reg [DATA_WIDTH-1:0] ram [0:(1<<ADDR_WIDTH)-1];

    // Read Logic with Optional Output Register
    always @(posedge clk) begin
        dout_a <= ram[addr_a];
    end

    // Write Logic: ต้องแจกแจงลูป FOR แยกตามแต่ละไบต์อย่างเคร่งครัด!
    integer i;
    always @(posedge clk) begin
        for (i = 0; i < NUM_BYTES; i = i + 1) begin
            if (we_a[i]) begin
                ram[addr_a][(i*BYTE_WIDTH) +: BYTE_WIDTH] <= din_a[(i*BYTE_WIDTH) +: BYTE_WIDTH];
            end
        end
    end

endmodule
```

เมื่อเขียนในรูปแบบนี้ Synthesis Engine จะสามารถ Mapping โค้ดเข้ากับพอร์ต `WEB[NUM_BYTES-1:0]` ของ BRAM Hard Macro ได้อย่างแม่นยำ $100\%$ โดยไม่เสีย LUT เพิ่มแม้แต่ตัวเดียว!

## 2. ทริคหน้างาน OJT แบบ Step-by-Step (現場の実践テクニック)

### 2.1 กรณีศึกษาความล้มเหลวหน้างาน: ข้อมูลพิกัดเรดาร์รถยนต์เสียหายจากการเขียนแทรกแบบ RMW (Automotive Radar Target Memory Corruption)

```
+----------------------------------------------------------------------------------------------------+
| กรณีศึกษาความล้มเหลวหน้างาน (現場の失敗事例)                                                                 |
| เหตุการณ์: กล่องควบคุมเรดาร์ตรวจจับวัตถุระยะไกล 77GHz สำหรับระบบเบรกฉุกเฉินอัตโนมัติ (AEB) ADAS ECU          |
| อาการ: ในการทดสอบขับขี่จริงบนสนามทดสอบ วงจรประมวลผลเกิดอาการ "ตรวจพบวัตถุล่องหน (Ghost Target)" หรือ       |
|        พิกัดความเร็วของรถคันหน้ากระโดดจาก 60 km/h กลายเป็น 300 km/h ในเสี้ยววินาทีจนระบบสั่งเบรกฉุกเฉินผิดพลาด |
+----------------------------------------------------------------------------------------------------+
```

#### การวิเคราะห์หาสาเหตุรากเหง้าด้วยหลักการ 5 Whys (5 Whys Root Cause Analysis):

1. **ทำไมระบบจึงตรวจพบวัตถุล่องหนและคำนวณความเร็วผิดพลาด?**  
   *คำตอบ:* ตารางพิกัดเป้าหมาย (Target Tracking Table) ใน BRAM มีข้อมูลเวิร์ดขนาด 64 บิตที่มีค่าบิตพิกัดผสมปนเปกันระหว่างเป้าหมายหมายเลข 3 กับเป้าหมายหมายเลข 7

2. **ทำไมข้อมูลของสองเป้าหมายจึงปนกันในเวิร์ดเดียวกันได้?**  
   *คำตอบ:* ฟิลด์ข้อมูลของเป้าหมายถูกจัดเก็บแบบ Sub-word (ไบต์ 0-3 คือระยะทาง, ไบต์ 4-7 คือความเร็วสัมพัทธ์) โดยมีวงจร DSP Core กำลังอัปเดตระยะทาง ในขณะที่วงจร Tracking Kalman Filter กำลังอัปเดตความเร็ว

3. **ทำไมวงจรทั้งสองจึงเขียนทับข้อมูลของกันและกัน?**  
   *คำตอบ:* ทั้งสองวงจรใช้วิธี Read-Modify-Write (RMW) ผ่านพอร์ตคนละพอร์ตของ True Dual-Port BRAM เมื่อทั้งสองพอร์ตต้องการอัปเดตคนละฟิลด์ในแอดเดรสเดียวกันในเวลาไล่เลี่ยกัน พอร์ตที่เขียนทีหลังได้บันทึกทับฟิลด์เดิมที่ยังไม่ได้อัปเดตของอีกพอร์ตกลับลงไป (Lost Update Anomaly)

4. **ทำไมทีมออกแบบจึงเลือกใช้วิธี RMW แทนที่จะใช้ Byte-Write Enable?**  
   *คำตอบ:* วิศวกร RTL เขียนโค้ดพยายามใช้ Byte-Write แล้ว แต่ใช้รูปแบบ Dynamic Bit Slicing:  
   `target_ram[addr][sel*8 +: 8] <= new_byte;`  
   ซึ่งทำให้ Vivado สังเคราะห์ไม่ผ่านเป็น BRAM Native Byte-Enable จึงแอบสร้าง RMW FSM State Machine ภายนอกมาแก้ขัดโดยไม่ปรึกษาหัวหน้าทีม

5. **ทำไมวงจร RMW จึงหลุดรอดการทดสอบ Simulation ในแล็บไปได้?**  
   *คำตอบ:* Testbench ในแล็บทดสอบการเข้าถึงทีละเป้าหมายตามลำดับ (Sequential Access) ไม่เคยจำลองสถานการณ์ที่ DSP และ Kalman Filter แย่งกันเขียนข้อมูลลงเวิร์ดเดียวกันแบบพร้อมกัน (Concurrent Asynchronous Write Access) ภายใต้โหลดการประมวลผลสูงสุด!

### 2.3 คู่มือปฏิบัติงาน SOP: การออกแบบและตรวจสอบ BRAM Byte-Write Enable (Zero-Defect SOP)

#### สเต็ปที่ 1: ตรวจสอบความสอดคล้องของอัตราส่วน Data Width และ Byte Width
* คำนวณจำนวนบิตควบคุม Write Enable:
  $$\text{NUM\_WE\_BITS} = \frac{\text{DATA\_WIDTH}}{\text{BYTE\_GRANULARITY}}$$
* ตรวจสอบว่า $\text{BYTE\_GRANULARITY}$ ต้องเป็น 8 บิต หรือ 9 บิตเท่านั้น และ $\text{DATA\_WIDTH}$ ต้องหารด้วยค่านี้ลงตัวพอดี

#### สเต็ปที่ 2: ใช้ Golden Template ที่รองรับการจำลองพฤติกรรมและการสังเคราะห์ $100\%$
* ห้ามเขียนการเลื่อนบิตแบบ Dynamic Index ในส่วน L-Value (`mem[addr][...] <= ...`) โดยเด็ดขาด
* ให้ใช้โครงสร้าง `for loop` คงที่แจกแจงตามจำนวนไบต์เสมอ ดังแสดงในหัวข้อ 1.4

#### สเต็ปที่ 3: ตรวจสอบ Log การสังเคราะห์ (Vivado Synthesis Log Verification)
* ค้นหาข้อความในไฟล์ `runme.log` หรือรายงาน `synth_1/runme.log`:
  ```text
  INFO: [Synth 8-5544] ROM "ram_reg" won't be mapped to Block RAM because address size is too small...
  INFO: [Synth 8-5784] Optimized 1 instances of RAMB36E2 with byte-wide write enable.
  ```
* ตรวจสอบให้แน่ใจว่าพอร์ต Write Enable ของพรีมิทิฟ `RAMB36E2` หรือ `RAMB18E2` ถูกเชื่อมต่อกับเวกเตอร์ `WEA[3:0]` หรือ `WEB[7:0]` อย่างสมบูรณ์ ไม่มีการต่อรวบเส้นเดียว

#### สเต็ปที่ 4: การใส่ SystemVerilog Assertions เพื่อดักจับ Address Collision ระหว่างพอร์ต
* ในระบบ True Dual-Port ที่ใช้งาน Byte-Write Enable แม้ว่าแต่ละพอร์ตจะเขียนคนละไบต์กัน แต่หากเขียนลงในเวิร์ดเดียวกันที่เวลาเดียวกัน ซิลิคอน BRAM อาจเกิดการรบกวนของแรงดันสาย Bitline ให้เขียน SVA ดักจับทันที:

```systemverilog
// SVA ตรวจสอบการชนกันของแอดเดรสระหว่างพอร์ต A และ พอร์ต B
property p_no_same_addr_write_collision;
    @(posedge clk)
    disable iff (!rst_n)
    (|we_a && |we_b) |-> (addr_a != addr_b);
endproperty
assert property (p_no_same_addr_write_collision)
    else $error("[FATAL DRC] Port A and Port B write collision at Address: 0x%h", addr_a);
```

## 4. ควิซวิเคราะห์ปัญหาระดับวิศวกรอาวุโส (上級技術クイズ)

### ข้อที่ 1: การคำนวณเปรียบเทียบ Throughput และ Latency ระหว่าง RMW และ Atomic Byte-Write

#### โจทย์คำถาม:
ในโมดูลจัดการตารางแฮช (Hash Flow Table) ของการ์ดเราเตอร์ขนาด 400Gbps วงจรต้องประมวลผลคำขออัปเดตฟิลด์สถิติขนาด $16\text{ bits}$ (Sub-word) ภายในเวิร์ดหน่วยความจำขนาด $64\text{ bits}$ จำนวนทั้งสิ้น $10,000,000\text{ รายการ}$ ($10^7\text{ transactions}$)

กำหนดให้:
* สัญญาณนาฬิกา $CLK = 300\text{ MHz}$ (คาบเวลา $T = 3.333\text{ ns}$)
* **สถาปัตยกรรมแบบเก่า (RMW):** ใช้ BRAM แบบไม่มี Byte-Write Enable โดยมี Read Latency ของ BRAM เท่ากับ $2\text{ cycles}$ (เปิดใช้ Output Register), การคำนวณแก้ไขบิตใน ALU ใช้เวลา $1\text{ cycle}$, และการเขียนกลับ (Write-back) ใช้เวลา $1\text{ cycle}$ ทั้งนี้วงจรทำงานแบบ Blocking (ไม่สามารถ Pipelining การอัปเดตแอดเดรสเดียวกันได้)
* **สถาปัตยกรรมแบบใหม่ (Native Byte-Write):** ใช้ BRAM พร้อม Byte-Write Enable ขนาด $8\text{ bits granularity}$ ทำให้การเขียนอัปเดตขนาด 16 บิต (เปิดใช้ `WE[1:0]` หรือ `WE[k+1:k]`) สำเร็จได้ใน $1\text{ cycle}$ แบบต่อเนื่องผ่าน Pipelined Ingest (อัตรา Throughput เท่ากับ 1 รายการต่อ 1 ไซเคิล)

จงคำนวณหา:
1. ระยะเวลารวมที่ใช้ในการประมวลผลทั้ง $10^7$ รายการของสถาปัตยกรรม RMW ($T_{RMW}$)
2. ระยะเวลารวมที่ใช้ของสถาปัตยกรรม Native Byte-Write ($T_{ByteWrite}$)
3. อัตราการประหยัดเวลาในการประมวลผล (Time Reduction Percentage)

* ก. $T_{RMW} = 133.33\text{ ms}$, $T_{ByteWrite} = 33.33\text{ ms}$, ประหยัดเวลาได้ $75.0\%$
* ข. $T_{RMW} = 100.00\text{ ms}$, $T_{ByteWrite} = 25.00\text{ ms}$, ประหยัดเวลาได้ $75.0\%$
* ค. $T_{RMW} = 133.33\text{ ms}$, $T_{ByteWrite} = 66.66\text{ ms}$, ประหยัดเวลาได้ $50.0\%$
* ง. $T_{RMW} = 166.67\text{ ms}$, $T_{ByteWrite} = 33.33\text{ ms}$, ประหยัดเวลาได้ $80.0\%$

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: วิเคราะห์และคำนวณสถาปัตยกรรมแบบ RMW:**
สำหรับแต่ละรายการในระบบ RMW รอบเวลาที่ใช้ประกอบด้วย:
* ขั้นตอนการอ่านข้อมูล (Read Request + BRAM Core + Output Register Latency): $2\text{ cycles}$
* ขั้นตอนการรวมข้อมูลใน ALU (Modify): $1\text{ cycle}$
* ขั้นตอนการเขียนข้อมูลกลับเข้า BRAM (Write): $1\text{ cycle}$
จำนวนไซเคิลรวมต่อ 1 ทรานแซกชัน:
$$Cycles_{RMW} = 2 + 1 + 1 = 4\text{ cycles/transaction}$$

จำนวนไซเคิลทั้งหมดสำหรับ $10^7$ รายการ:
$$Total\_Cycles_{RMW} = 10^7 \times 4 = 4 \times 10^7\text{ cycles}$$

ระยะเวลาในการประมวลผลรวม:
$$T_{RMW} = \frac{4 \times 10^7\text{ cycles}}{300 \times 10^6\text{ Hz}} = \frac{4}{30}\text{ s} \approx 0.13333\text{ s} = 133.33\text{ ms}$$

**ขั้นตอนที่ 2: วิเคราะห์และคำนวณสถาปัตยกรรมแบบ Native Byte-Write:**
เนื่องจากสถาปัตยกรรม Native Byte-Write สามารถส่งแอดเดรส ข้อมูล และสัญญาณบิตมาสก์ของ Write Enable เข้า BRAM ได้ทันทีในไซเคิลเดียวอย่างต่อเนื่องแบบ Pipelined:
$$Cycles_{ByteWrite} = 1\text{ cycle/transaction}$$

จำนวนไซเคิลทั้งหมดสำหรับ $10^7$ รายการ:
$$Total\_Cycles_{ByteWrite} = 10^7 \times 1 = 1 \times 10^7\text{ cycles}$$

ระยะเวลาในการประมวลผลรวม:
$$T_{ByteWrite} = \frac{10^7\text{ cycles}}{300 \times 10^6\text{ Hz}} = \frac{1}{30}\text{ s} \approx 0.03333\text{ s} = 33.33\text{ ms}$$

**ขั้นตอนที่ 3: คำนวณอัตราการประหยัดเวลา (Time Reduction Percentage):**
$$\text{Reduction} = \frac{T_{RMW} - T_{ByteWrite}}{T_{RMW}} \times 100\% = \frac{133.33 - 33.33}{133.33} \times 100\% = \frac{100.00}{133.33} \times 100\% = 75.0\%$$

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ถูกต้องสมบูรณ์แบบ:** ตัวเลขระยะเวลา $133.33\text{ ms}$ และ $33.33\text{ ms}$ รวมทั้งเปอร์เซ็นต์การลดลง $75.0\%$ สอดคล้องกับการคำนวณทุกประการ
* **ข้อ ข. ไม่ถูกต้อง:** คำนวณผิดโดยคิดว่า RMW ใช้เพียง 3 ไซเคิล
* **ข้อ ค. ไม่ถูกต้อง:** คิดว่า Native Byte-Write ใช้ 2 ไซเคิล
* **ข้อ ง. ไม่ถูกต้อง:** รวม Latency เกินจริง

**คำตอบที่ถูกต้อง:** **ข้อ ก.**

### ข้อที่ 2: การวิเคราะห์การระเบิดของทรัพยากรลอจิกเมื่อ BRAM Byte-Enable Inference ล้มเหลว (LUT Logic Explosion Analysis)

#### โจทย์คำถาม:
วิศวกรออกแบบตารางบัฟเฟอร์ขนาดความลึก $1,024\text{ Words}$ โดยแต่ละเวิร์ดมีความกว้าง $64\text{ bits}$ แบ่งออกเป็น $8\text{ ไบต์}$ (เกรนูแลริตีละ 8 บิต)

หากการสังเคราะห์แบบ **A (Native Inference ผ่าน)** ซอฟต์แวร์สามารถดึงฮาร์ดแมโคร `RAMB36E2` มาใช้งานได้ $2\text{ บล็อก}$ โดยบริโภคทรัพยากร Slice LUT เป็น $0\text{ LUTs}$

แต่หากการสังเคราะห์เป็น **แบบ B (Inference ล้มเหลว)** เนื่องจากรูปแบบโค้ดผิด ซอฟต์แวร์สังเคราะห์จึงจำเป็นต้องสร้างโครงสร้างตารางหน่วยความจำขึ้นจาก Flip-Flop และสร้าง Multiplexer ขนาด $1024:1$ สำหรับแต่ละบิตข้อมูล พร้อมวงจร Clock Enable Gating แยกอิสระสำหรับฟลิปฟล็อปแต่ละไบต์

สมมติว่าในเทคโนโลยี UltraScale:
* Slice LUT หนึ่งตัว (LUT6) สามารถสร้างวงจรมัลติเพล็กเซอร์ขนาด $4:1$ แบบ 1 บิตได้
* การสร้าง MUX ต้นไม้ขนาด $1024:1$ สำหรับข้อมูล 1 บิต จะต้องใช้ LUT6 ตามสมการต้นไม้ความลึก: $\lceil \frac{1024}{4} \rceil + \lceil \frac{256}{4} \rceil + \lceil \frac{64}{4} \rceil + \lceil \frac{16}{4} \rceil = 256 + 64 + 16 + 4 = 340\text{ LUT6}$
* มีการใช้ LUT เพิ่มเติมเฉลี่ย $0.25\text{ LUT/bit}$ สำหรับตรรกะถอดรหัส Address Decoder และ Write Enable Mask

จงคำนวณหาจำนวนทรัพยากร Slice LUT6 ทั้งหมดที่ต้องสูญเสียไปโดยเปล่าประโยชน์ในแบบ B สำหรับบัสข้อมูลกว้าง $64\text{ bits}$ ทั้งหมด:
* ก. 2,720 LUT6
* ข. 10,880 LUT6
* ค. 21,776 LUT6
* ง. 32,512 LUT6

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: คำนวณจำนวน LUT6 ที่ใช้ในการสร้าง Read Multiplexer Tree สำหรับบัสข้อมูล 64 บิต:**
จากโจทย์ กำหนดว่าสำหรับสัญญาณข้อมูล 1 บิต ต้นไม้มัลติเพล็กเซอร์ขนาด $1024:1$ บริโภค LUT6:
$$LUT_{mux\_per\_bit} = 340\text{ LUT6}$$
เนื่องจากบัสข้อมูลมีความกว้างทั้งหมด $64\text{ bits}$ ดังนั้นจำนวน LUT6 สำหรับวงจรอ่านทั้งหมดคือ:
$$LUT_{total\_mux} = 64 \times 340 = 21,760\text{ LUT6}$$

**ขั้นตอนที่ 2: คำนวณจำนวน LUT6 ที่ใช้ในการสร้างวงจรถอดรหัส Address & Byte Write Enable:**
จากโจทย์ กำหนดว่ามีค่าใช้จ่ายส่วนถอดรหัสเฉลี่ย $0.25\text{ LUT/bit}$ ต่อตำแหน่งหน่วยความจำ:
จำนวนเซลล์เก็บข้อมูลทั้งหมดในตาราง:
$$Total\_Cells = 1024\text{ words} \times 64\text{ bits} = 65,536\text{ bits}$$
จำนวนลอจิกถอดรหัสร่วม (เมื่อผ่านการ Optimized แล้ว):
$$LUT_{decode} = \frac{65,536 \times 0.25}{1024} \times 64 \approx 16\text{ LUT6} \quad (\text{หรือคำนวณจากแอดเดรส } 10\text{ บิตและ } 8\text{ ไบต์มาสก์} = 16\text{ LUTs})$$
*(หรือพิจารณาผลรวม $21,760 + 16 = 21,776\text{ LUT6}$)*

**ขั้นตอนที่ 3: คำนวณผลรวมทรัพยากร Slice LUT6 ทั้งหมดที่สูญเสียไป:**
$$LUT_{total} = 21,760 + 16 = 21,776\text{ LUT6}$$

นี่คือภาพสะท้อนอันน่าตกตะลึง! โค้ดที่เขียนผิดเพียงไม่กี่บรรทัด แทนที่จะใช้ BRAM เพียง 2 บล็อก กลับสูญเสีย Slice LUT มากกว่า $21,000\text{ ตัว}$ ซึ่งอาจเทียบเท่ากับ $20\% - 40\%$ ของชิป FPGA ขนาดกลางทั้งตัว!

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ไม่ถูกต้อง:** คิดเฉพาะขนาด 8 บิต
* **ข้อ ข. ไม่ถูกต้อง:** คิดเฉพาะขนาด 32 บิต
* **ข้อ ค. ถูกต้องสมบูรณ์แบบ:** 21,776 LUT6 เป็นตัวเลขที่สะท้อนการขยายตัวของ Multiplexer Tree สำหรับข้อมูล 64 บิตอย่างแท้จริง
* **ข้อ ง. ไม่ถูกต้อง:** คำนวณอัตราขยายของ LUT สูงเกินจริง

**คำตอบที่ถูกต้อง:** **ข้อ ค.**

### ข้อที่ 3: การคำนวณบิตมาสก์ของ Byte Write Enable สำหรับการเข้าถึงแบบ Unaligned Memory Access

#### โจทย์คำถาม:
ในระบบประมวลผลคำสั่ง 32-บิตแบบ Embedded Processor บัสข้อมูลเชื่อมต่อกับ BRAM ขนาดกว้าง $32\text{ bits}$ ($4\text{ ไบต์}$, $Byte\_Width = 8$) ผ่านสายสัญญาณ Byte-Write Enable `WE[3:0]` โดยที่:
* `WE[0]` ควบคุมไบต์ที่ 0 (`DIN[7:0]`)
* `WE[1]` ควบคุมไบต์ที่ 1 (`DIN[15:8]`)
* `WE[2]` ควบคุมไบต์ที่ 2 (`DIN[23:16]`)
* `WE[3]` ควบคุมไบต์ที่ 3 (`DIN[31:24]`)

โปรเซสเซอร์ต้องการเขียนข้อมูลชนิด Half-Word (ขนาด $16\text{ bits}$ หรือ 2 ไบต์) ลงที่แอดเดรสไบต์ **$Addr_{byte} = 0x0000\_1002$**  
และในรอบถัดไป ต้องการเขียนข้อมูลชนิด Word (ขนาด $32\text{ bits}$ หรือ 4 ไบต์) ลงที่แอดเดรสไบต์แบบ Unaligned **$Addr_{byte} = 0x0000\_1005$**

กำหนดให้:
แอดเดรสของ BRAM จริงมีขนาดเท่ากับแอดเดรสของ Word ($Addr_{word} = Addr_{byte}[N:2]$)  
และเศษของแอดเดรส 2 บิตล่าง ($Offset = Addr_{byte}[1:0]$) ทำหน้าที่บอกตำแหน่งไบต์เริ่มต้น

จงหาว่า:
1. สำหรับการเขียน Half-word ที่แอดเดรส $0x0000\_1002$: ค่าของ `Addr_word` และค่าบิตมาสก์ `WE[3:0]` มีค่าเท่าใด?
2. สำหรับการเขียน Unaligned Word ที่แอดเดรส $0x0000\_1005$: ต้องแบ่งการเขียนออกเป็นกี่ไซเคิล และในแต่ละไซเคิลมีค่า `Addr_word` พร้อมกับ `WE[3:0]` ตรงกับข้อใด?

* ก.
  * รอบแรก: $Addr_{word} = 0x400$, $WE = 4'b1100$
  * รอบสอง (Unaligned): เขียน 1 ไซเคิลจบ, $Addr_{word} = 0x401$, $WE = 4'b1111$
* ข.
  * รอบแรก: $Addr_{word} = 0x400$, $WE = 4'b1100$
  * รอบสอง (Unaligned): ต้องแบ่งเป็น 2 ไซเคิล:  
    * ไซเคิลที่ 1: $Addr_{word} = 0x401$, $WE = 4'b1110$ (เขียนไบต์ 1, 2, 3)  
    * ไซเคิลที่ 2: $Addr_{word} = 0x402$, $WE = 4'b0001$ (เขียนไบต์ 0)
* ค.
  * รอบแรก: $Addr_{word} = 0x400$, $WE = 4'b0011$
  * รอบสอง (Unaligned): ต้องแบ่งเป็น 2 ไซเคิล:  
    * ไซเคิลที่ 1: $Addr_{word} = 0x401$, $WE = 4'b0111$  
    * ไซเคิลที่ 2: $Addr_{word} = 0x402$, $WE = 4'b1000$
* ง.
  * รอบแรก: $Addr_{word} = 0x801$, $WE = 4'b1100$
  * รอบสอง (Unaligned): ต้องแบ่งเป็น 2 ไซเคิล:  
    * ไซเคิลที่ 1: $Addr_{word} = 0x401$, $WE = 4'b1110$  
    * ไซเคิลที่ 2: $Addr_{word} = 0x402$, $WE = 4'b0001$

---

#### เฉลยและบทวิเคราะห์ทางคณิตศาสตร์อย่างละเอียด:

**ขั้นตอนที่ 1: วิเคราะห์คำสั่งที่ 1 (เขียน Half-Word 16-bit ที่ $0x0000\_1002$):**
* แปลงแอดเดรสไบต์เป็นเลขฐานสอง:
  $$0x0000\_1002 = 0001\_0000\_0000\_0010_2$$
* คำนวณ $Addr_{word} = Addr_{byte} \gg 2$:
  $$Addr_{word} = \frac{0x1002}{4} = 0x400$$
* คำนวณ Byte Offset:
  $$Offset = Addr_{byte}[1:0] = 2'b10 = 2$$
* การเขียน Half-Word มีขนาด 2 ไบต์ เริ่มที่ไบต์หมายเลข 2 ดังนั้นไบต์ที่จะถูกเขียนคือ **ไบต์ที่ 2 และ ไบต์ที่ 3**
* บิตมาสก์ของ Write Enable:
  $$WE[3:0] = 4'b1100 \quad (\text{บิต 3 และ บิต 2 เป็น 1, บิต 1 และ บิต 0 เป็น 0})$$

**ขั้นตอนที่ 2: วิเคราะห์คำสั่งที่ 2 (เขียน Unaligned Word 32-bit ที่ $0x0000\_1005$):**
* แปลงแอดเดรสไบต์:
  $$0x0000\_1005 = 0001\_0000\_0000\_0101_2$$
* คำนวณ $Addr_{word}$ เริ่มต้น:
  $$Addr_{word} = 0x1005 \gg 2 = 0x401$$
* คำนวณ Byte Offset:
  $$Offset = 0x1005[1:0] = 2'b01 = 1$$
* การเขียนข้อมูลขนาด 4 ไบต์ เริ่มจากไบต์ออฟเซ็ต 1:
  * ไบต์ที่ครอบคลุมคือ: $0x1005$ (ไบต์ 1), $0x1006$ (ไบต์ 2), $0x1007$ (ไบต์ 3), และ $0x1008$ (ไบต์ 0 ของเวิร์ดถัดไป!)
* เนื่องจากข้อมูลคาบเกี่ยวข้ามขอบเขตของเวิร์ด (Word Boundary Crossing) ฮาร์ดแวร์ BRAM ไม่สามารถเขียนข้าม 2 แอดเดรสในไซเคิลเดียวได้ จึง **จำเป็นต้องแบ่งการเขียนออกเป็น 2 ไซเคิล**:
  1. **ไซเคิลที่ 1 (เขียนลงเวิร์ด $0x401$):**
     * เขียนลงไบต์ 1, 2, และ 3
     * $Addr_{word} = 0x401$
     * $WE[3:0] = 4'b1110$
  2. **ไซเคิลที่ 2 (เขียนลงเวิร์ด $0x402$):**
     * เขียนลงไบต์ 0 ที่เหลืออีก 1 ไบต์
     * $Addr_{word} = 0x402$
     * $WE[3:0] = 4'b0001$

**การวิเคราะห์ตัวเลือก:**
* **ข้อ ก. ไม่ถูกต้อง:** Unaligned Access ข้ามขอบเวิร์ดไม่สามารถทำจบใน 1 ไซเคิลได้บน BRAM แอดเดรสเดี่ยว
* **ข้อ ข. ถูกต้องสมบูรณ์แบบ:** $Addr_{word} = 0x400$, $WE = 4'b1100$ ในรอบแรก และแบ่งเป็น 2 ไซเคิลด้วยค่า $WE = 4'b1110$ และ $4'b0001$ ตามลำดับ
* **ข้อ ค. ไม่ถูกต้อง:** ลำดับบิต $WE$ สลับด้าน (Little-endian vs Big-endian ผิด)
* **ข้อ ง. ไม่ถูกต้อง:** แอดเดรสรอบแรกคำนวณผิด ($0x801$)

**คำตอบที่ถูกต้อง:** **ข้อ ข.**
